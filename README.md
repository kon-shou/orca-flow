# orca-flow

Claude Code のプラグイン。Orca で、1タスク＝1 worktree の「設計 → 目視レビュー → サブエージェントで実行 → 統合」を回すためのスキル・担当・CLI をまとめたものです。

## 要るもの

- Claude Code
- Orca
- git
- Node 22.18 以上（CLI は型の取り除きで .ts をそのまま動かすので、ビルドは要りません）
- pnpm（このリポジトリ自体を開発するときだけ）

## 入れ方

Claude Code で次を流します。

```
/plugin marketplace add kon-shou/orca-flow
/plugin install orca-flow@orca-flow
```

## 使い始め方

1. リポジトリごとに1回、Orca でそのリポジトリを開き、メインのチェックアウトのタブで `/orca-flow:init` を流します。
2. 統括役のタブで `/orca-flow:new [--auto] 〈やりたいこと〉` を打つ（おまかせにするときだけ頭に `--auto` をつける）と、Orca の左にタスクが増え、設計書が書かれます。
3. 設計書を読み、よければ `/orca-flow:approve 〈ID〉` で承認します。実行はサブエージェントが進めます。
4. 「統合待ち」になったら報告と差分を読み、`/orca-flow:integrate 〈ID〉` で統合します。

Notion の要件から始めるときは、人が Notion の MCP をつないでおき（プラグインには入っていません）、統括役のタブで `/orca-flow:intake 〈チケットの URL〉` を打ちます。チケットとイシューを読んで仕様とタスクへの分け方を子ページに書き、人が「よい」と言ったあと、分けた1つずつを `new` で始めます。Notion から書き出したチケットを手元のパスで渡すと（`/orca-flow:intake 〈手元のパス〉`。URL のときと同じく新しいタブが立ちます）、そのタブで Notion を使わず、タスクも始めずに、仕様の下書きだけを一時ディレクトリに作って止まるので、設計の試しに使えます。

設計書・報告・進捗表（タスクの記録）は、既定で公開に出ません。`init` が `.gitignore` に行を足し（`--yes` のとき）、無視された記録はコミットせず、統合でメインの作業ツリーへ写します。記録は手元の clone の中にだけ残ります。config.json で tasksDir・reportsDir・progress.file を直したら、`init --yes` をもう一度流して行を確かめ、`.gitignore` をコミットしてください。移り方は [docs/spec.md](docs/spec.md) の12章を読んでください。

チームのリポジトリで差分に何も出したくないときは、`/orca-flow:init --untracked`（または `orca-flow init --untracked --yes`）で入れます。orca-flow のファイルと設定は `.git/info/exclude` で無視され、orca.yaml も置きません。かわりに、Orca の設定画面の「ワークツリーフック」の「セットアップスクリプト」に `bash "$ORCA_ROOT_PATH/.orca-flow/setup.sh"` を入れ、「セットアップが完了するまで待ってから Agent を開始」を入にします（リポジトリごと・マシンごとに1回。`init` は流すたびに手順と今の状態を出します）。決定の記録は手元に残り、コミットしません。くわしくは [docs/spec.md](docs/spec.md) の12章を読んでください。

くわしい流れと設定は [docs/spec.md](docs/spec.md) を読んでください。

## スキル

スキルは、人が自分で打つものと、orca-flow が中で使うものに分かれます。人が打つスキルは、統括役のタブ（メインのチェックアウト）などで、人が決めた節目に打ちます。中で使うスキルは、CLI・タスク長・見張りが決まった時に呼ぶので、人は打たなくてかまいません。

手順のくわしい中身は [docs/spec.md](docs/spec.md) の 10.1 にあります。ここでは、いつ・どこで打つか、何が起きるか、次に人がすることまでを書きます。

### 人が打つスキル

| スキル                 | 打つ場所                     | 概要                                              |
| ---------------------- | ---------------------------- | ------------------------------------------------- |
| `/orca-flow:init`      | 統括役のタブ                 | リポジトリに orca-flow を入れる                   |
| `/orca-flow:new`       | 統括役のタブ                 | やりたいことからタスクを1つ始める                 |
| `/orca-flow:approve`   | 統括役のタブ                 | 読んだ設計書を承認し、実行を始めさせる            |
| `/orca-flow:integrate` | 統括役のタブ                 | 統合待ちのタスクを main にマージする              |
| `/orca-flow:auto`      | 統括役のタブ                 | おまかせのタスクの一覧と、背景の待ち受け          |
| `/orca-flow:intake`    | 統括役かワークスペースのタブ | Notion の要件から仕様を書き、タスクに分けて始める |
| `/orca-flow:push`      | 統括役のタブ                 | push と PR の作成を案として積む（送らない）       |
| `/orca-flow:send`      | 統括役のタブ                 | 積んだ案を、人が承認して GitHub へ送る            |
| `/orca-flow:merge`     | 統括役のタブ                 | マージ待ちの PR を、人が承認してマージする        |
| `/orca-flow:split`     | 統括役のタブ                 | 大きくなったタスクの残りを子のタスクに分ける      |
| `/orca-flow:to-lint`   | 統括役のタブ                 | レビューで見つけた誤りを lint の決まりにする      |
| `/orca-flow:workspace` | ワークスペースのタブ         | 複数のリポジトリをまたぐ設定を作り、用意する      |
| `/orca-flow:qa-check`  | タスクのタブ                 | プレビューのブラウザで QA 項目を確かめる          |

#### `/orca-flow:init [--untracked]`

リポジトリごとに1回、メインのチェックアウトのタブで打ちます。設定・worktree の準備・設計書のテンプレートの置き方を見せ、リポジトリに合わせて直すところを人と決めてから置き、コミットします。`--untracked` をつけると、差分に何も出さずに入れます（コミットはしません）。終わったら、`new` でタスクを始められます。

#### `/orca-flow:new [--auto] 〈やりたいこと〉`

やりたいことを1つ渡すと、Orca にタスクの worktree を作り、そのタブでタスク長が設計書を書き始めます。おまかせにするときだけ頭に `--auto` をつけます。人は、カードが「設計書のレビュー待ち」になるのを待って設計書を読みます。待つ間に、別のタスクを始めてもかまいません。

#### `/orca-flow:approve 〈ID〉`

設計書を読んでよいと判断したら打ちます。設計書に「main への事前変更」があれば統括役が main に入れ、タスク長に実行を始めさせます。人の答えが設計書と違えば、先に設計書を直させてから承認します。そのあとは、カードが「統合待ち」になるまで手を出さなくてよく、「質問があります」になったときだけ、そのタスクのタブで答えます。

#### `/orca-flow:integrate 〈ID〉`

カードが「統合待ち」になり、報告と差分を読んでよいと判断したら打ちます。範囲の確認とテストの記録を確かめて main にマージし、作業中のほかのタスクに知らせます。確かめに落ちたときは、タスク長に直し方を送って止まるので、直ったらもう一度打ちます。

#### `/orca-flow:auto [引数]`

おまかせ（承認と統合の人の確認を飛ばす）のタスクの一覧を出し、統括役のタブで背景の待ち受けを始めます。番が来たタスクから、承認か統合を進めます。引数で、おまかせを外す（`off`）・つける（`on`）・決めたことを読む（`show`）こともできます。推奨が決めきれないときや大事な共有のファイルを変えるときは、今までどおり人に聞きます。

#### `/orca-flow:intake 〈チケットの URL〉`

Notion のチケットとそこから行けるイシューを読み、仕様とタスクへの分け方をチケットの子ページに書きます。人が「よい」と言ったら、分けた1つずつを `new` で始めます。Notion の MCP は人が自分でつなぎます。手元に書き出したチケットのパスを渡したときは、Notion を使わず、タスクも始めずに、仕様の下書きだけを作って止まります。複数のリポジトリをまたぐ要件は、ワークスペースのフォルダのタブで打ちます。

#### `/orca-flow:push 〈ID〉`

PR で出すときに、`integrate` のかわりに打ちます。タスクのブランチを確かめ、PR の本文を書き、push と PR の作成を案として積んで見せます。GitHub にはまだ何も送りません。カードが「送る前の確認待ち」になったら、`send` を打ちます。

#### `/orca-flow:send 〈ID〉`

積まれた送りの案（push・PR の作成・指摘への返信など）を全文で見せ、人が許可の画面で承認したものだけを GitHub へ送ります。送ったあとは見張りが PR のレビューと CI を見て、指摘があればタスク長を起こします。

#### `/orca-flow:merge 〈ID〉`

カードが「マージ待ち」になったら打ちます。確かめの結果と PR の先頭を見せ、人が許可の画面で承認したときだけマージし、続けて後始末（main の取り込み・ほかのタスクへの知らせ・worktree の片付け）をします。GitHub の画面からはマージしません。

#### `/orca-flow:split 〈ID〉`

実装が見込みを大きく超えて統合待ちになったタスクで、報告に「分ける案」があるときに打ちます。人が選んだ分け方で、残りを子の ID の新しいタスクとして始め、後続の依存と仕様のページも分けた形に合わせます。push と PR の作成はしません。

#### `/orca-flow:to-lint 〈誤りの説明〉`

人のレビューで見つけた誤り（教訓）を渡すと、「lint にできる」「テストにする」「md に残す」に分けて見せます。lint にできるときだけ、決まりを足して落ちる例と通る例で確かめるタスクを始めます。テストにするときは、新しいタスクを始める `/orca-flow:new` の1行を示して止まり、md に残すときは、そう伝えて止まります。

#### `/orca-flow:workspace [パスか URL…]`

複数のリポジトリをまたぐ要件のために、ワークスペースのフォルダのタブで打ちます。リポジトリを読んで設定（`orca-flow-workspace.json`）を人と決めて作り、用意の一覧を見せます。人がよければ、ないリポジトリの clone とプラグインの導入まで進めます。

#### `/orca-flow:qa-check 〈ID〉`

人が QA をする前に、そのタスクのタブで打ちます。依頼の QA 項目を、タスクのブランチのプレビューで AI がブラウザを動かして確かめます。事実の項目は判定し、目で見る項目は前と後の画面を撮って並べるだけにして、判定は人に任せます。コードは直しません。

### 中で使うスキル

この節のスキルは、人が打たなくてかまいません。CLI・タスク長・見張りが、決まった時に呼びます。カードの comment で今どこにいるかが分かるので、人は質問に答えるときと、人が打つスキルの番が来たときだけ動きます。

| スキル               | 呼ぶもの | 概要                                         |
| -------------------- | -------- | -------------------------------------------- |
| `/orca-flow:spec`    | CLI      | 設計書を書き、重なりを確かめてレビューを待つ |
| `/orca-flow:run`     | CLI      | 担当を動かして実装し、報告を書いて統合を待つ |
| `/orca-flow:review`  | タスク長 | 差分にコードレビューをかける                 |
| `/orca-flow:respond` | 見張り   | PR の指摘と CI の赤に答える                  |
| `/orca-flow:bump`    | 見張り   | 共通のパッケージの版を上げ直す               |

#### `/orca-flow:spec 〈ID〉 〈タスク名〉`

`new` がタスクの worktree を作ったあと、CLI がそのタブに最初に送ります。タスク長がコードと文書を読み、設計書を書き、作業中のほかのタスクとの重なりを確かめてコミットし、人の目視レビューを待ちます。決めきれないことがあれば、カードを「質問があります」にして人に聞きます。

#### `/orca-flow:run 〈ID〉`

`approve` のあと、CLI がタスクのタブに送ります。タスク長が担当を背景で動かして実装させ、確認役とコードレビューに差分を読ませ、テストを流して報告を書き、カードを「統合待ち」にします。タスク長は自分では大きな実装をしません。

#### `/orca-flow:review 〈ID〉`

タスク長が `run` の中で呼びます。差分に5つの観点（正しさ・セキュリティ・設計・テスト・運用と互換性）のコードレビューをかけ、検証役で確かめた指摘を重さで並べて返します。ファイルは変えず、カードの状態も変えません。

#### `/orca-flow:respond 〈ID〉`

PR にレビュー・コメント・CI の赤が付くと、見張りがタスク長を起こして渡します。タスク長は指摘ごとに「直す・理由を書いて直さない・質問する」の案を作り、PR ごとにまとめて人に聞きます。直したものと返信は送りの案として積まれ、人が `send` で承認したものだけが送られます。

#### `/orca-flow:bump 〈ID〉`

共通のパッケージの新しい版が出た、または共通の枝が動いたとき、見張りがアプリのタスクのタスク長に渡します。タスク長は判定を読んで版を上げ直すか取り込み直し、テストを通して push の案を積み、人に `send` を頼みます。

## Windows で使う

Windows 11 でも、Orca の上で使い、このリポジトリ自体を開発できます。sh の書き方のスキルとフックを動かすため、Git Bash を使うのが前提です。PowerShell だけの環境は範囲の外です。

要るもの：

- Git for Windows（Git Bash が入ります）
- Node 22.18 以上
- pnpm（このリポジトリ自体を開発するときだけ）
- Orca の CLI（`orca`。Windows では `orca.cmd` として呼ばれます）

設定：

- Orca の設定で、ターミナルのシェルを Git Bash にします。Orca は worktree の setup を、ターミナルのシェルが Git Bash のときだけ sh で流します。ほかのシェルだと cmd で流れ、`.orca-flow/setup.sh` が動きません。
- 改行は LF にそろえてあります（`.gitattributes`）。`core.autocrlf` が true でも、clone した `bin/orca-flow` と `setup.sh` は壊れません。

人が試す手順：

1. Git Bash で clone し、`pnpm install` を流します。
2. `pnpm lint`・`pnpm typecheck`・`pnpm test` が通ることを確かめます。
3. Orca でそのリポジトリを開き、Orca のターミナルを Git Bash にして、メインのチェックアウトのタブで `/orca-flow:init` を流します。
4. `/orca-flow:new [--auto] 〈やりたいこと〉` で worktree が増え、設計書が書かれることを確かめます。
5. 落ちたところ（コマンド、出力、使ったシェル）を控えて知らせてください。

### WSL2 で使う

WSL2 の中にリポジトリを置き、Claude Code と orca-flow の CLI も WSL の中で動かす場合の注意です。

- Windows 側の Orca は、場所を `\\wsl.localhost\Ubuntu\home\…` という Windows の形で返します。orca-flow は、WSL の中（Linux で `WSL_DISTRO_NAME` がある）では、今のディストリビューションを指すこの形を `/home/…` に戻して使います。ほかのディストリビューションの場所は戻しません。Mac と Git Bash の動きは変わりません。
- 逆向きの `--repo path:/home/…` は、Orca の WSL の入口が変換しないことがあり、`repo_not_found` になります。orca-flow は変換しないので、`orca` の名前でラッパーを PATH の先頭に置き、`--repo path:/…` だけ `wslpath -w` で Windows の形にして Orca の WSL 用 CLI に渡してください。`--worktree path:/…` は Linux の形のまま通ります。
