あなたは統括役として、次のやりたいことのタスクを始める。

やりたいこと：$ARGUMENTS

CLI は `orca-flow` で呼ぶ（プラグインの bin が PATH に入っている）。見つからなければ `"${CLAUDE_PLUGIN_ROOT}/bin/orca-flow"` で呼ぶ。終了コードは 0＝成功、1＝失敗、2＝人間か統括役の作業が先に要る、3＝git の競合。

## 手順

1. やりたいことの頭に `--auto` があれば外す（外した残りを、以降の「やりたいこと」とする。「おまかせ」で進める印として覚える）。やりたいことが空なら、人間に何をしたいかを聞いて待つ。
2. `orca-flow config --json` で設定を読む（progress・idPrefix・integratorName・baseBranch・reportsDir）。
3. 依存しそうなタスクを探す。
   - `orca-flow active` で作業中のタスクと、その書き込んでよい場所を読む。
   - 進捗表（progress.file）があれば読み、まだ統合済みでないタスクを見る。
   - やりたいことが、そのタスクの作るものや書き込む場所に関わるものを、依存の候補にする。迷うものは入れない。
4. 短い日本語のタスク名（20文字くらいまで）と、英語の slug（小文字・数字・ハイフンだけ、3語くらいまで。例：`shopping-fix`）を決める。
5. やりたいことの全文（手順1で人間に聞いた答えも含む）を、リポジトリの外の一時ファイルに書く。
   - `mktemp -d` で一時ディレクトリを作り、その中にファイルを置く。中身は Write ツールで書く。シェルのヒアドキュメントや echo で書かない（`$` やバッククォートが展開されて崩れるため）。
   - やりたいことがほかのタスクの報告の項目を指すとき（「T27 の確認事項の2」など）は、その項目の全文（見出し・起きること・根拠・推奨と理由）と、元の報告の場所と項目の番号を、依頼のファイルに写す。場所は、その報告が無視されていなければ `git show 〈baseBranch〉:〈reportsDir〉/〈ID〉.md`（〈baseBranch〉と〈reportsDir〉には手順2で読んだ実際の値を入れる。例：baseBranch が main なら `main`）、無視されていれば（メインの作業ツリーで `git check-ignore -q 〈reportsDir〉/〈ID〉.md` が成功する）メインの作業ツリーの `〈reportsDir〉/〈ID〉.md` のパスにする。無視されていればファイルを読む。報告は統合のとき、メインの作業ツリーの同じパスへ写されている。要約しない。
   - `orca-flow new --title "〈タスク名〉" --slug 〈slug〉 --request-file 〈一時ファイルのパス〉` を流す。依存があれば `--depends 〈ID〉,〈ID〉` を足す。人間が ID を指定したときだけ `--id 〈ID〉` を足す。手順1で `--auto` を外したときは `orca-flow new --auto ...` にする（`--auto` がなければ足さない）。後続のタスクを作る流れ（integrate が new の手順を読むとき）では、`--auto` をつけない。
   - new は作成のあと15秒ほど worktree が残っているかを確かめるので、その間は何も出ない。終わるまで待つ。
   - 終了コード2：メッセージ（統括役の場所でない、未コミットの変更がある、作業中のタスクが上限、など）を人間にそのまま伝え、何をすればよいかを添えて止まる。自分で直さない。
   - 終了コード1：メッセージを人間に伝えて止まる（すでにある ID、Orca が動いていない、依頼のファイルが読めない、作った worktree が15秒以内に消えた、など）。自分でやり直さない。worktree が消えたときは、メッセージの「残っているもの」と片付けのコマンドを人間に伝える（自分では流さない）。人間が中を確かめて片付けたあと、`/orca-flow:new` をもう一度流す。
6. new の終了コードにかかわらず、終わったら一時ディレクトリを消す（止まるときも消す。CLI が共通ディレクトリに写している）。成功したら、出力から ID・ブランチ・worktree のパスを読み、人間に伝える。
   - 「Orca の左に『〈ID〉 〈タスク名〉』が増えました。設計書ができたら未読の印がつきます」
   - `--auto` で作ったとき：出力に「おまかせ」が出る。人間に、次を伝える。承認と統合は統括役が進めること。止まる所（設計書の決めてほしいことの推奨が決めきれないとき・大事な共有のファイル（`.claude/` の下（CLAUDE.md を除く）・`.orca-flow/` の下・`orca.yaml`・`package.json`・`.worktreeinclude`）を変えるとき・テストの失敗や競合など）では今までどおり人間に聞くこと。決めたことは `orca-flow auto show 〈ID〉` で読めること。外すときは `/orca-flow:auto off 〈ID〉`（全部は `off --all`）。
   - 依存を付けたときは、依存先がまだ統合されていないことと、承認を依存先の統合のあとにするかは統括役が決めることを添える。

7. `--auto` で作れたときだけ、`orca-flow auto wait` を背景で流す（Bash の run_in_background）。これが統括役のタブの待ち受けで、番（承認か統合の順番）を1つ拾うと終わる。終了コード2は、ほかの待ち受けがもう動いているので何もしない。待ち受けが終わったときの扱いは `${CLAUDE_PLUGIN_ROOT}/skills/auto/SKILL.md` の「番が来たら」に従う。

## 守ること

- タスクの worktree の中のファイルを、統括役のタブから書き換えない。設計はタスク長が行う。
