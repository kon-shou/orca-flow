あなたは統括役として、次の誤りを lint の決まりに寄せるタスクを始める。

渡されたもの：$ARGUMENTS

CLI は `orca-flow` で呼ぶ（プラグインの bin が PATH に入っている）。見つからなければ `"${CLAUDE_PLUGIN_ROOT}/bin/orca-flow"` で呼ぶ。終了コードは 0＝成功、1＝失敗、2＝人間か統括役の作業が先に要る、3＝git の競合。

## 手順

1. `orca-flow config --json` で設定を読む（baseBranch・integratorName・verify・pathVerify）。
2. 元の誤りを決める。`orca-flow lessons` は入っていないことがあるので、終了コード0で使えるときだけ教訓を読む。
   - 渡されたものが空で、`orca-flow lessons` が終了コード0なら、教訓の一覧から lint にできそうな項を並べて人に選ばせる。使えないとき（終了コードが0でない・サブコマンドがない）は、人に誤りの説明を聞いて待つ。
   - 見出しが渡され、`orca-flow lessons` が使えれば、その項を全文読む。使えないか、見つからなければ、渡された文を誤りの説明として扱う。
3. 誤りを3つに分けて、理由を添えて人に示す。
   - 「lint にできる」：名前・呼び出し・import・ファイルの置き場など、コードの形で分かるもの。
   - 「テストにする」：動かして分かるもの。`/orca-flow:new [--auto] 〈やりたいこと〉` の1行を示して止まる（人に示すときは角かっこを外し、やりたいことを具体的な文にして、おまかせにするときだけ頭に `--auto` をつける。`--auto` は頭に置く。末尾に置くとやりたいことの文に混ざる）。
   - 「md に残す」：意図や設計の判断が要るもの。そう伝えて止まる。
   - 人が分け方を直したら従う。「lint にできる」以外では、ここで止まる（new を流さない）。
4. 導入先の決まりを読む。`git show 〈baseBranch〉:.orca-flow/lint.md` で読む（〈baseBranch〉には手順1で読んだ実際の値を入れる。作業ツリーのファイルではなく baseBranch のものを読む）。
   - `.orca-flow/lint.md` が無視されているとき（メインで `git check-ignore -q .orca-flow/lint.md` が成功する。untracked の導入）は、`git show` でなく、メインのチェックアウトの `.orca-flow/lint.md` のファイルを読む。新しく作るときもそこに置き、`git add` もコミットもしない（コミットしない）。以降の `git show 〈baseBranch〉:.orca-flow/lint.md` も、同じファイルを読む読み替えにする。
   - なければ、`${CLAUDE_PLUGIN_ROOT}/templates/lint.md` の見出し（「道具」「決まりの置き場」「足し方」「確かめ方」「流すコマンド」）ごとに人に聞いて作る。
   - 下書きは `mktemp -d` で作ったリポジトリの外のディレクトリに Write ツールで書く。ヒアドキュメントや echo で書かない（`$` やバッククォートが展開されるため）。中身を人に示し、「よい」が来たら次へ進む。コミットしたあとも、止まるときも、そのディレクトリを消す。
   - コミットの前に、統括役の場所であることを3つとも確かめる：`git branch --show-current` が baseBranch、`git rev-parse --git-common-dir` が `.git`（メインのチェックアウト）、`git status --porcelain --untracked-files=no` が空（追跡中のファイルに未コミットの変更がない）。満たさなければ、人に伝えて止まる（自分で直さない）。
   - 満たしたら、メインのチェックアウトに `.orca-flow/lint.md` として置き、`git add -- .orca-flow/lint.md` だけを add し、件名 `〈integratorName〉: lint の決まりの足し方を置く` でコミットする（integratorName は手順1で読んだ値）。push はしない。
   - 「道具」がまだ入っていなければ、決まりの前に道具を入れるタスクを勧めて止まる（開発用の依存は統括役が事前変更で足す）。
5. verify とのつながりを確かめる。「流すコマンド」が設定の verify か pathVerify のコマンドにあるかを見る。
   - なければ、依頼のファイルの「main への事前変更」に「`.orca-flow/config.json` の verify に〈コマンド〉を足す」と書く。足した決まりが、どのタスクの確認でも必ず流れるため。
6. 依頼のファイルを作り、タスクを始める。`${CLAUDE_PLUGIN_ROOT}/skills/new/SKILL.md` の手順4〜6（タスク名と slug を決める・一時ファイルに書いて `orca-flow new` を流す・一時ディレクトリを消す）に従い、`orca-flow new --title '〈タスク名〉' --slug 〈slug〉 --request-file 〈一時ファイルのパス〉` を流す（タスク名は一重引用符で囲み、中の ' は '\'' にする。バッククォートや $(…) をコマンドとして動かさないため。slug は小文字・数字・ハイフンだけなので囲まなくてよい）。new の終了コード1・2の扱いも、その手順に従う。依頼には次を書く。
   - 元の誤り（教訓の全文か説明）と、決まりの案、落ちる例と通る例（それぞれ1つ以上）。
   - `git show 〈baseBranch〉:.orca-flow/lint.md` を読んで、その「決まりの置き場」「足し方」に従って足すこと（〈baseBranch〉は実際の値）。完了条件の形：「確かめ方」のコマンドが落ちる例で落ち、通る例で通り、verify が全体で通る。
   - 決まりのメッセージに、教訓の決まりと理由を短く入れること（教訓を消したあとも理由が残るため）。
   - 手順5で足すものがあれば、「main への事前変更」の節。
   - 教訓から始めたときは、報告の「後回しにしたもの」に「main に入ったら教訓から消す：〈見出し〉（`orca-flow lessons remove`）」と書くこと。
7. 成功したら、出力から ID・ブランチ・worktree のパスを読み、人間に伝える。教訓は、このタスクが main に入ったあと、報告の「教訓から消す」の1行を見て人が `orca-flow lessons remove` で消すことも添える（入る前には消さない）。

## 守ること

- タスクの worktree の中のファイルを、統括役のタブから書き換えない。決まりを足す作業はタスク長のタスクとして始める。
- 教訓をこのスキルでは消さない。
- 導入先の lint の道具を、orca-flow の依存にしない。
