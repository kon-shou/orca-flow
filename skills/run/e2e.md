# E2E の確かめ（run が読む）

伴う記録（`orca-flow e2e` が読む記録）のある E2E のリポジトリのタスクで、タスク長が行う。レビューの直しが済んだあと、報告を書く前に流す（テストを直したら流し直す）。伴う記録がなければ（`orca-flow e2e 〈ID〉` が終了コード2で「伴う記録がない」と答える）、この文書は使わず、報告に一言書く。

## 流す

1. 担当がテストの追加・直しを済ませたら、worktree で `orca-flow e2e 〈ID〉` を流す。特定のテストだけ流すときは `orca-flow e2e 〈ID〉 -- 〈テストの指定〉` と書く。
   - アプリごとのコマンド（伴う記録の `command` がアプリの名前をキーにしたオブジェクト）なら、`orca-flow e2e 〈ID〉` は記録のアプリの順に1つずつ流し、1つでも落ちれば1を返す（残りも流す）。1つのアプリの分だけ流すときは `orca-flow e2e 〈ID〉 --app 〈名前〉` と書く。コマンドが2本以上でテストの指定を付けるときは `--app` が要る（`orca-flow e2e 〈ID〉 --app 〈名前〉 -- 〈テストの指定〉`。テストの指定はそのアプリのコマンドにだけ足す）。落ちたアプリだけを直して流し直すときも `--app` で絞る。キーが2つ以上なら1つずつ流すので、時間がアプリの数だけ延びる（1本あたり30分まで）。背景で流すか、`--app` で分けて流してよい。
2. 終了コードで分ける。
   - 0：通った。報告の確かめの節に、流した回数と「通った」を書く。
   - 2（そろっていない）：理由（アプリの preview の記録がない・URL が答えない・アプリの実装が済んでいない）を読む。`orca-flow e2e 〈ID〉 --wait` を背景で流して待ち、0で終わったら流し直す。`--app` で絞って流したあとでも、`--wait` には `--app` を付けない（一緒には使えず1で止まる。そろうかは記録の全部のアプリで見る）。待つ間はほかの確かめを進める。`--wait` が2で終わったとき（24時間でそろわない）は、理由を添えて `orca-flow status question` で人に聞く。`--wait` が1で終わったとき（記録が壊れているなど）は、標準エラーの文を人に伝えて止まる。プレビューの記録がないときは、親のタブで `workspace --preview 〈ブランチ名〉` が要ると人に伝える（`orca-flow status question` にして伝える）。〈ブランチ名〉はこのタスクのブランチ名（worktree で `git branch --show-current`。組は全部の子で同じ ID と短い名前で始めるので、組のブランチ名と同じ）。ID で頼まない（番号だけ同じ別のアプリのブランチがあると、CLI が止まるため）。
   - 2（土台のアプリがそろっていない）：印のアプリがこのブランチにないとき（伴う記録の `baseApps`）、`e2e` はそのアプリを依存元のタスクのプレビューか、baseBranch の先頭で立てた土台のアプリの URL で埋める。理由は、依存元のタスクのプレビューがない・答えない・依存元の実装が済んでいない、土台のアプリの記録がない・答えない、出どころを決めきれない（前を待つ印から依存元を1つに決められない）のどれか。依存元のプレビューと土台のアプリは親のタブの `workspace --preview 〈ブランチ名〉` が立てるので、上と同じく `orca-flow status question` にして人に組のプレビューを頼み、`--wait` を背景で流して待つ。依存元の実装が済んでいないだけなら `--wait` で待つ。決めきれないときは待ってもそろわないので、理由を添えて `orca-flow status question` で人に聞く。自分で土台のアプリや依存元のプレビューを立てたり止めたりせず、ほかの URL を印に書いて流さない。
   - 1（落ちた）：標準エラーの最後の数行を読み、テストを直す。直したら流し直す。
   - 1（流す前に止まった）：標準エラーが引数の誤りを言うとき（`--app` の名前が記録のキーにない・コマンドが2本以上でテストの指定があるのに `--app` がない・`--app` を `--wait` と一緒に付けたなど）は、テストを流していない。文に従って引数を直して流し直す。テストを直しに行かない。

## 録る

通ったあとの録画は `skills/run/e2e-capture.md` に従う（伴う記録に録画の設定があるときだけ）。

## 落ちたときの分け方

- テストが間違っている（待ち方・探し方・期待する文言）：テストを直す。
- アプリの不具合・プレビューのデータにテストの前提のものがない・ログイン情報がないなど、テストを直しても通らない落ち：直さずに止め、`orca-flow status question` にして、AskUserQuestion で人に聞く。アプリの直しはアプリのブランチの仕事で、E2E のタスクでは直さない。
- 同じ落ち方で2回直しても通らなければ、同じ分け方で止めて聞く。

## 守ること

- プレビューのターミナルの出力は読まず、報告にもカードにも写さない。`e2e` の標準エラーの数行も、秘密のありそうな値を報告に書かない。
- テストを消したり弱めたりして通さない。
- 結果は報告に書く（流した回数・最後の終了コード・待ったか・人に聞いたこと）。アプリごとのコマンドなら、結果をアプリごとに1行で書く（「〈アプリ〉：通った」「〈アプリ〉：落ちた（〈理由〉）」。`--json` の `runs` の `app`・`result` で読める）。
