description: 承認された orca-flow のタスクを、担当を背景で動かして実装し、確認役とコードレビューに差分を読ませ、報告を書いて統合を待つ。タスクの worktree のタブに、approve のときに CLI が送る。
argument-hint: "[ID]"
disable-model-invocation: true

あなたはタスク $0 のタスク長として、承認された設計書のとおりに実装を進める。自分では大きな実装をせず、担当に割り振る。

CLI は `orca-flow` で呼ぶ（プラグインの bin が PATH に入っている）。見つからなければ `"${CLAUDE_PLUGIN_ROOT}/bin/orca-flow"` で呼ぶ。終了コードは 0＝成功、1＝確認に落ちた・失敗、2＝人間か統括役の作業が先に要る、3＝git の競合。

ブランチを切り替えない。メインのチェックアウトを変更しない。

節目で `orca-flow status working --note "〈一言〉"` を流し、Orca のサイドバーの comment に今の作業を出す。一言は20文字くらいまでにする（CLI では切らない）。

## 手順

1. `orca-flow config --json` で設定を読む（baseBranch・tasksDir・reportsDir・verify・pathVerify・appendOnlyFiles・maxWorkersPerTask・workerAgent・reviewerAgent・codeReview・reviewBackend・localReview）。設計書 `〈tasksDir〉/$0.md` を全文読み、とくに「設計の経緯（run のときに読む）」を読む。設計で読んだファイルは、設計書と食い違うときや、直しに根拠が要るときだけ読み直す。
2. main を取り込んでいるかを確かめる：`git merge-base --is-ancestor 〈baseBranch〉 HEAD`。
   - 0以外なら、`orca-flow status question --note "main を取り込んでいません"` にして、人間に「統括役のタブで /orca-flow:approve $0 をやり直してください」と伝えて止まる。
3. `orca-flow status working --note "担当〈人数〉人が作業中"` を流す（〈人数〉は「担当の分け方」の担当の数）。
4. 「担当の分け方」の担当ごとに、workerAgent（既定は `orca-flow:task-worker`）を背景で起動する。
   - 同時に動かすのは maxWorkersPerTask まで。多ければ、終わった担当の分だけ次を起動する。
   - 渡すもの：設計書のパス、ID（$0）、担当の名前、書き込む場所、作るもの。
   - worktree を分けさせない（isolation を指定しない）。全員がこの worktree の今のブランチで動く。
5. 全員の報告を待つ。そのあと `orca-flow status working --note "テストを流している"` を流し、自分で `orca-flow verify` を流す。次の2つを行う。
   - `orca-flow verify`：main を取り込み、config の verify と当たる pathVerify を流して、通ったら記録を残す。終了コードの扱いは次のとおり。
     - 0：次へ進む。
     - 1（テストが落ちた）：標準エラーの出し方で分ける。
       - 時間切れ（「時間内に終わりませんでした」と出たとき。1つ30分）：担当に戻さず、すぐ `orca-flow status question` にして人間に伝える。環境の問題のことが多く、繰り返すと時間を使うため。時間切れは下の回数に数えない。
       - それ以外（「落ちました」）：落ちた場所の担当に戻して直させ、手順5からやり直す。落ちたコマンドごとに、落ちた回数を通算で数える（間にほかのコマンドが落ちても、通っても数え直さない）。担当に戻すのは2回まで。3回目に落ちたら、担当に戻さず `orca-flow status question` にする。その question に人間が答えて続けるときも数え直さず、次に落ちたらまた `orca-flow status question` にする（人間が毎回決められるため）。回数は、統括役から直しの指示が来たときだけ数え直す（手順6のやり直しの回数と同じ）。
     - 2（未コミットの変更）：手順9と同じく、どの担当のものかを確かめて片づけ、流し直す。
     - 3（rebase の競合。verify が abort 済み）：自分で `git rebase 〈baseBranch〉` をして競合を直し、`git rebase --continue` のあと流し直す。直せなければ `orca-flow status question` にして人間に伝える。
   - 範囲の確認（verify はしない）：`git diff --name-only 〈baseBranch〉...HEAD` のファイルが、すべて「書き込んでよい場所」・設計書・報告・appendOnlyFiles のどれかに入っていること。
6. `orca-flow status working --note "確認とコードレビュー中"` を流す（review はカードを変えないので、呼ぶ前にここで流す）。reviewerAgent（既定は `orca-flow:task-reviewer`）を背景で起動し、設計書のパスと `git diff 〈baseBranch〉...HEAD` を読ませる。確認役の報告を待たずに、codeReview が `off` でなければ、Skill で `/orca-flow:review $0 〈baseBranch〉...HEAD` を流し、コードレビューを並べて動かす。両方（`off` なら確認役だけ）の結果がそろうまで待つ。
   - `reviewBackend` が `local` なら、下のClaudeレビュー役の代わりに「ローカルレビュー（reviewBackend: local）」の節へ進む。確認役（reviewerAgent）はこれまでどおり起動し、結果を待つ。
   - codeReview が `off` なら、review を呼ばず確認役だけを起動する（review の Skill と、レビュー役・検証役の種類は確かめなくてよい）。報告の「コードレビュー」の節には「設定で止めている」と書く。
   - codeReview が `light` なら、最初の1回だけ review を呼ぶ（review がレビュー役1つで検証役なし、指摘は全部「報告に書くもの」に回す）。
   - review が「文書だけ（検証役なし）」と返したとき（設計書の要点に `- コードレビュー：文書だけ（軽く回す）` の行があり、差分が md だけのとき）は、「タスク長が確かめるもの」を1件ずつ、根拠のファイルと行を開いて確かめる。本当なら、直させるものと一緒に直す（書き込んでよい場所の中の小さな直しはタスク長、ほかは担当に戻す）。本当でなければ、理由を添えて報告の「コードレビュー」の節に書く。直したあと、タスク長が根拠をもう一度開いて、直ったかを確かめる。直しのやり直しの2回の枠は、ほかの直しと共有する。2回で直らない「必ず直す」は、review の直させるものと同じく「統合の前に人が決めるもの」で人に聞く。2回で直らない「直したほうがよい」は、混ぜたものと同じく報告に「2回で直らない」で書く。やり直しの review は、秘密と個人のパスの確かめだけを流し直す。確認役はいつもどおり動かす。
   - `off`・`light` ではやり直しの review を呼ばない（確認役の直しだけやり直す。`full` のときだけ、下のとおりやり直しの形で review を呼ぶ）。
   - review の Skill か、レビュー役・検証役（`orca-flow:code-reviewer`・`orca-flow:review-verifier`）の種類が見つからないときは、`orca-flow status question --note "プラグインの再読み込みが要る"` にして、人間に「このタブで /reload-plugins を打ってください」と頼んで待つ。再読み込みが済んだら、手順6をはじめからやり直す（確認役の結果がもう出ていれば、確認役は起動し直さない）。
   - review の結果と確認役の結果がそろったら、止まらずに次へ進む（review が返したところで番を終えない）。
   - review の「直させるもの」（「確か」の「必ず直す」）は、直す前にタスク長が根拠のファイルと行を開いて確かめる。本当でなければ、そのものを「直させるもの」から外し、理由を添えて報告の「コードレビュー」の節に書く（検証役の見落としとして扱う）。
   - 確認役の「必ず直すもの」と、review の「直させるもの」と、下の「混ぜるもの」を直す。`orca-flow status working --note "担当が直している"` を流し、その場所の担当に戻す（担当をもう一度起動し、直すことを渡す）。担当の場所の中の小さな直しは、タスク長が直してコミットしてよい。
   - 「書き込んでよい場所」の外を直す必要がある指摘は直させず、報告の「人間に決めてほしいこと」に書く（共有のファイルなら「共有のファイルの変更の依頼」に書く）。これらは次の回の「前の回の直させるもの」に書き出さない。確認役の「必ず直すもの」もなく、混ぜるものもなく、review の直させるものが全部これなら、直しに入らない（下の「報告に書くもの」と「未実施」の項目を扱ってから手順7へ進む）。
   - 直す前に `git rev-parse HEAD` を覚えておく（〈直す前のコミット〉）。直し終わったら `git diff --name-only 〈直す前のコミット〉..HEAD` を流し、空なら直っていないとして担当に戻す（review を流さない。やり直しの回数に数える）。空でなければ、直しのコミットの数（`〈直す前のコミット〉..HEAD` の数）を、直し終わったらすぐ、rebase より前に数えて覚える（rebase でコミットの名前が変わっても、数は変わらないため。作業中の rebase は数えたあとにする）。数えたあとに増えたコミットは、担当のものもタスク長のものも全部足す（担当に戻す前・片づける前の HEAD を覚え、戻ったら `〈覚えた HEAD〉..HEAD` の数を足す）。
   - 空でなければ、手順5をやり直し、`orca-flow status working --note "確認とコードレビュー中"` を流して確認役をもう一度起動する。review はやり直しの形で流す（`full` のときだけ）：Skill を流す直前に「前の回の直させるもの」として前の回の review の「直させるもの」をそのまま本文に書き出してから（review の直させるものも混ぜたものもないとき、つまり確認役の直しだけのときは「なし」と書き出す。混ぜるものだけがあるときも直しに入り、混ぜたものを「混ぜた」の印をつけて書き出す）、`/orca-flow:review $0 〈直す前のコミット〉..HEAD やり直し` を流す（〈直す前のコミット〉は下のとおり求め直したもの。レビュー役は最初の1回だけで、やり直しでは検証役1つだけが、前の回の直させるものを1件ずつ直った・直った（意図的な挙動変更）・直っていないで確かめ、直しで新しく入った問題を探す。直っていないものは「直させるもの」に残る。「前からある」の基準はいつも 〈baseBranch〉...HEAD）。
   - やり直しの review の直前に、`git rev-parse HEAD~〈数〉` が出したコミットの名前を〈直す前のコミット〉にして求め直す（`HEAD~〈数〉` を記号のまま review に渡さない。〈数〉は覚えた直しのコミットの数。手順5のやり直しで rebase が入ると、覚えたコミットの名前は古くなるため）。範囲の書き方は `〈直す前のコミット〉..HEAD` のままにする。rebase が直しのコミットを落としたときは、範囲が1つ広がるだけで、直しは漏れない。
   - 確認役の直しとコードレビューの直しを合わせて、直しのやり直しは2回まで（混ぜたものも数える）。2回で直らなかったもの（混ぜたものを除く）は、直さずに報告に書く（コードレビューのものは「コードレビュー」の節に、確認役のものは「人間に決めてほしいこと」に）。人には、下の「統合の前に人が決めるもの」で聞く。
   - 混ぜるもの：review の「報告に書くもの」のうち、検証役が「確か」とした「直したほうがよい」で、「前からある」問題でなく、書き込んでよい場所の中のものは、確認役の「必ず直すもの」と review の直させるものと一緒に担当に戻して直させる（混ぜる）。混ぜるのは最初の形の review（`/orca-flow:review $0 〈baseBranch〉...HEAD`）の分だけで、やり直しで新しく出た直したほうがよいは混ぜない（報告に回す）。やり直しの review の前の回の直させるものには「混ぜた」の印をつけて書き出し、直ったかを確かめる。どれを混ぜたか（観点・ファイルと行）は run が覚えておき、やり直しの review が直っていないとして返したものも「混ぜた」の印を保って書き出す。混ぜたものも直しのやり直しの2回の枠を共有し、2回で直らなければ報告に「2回で直らない」で書く（必ず直すものではないので、統合の前の question では聞かない）。直すと設計書の作るものを越えるものは混ぜず、報告に「設計で範囲の外」で書く（判断はタスク長）。codeReview が `light`（検証役なし）のときとローカルレビューの道は変えず、混ぜない。
   - review の「報告に書くもの」（「たぶん」、「直したほうがよい」「確認だけ」、「前からある」問題。上の「混ぜるもの」を除く）は直させずに、報告の「コードレビュー」の節に並べる。「直った（意図的な挙動変更）」は直ったものとして扱い、何をなぜ意図的に変えたかを報告に書く。
   - review が「未実施」とした観点があっても先に進む。報告の「コードレビュー」の節の観点ごとの件数に「未実施」と書き、「人間に決めてほしいこと」にも書く。人には、下の「統合の前に人が決めるもの」で聞く。
   - 統合の前に人が決めるもの：確認役の「必ず直すもの」と review の「直させるもの」（混ぜたものを除く）と文書だけの「タスク長が確かめるもの」の「必ず直す」で2回で直らなかったものと、review が「未実施」とした観点は、報告を書く前に `orca-flow status question --note "統合の前に決めてほしいことがある"` にして、見出し・起きること・推奨と理由を人間に出して答えを待つ（integrate は手順3でマージするので、マージの前に止まれるのは、integrate-wait の前のこのタブだけ）。答え（直す・後続のタスクにする・このままにする）は、手順8の「人間に決めてほしいこと」の項目に（「直す」で直ったものを除く）「人が選んだこと」として書く。未実施の観点の答えは、「直す」の代わりに「流し直す」にする。「直す」と「流し直す」のあとは、次の2つの箇条のとおりにする。
   - 人が「直す」と選んだとき（2回で直らなかったもの）は、直しの指示（下の「統括役から知らせが来たら」）と同じに、直しのやり直しの回数と手順5の終了コード1の回数を0から数え直し、`orca-flow status working --note "担当が直している"` を流して担当に戻し、手順5からやり直す。担当に戻す前に〈直す前のコミット〉（`git rev-parse HEAD`）を覚え、直しのコミットの数を上の箇条と同じに数えて、やり直しの review の直前に求め直す（差分が空なら直っていないとして数えるのも上と同じ）。review は、`full` ならやり直しの形で流し、「前の回の直させるもの」には人が「直す」を選んだもののうち review の直させるものだけを書き出す（確認役のものだけなら「なし」と書き出す）。`light`・`off` では review を呼ばない（確認役だけやり直す。`light` の「最初の1回」は数え直さない）。ここが、手順6のはじめから review を流す直しの指示との違い。また2回で直らなければ、もう一度 `orca-flow status question` で聞く（人が毎回決められる。手順5の3回目と同じ考え）。直ったものは、報告の「コードレビュー」の節の直したものに、人が「直す」を選んだと添えて書き、「人間に決めてほしいこと」には残さない。
   - 未実施の観点の答えは「流し直す」「後続のタスクにする」「このままにする」にする（見ていない観点は、担当に戻しても review が流れないため）。「流し直す」なら、最初の形の `/orca-flow:review $0 〈baseBranch〉...HEAD` をもう一度流し、出た直させるものは、ふだんの直しと同じに扱う。また未実施なら、もう一度聞く。
7. 共有のファイル（sharedPaths）の変更が要るときは、**自分で変えず、報告に書く**。それがないと先に進めないときは、`orca-flow status question --note "〈一言〉"` にして、人間に何が要るかを伝えて待つ。
8. `orca-flow status working --note "報告を書いている"` を流し、報告を `〈reportsDir〉/$0.md` に書く。設計書の「報告の形」に従い、少なくとも次を入れる：結果（完了・一部完了・未完了）、変更したファイル、実行したテストと結果、設計と違う判断、共有のファイルの変更の依頼、人間に決めてほしいこと、後回しにしたもの、コードレビュー（観点ごとの件数（未実施の観点を含む）、直したもの、残った指摘を重さの順に。2回で直らなかったものと「前からある」問題には印をつける。文書だけとして軽く回したときは「文書だけとして軽く回した」と書き、直したものに「検証役なし・タスク長が確かめた」の印をつける。テストだけとして観点を絞ったときは「テストだけとして観点を絞った」と書き、見ない3つの観点は「テストだけで絞った」と書く（未実施にしない））。ローカルレビューのときは、指摘ごとの修正の背景（元の指摘、検証の根拠、何をなぜ直したか、意図的な挙動変更、残リスク、Opusの裁定）も書く。人間の言葉で書き、関数名や手順の番号は根拠に括弧で添える程度にする。節は次のように分ける。
   - 「共有のファイルの変更の依頼」：統括役が main で行う変更と、統括役への依頼。項目ごとに、何をどう変えるか、なぜ変えるか、推奨（「main で今変える」「変えない」のどちらか1つと、理由1つ）を書く。統合のとき、選ばれたら承認とみなして main で変える。大事な変更（`.claude/` の下（CLAUDE.md を除く）・`.orca-flow/` の下・`orca.yaml`・`package.json`（ファイル全体）・`.worktreeinclude`）は、統合のとき差分を見せてから入る。
   - 「人間に決めてほしいこと」：人が選ぶもの。なければ「なし」と書く。項目ごとに次を書く。
     - 見出し：何の話かを人間の言葉で1行。
     - 残った理由：範囲の外・設計で範囲の外・前からある・2回で直らない・直しのあとに見つけた・確かめきれないから1つ。意味は、範囲の外＝直すには書き込んでよい場所の外を変える、設計で範囲の外＝直すと設計書の作るものを越える、前からある＝このタスクで入れた問題ではない、2回で直らない＝直しを2回やり直しても直らなかった、直しのあとに見つけた＝やり直しのレビューで新しく出た直したほうがよい、確かめきれない＝検証役が「たぶん」とした・未実施の観点・人が確かめる種類。
     - 起きること：人が出会う場面で1〜2文。なぜ困るかまで書く。
     - 根拠：ファイルと行・関数名・レビューの番号を括弧で短く（後続のタスクがここから元をたどる）。
     - 推奨：「後続のタスクにする」「このままにする」のどちらか1つと、理由1つ。
     - ほかの案：あれば1行。
     - 人が選んだこと：統合の前に `orca-flow status question` で聞いたものだけ。人の答えを書く。
   - 「後回しにしたもの」：設計で範囲外にしたもの、前からある問題で、今回は選ぶ必要のないもの。1項目1行で、何か・どこに書いてあるか。
   - コードレビューの「直したほうがよい」の残りは、件数があれば「人間に決めてほしいこと」に1項目にまとめて推奨をつける。まとめるときは理由ごとの件数を書く（例「直しのあとに見つけた3件・前からある1件」）。個々の指摘は「コードレビュー」の節に残す。混ぜて直したものは、「コードレビュー」の節の直したものに「直したほうがよい（混ぜた）」と印をつけて書き、「人間に決めてほしいこと」には残さない。「直しのあとに見つけた」の推奨はふだん「このままにする」にする（人が出会う場面で困るものだけ「後続のタスクにする」を推す）。
   - 統合の前に人が決めるもの（手順6の「統合の前に人が決めるもの」）は（「直す」で直ったものを除く）、「人間に決めてほしいこと」に「人が選んだこと」を添えて書く。それ以外の統合の前に直すべきものは、タスク長が直す。
9. 先に、この worktree で `git check-ignore -q 〈reportsDir〉/$0.md` を流して、報告が無視されているかを確かめる（成功＝終了コード0なら無視されている。追跡中のファイルは当たらない）。無視されていればコミットしない（integrate がマージの前にメインの作業ツリーへ写す）。無視されていなければ、報告を `git add 〈reportsDir〉/$0.md && git commit -m "$0: 報告を書く"` でコミットする。`git add -f` は使わない（無視を破ると記録が公開に出る）。`git status --porcelain` で、未コミットの変更が残っていないことを確かめる。残っていれば、どの担当のものかを確かめて片づける。
10. 報告をコミットしたときは、そのコミットで HEAD が動き、手順5の記録が使えなくなるので、`orca-flow verify` をもう一度流す。報告が無視されていてコミットしなかったときは、HEAD が動かず手順5の記録がそのまま使えるので、verify を流し直さない（片づけでコミットしたときだけ流し直す）。流すときの扱いは次のとおり（終了コードの扱いは手順5と同じ。落ちたら、直したあと報告も直してコミットし直す）。通ったら `git status --porcelain` が空かを確かめる。空でなければ、手順9と同じく、どの担当のものかを確かめて片づける。コミットせずに片づけた（消した・元に戻した）なら、HEAD が動かず verify の記録が使えるので、verify を流し直さず `git status --porcelain` だけ見直す。片づけでコミットしたときだけ `orca-flow verify` を流し直す。前に片づけたファイルがまた出たかは、`git status --porcelain --untracked-files=all` で見る（`git -c core.quotePath=false status --porcelain --untracked-files=all` として流し、日本語の名前を `"` で囲ませない。空白を含む名前はこれでも囲まれる。追跡外のフォルダも、中のファイルごとに出る）。手順9か手順10で前に片づけたファイルが verify のあとにまた出たら、テストが毎回作るものとみなす。`??` の行（追跡外のファイル）だけを、1つずつ `rm -- '〈パス〉'` で消して進み（フォルダごと消さない）、手順11の伝え方に「〈ファイル〉を `.gitignore` に足してほしい」と添える。パスが `"` で始まる（git が引用した特殊な名前）か `'` を含むとき、`??` 以外の行（追跡中のファイル）がまた出たとき、消してよいか分からないファイルのときは、元に戻さず、消さずに `orca-flow status question` にして人間に聞く。空なら `orca-flow status integrate-wait` を流す。
11. 報告の要点（結果・テスト）を5行くらいで伝える。「人間に決めてほしいこと」があれば、項目ごとに見出し・推奨に残った理由を添えて1行ずつ出す。「人が選んだこと」のある項目には人の答えを添える。「統合のとき統括役が選択肢で聞くので、今答えなくてよい」は、人が選んだことのない項目だけに言う。そのうえで「報告と差分を読んで、よければ統括役のタブで /orca-flow:integrate $0」と添えて**止まる**。

## ローカルレビュー（reviewBackend: local）

確認役（reviewerAgent）はこの節でも起動し、結果を待つ。コードレビューは `orca-flow review-local` と `orca-flow review-ledger` で回す。`codeReview` が `off` ならこの節は行わない。

### 共通の決まり

- 1周分は `orca-flow review-local $0 〈範囲〉 first|redo --stage 〈段〉 --cycle 〈周〉 --verify-result 〈verify の結果〉 --json` で流す。返る `mustFix` と `report` を使う。範囲は最初が `〈baseBranch〉...HEAD`、やり直しが `〈直す前のコミット〉..HEAD`。
- やり直しの範囲：`redo` の〈直す前のコミット〉は、手順6と同じに求める。直す前に `git rev-parse HEAD` を覚え、直し終わったらすぐ、rebase より前に直しのコミットの数を数えて覚える（数えたあとに増えたコミットも足す）。`review-local` を流す直前に、`git rev-parse HEAD~〈数〉` が出したコミットの名前を〈直す前のコミット〉にして求め直す（`HEAD~〈数〉` を記号のまま渡さない。手順5のやり直しで rebase が入ると、覚えたコミットの名前は古くなるため）。範囲の書き方は `〈直す前のコミット〉..HEAD` のままにする。
- 直しの差分が空：直し終わったら `git diff --name-only 〈直す前のコミット〉..HEAD` を流し、空なら直っていないとして担当に戻す。`review-local` を流さず、その段を止める（担当に戻して直らないまま周を進めない。手順6と同じにやり直しの回数に数え、2回で直らなければ報告に書く）。
- `mustFix` が0件で `localReview.stopOnNoMustFix` が true なら、その段のローカルレビューを終える。やり直しの検証が `fixed_intentional` を返したら、意図的な挙動変更として台帳と報告に残す。
- `mustFix` を直すときは、その場所の担当（Sonnet）に、指摘・検証の根拠・直し方の案・設計書を渡す。修正メモ（指摘ID、変えたファイルと行（`src/foo.ts:12` か `src/foo.ts:12-20`）、何をなぜ変えたか、意図的な挙動変更か、テスト、残リスク、前の修正を戻す理由）を JSON にして、worktree の外の一時ファイルに書く。`orca-flow review-ledger record-fix --stage 〈段〉 --input 〈ファイル〉` で台帳に記録する。
- `record-fix` が終了コード1で「前の修正と重なる」と言ったら、担当に戻す前に `revertJustification` を修正メモに足す。足せないなら、その修正はせず、Opus検証か人間に回す。
- 修正のあと `orca-flow verify` を流す。終了コードの扱いは手順5と同じ。終了コード1のとき、時間切れ（「時間内に終わりませんでした」）は担当に戻さず、すぐ `orca-flow status question` にする。それ以外（「落ちました」）は、手順5と同じく落ちたコマンドごとに落ちた回数を通算で数える（間にほかのコマンドが落ちても、通っても数え直さない）。担当に戻すのは2回まで、3回目で `orca-flow status question` にする。これに加えて、同じテストで2回続けて落ちたら、その段を止めて人間に渡す。
- 同じ指紋の must-fix が `localReview.repeatLimit` 周続いたら、その段を止める。時間が `localReview.maxMinutes` を超えたら止める。修正が `maxFixLines` を超えたら、いったん止めて人間に渡す。
- ローカルが2回続けて失敗したら、`localReview.fallback` に従う。`claude-once` なら `/orca-flow:review $0 〈baseBranch〉...HEAD` を1回だけ流し、その結果で修正し、再レビューはしない。`human` なら `status question` にして人間に渡す。

### 終わったあと

ローカルレビュー（`light`・`full`）が終わったら、手順7へ進む。そのあとの手順8〜11は変わらない。報告のあとの手順9（片づけ）と手順10（`orca-flow verify` の流し直し）は、Claude のレビューと同じに行う。

### codeReview: light

1. `review-local ... first --stage 1 --cycle 1` を1回流す。
2. must-fix をSonnetに直させ、修正メモを台帳に記録し、`orca-flow verify` を流す。
3. 修正後の確認として `review-local ... redo --stage 1 --cycle 2` を1回だけ流す。
4. Opus検証はしない。追加の周回もしない。残った指摘、直した内容と意図、残リスクを報告に書く。

### codeReview: full

1段目は最大 `localReview.stageLimits[0]` 周（既定5）。`localReview.fullReviewAt` の周は `first`、それ以外は `redo`。must-fix がなくなったら早く終える。

1. 1段目の各周で、`review-local` を `first` か `redo` で流し、must-fix を直し、修正メモを台帳に記録し、`orca-flow verify` を流す。
2. 1段目が終わったら、`orca-flow:stage-verifier` を背景で起動する。渡すもの：ID、設計書、baseBranch、`git diff 〈baseBranch〉...HEAD`、台帳のパス、直近の verify の結果、`localReview.humanReviewCategories`。台帳は `orca-flow review-ledger show --stage 1 --json` で取れる。
3. stage-verifier の裁定を1件ずつ `orca-flow review-ledger record-opus --stage 1 --input 〈ファイル〉` で記録する。`must_fix` に `newEvidence` がなければ、その裁定は受け取らない。1回だけ stage-verifier に再裁定を頼み、それでもなければ人間に渡す。`newFindings` があれば、1件ずつ `orca-flow review-ledger record-finding --stage 1 --input 〈ファイル〉` で台帳に足す（`verdict` は付けない。stage-verifier が見つけた新しい指摘として `confirmed` で入る）。`humanReview` が true のものはSonnetに戻さず、報告の「人間に決めてほしいこと」に書く。その段の終わりに `status question` にする。
4. `must_fix` がなければ、2段目は行わない。`needs_human` があれば `status question` にして人間に渡す。報告に、`accept_intentional`・`low_risk_ignore`・`needs_human` と理由を書く。
5. `must_fix` があればSonnetに直させ、修正メモを記録し、`orca-flow verify` を流す。2段目は最大 `localReview.stageLimits[1]` 周（既定3）。各周で `review-local` を流し、1周目は `first`、2周目は `redo`、3周目は `first`。
6. 2段目のあと、`orca-flow:stage-verifier` をもう1回起動し、段2の台帳を渡す（Opus検証は `localReview.opusChecks` 回まで）。`must_fix` が残ったら、追加のローカル周回はせず、`status question` にして人間に渡す。`accept_intentional`・`low_risk_ignore`・`needs_human` は理由とともに報告に書く。`needs_human` があれば `status question` にして人間に渡す。
7. 台帳（`〈git の共通ディレクトリ〉/orca-flow/reviews`）はコミットしない。報告の「コードレビュー」の節に、指摘ごとの結果、直した内容と意図、意図的に変えた挙動、見逃したリスクと理由を書く。人に選んでほしいことは「人間に決めてほしいこと」の節に書く。

## 統括役から知らせが来たら

- 「main に 〈ID〉 が入りました」：
  - 作業中（担当が動いている間）：rebase しない。担当が全員終わった区切りで `git rebase 〈baseBranch〉` をし、手順5（`orca-flow verify`）を流す。競合したら直して `git rebase --continue` で終える。直せなければ `orca-flow status question` にして人間に伝える。
  - 統合待ち（integrate-wait にしたあと）：始めに `orca-flow status working --note "テストを流し直している"` を流し（人間に流し直し中と見え、integrate を打たずに待てる）、`orca-flow verify` を流し直す。通ったら `git status --porcelain` が空かを確かめ、空なら `orca-flow status integrate-wait` に戻す（未読の印がもう一度つく）。
    - `orca-flow verify` の終了コードが0以外（1・2・3のどれでも）なら、直さずに `orca-flow status question` にして、終了コードと理由を人間に伝える（人間が報告を読んでいる最中のため。3でも自分で rebase しない）。
    - `git status --porcelain` が空でなければ、直さずに `orca-flow status question` にして、残っているファイルを人間に伝える。
- 「main に 〈ID〉 が入り、main の確かめが通りました」（「main の確かめが通りました」を含む知らせ。統括役の設定が after-merge のとき）：
  - 作業中（担当が動いている間）：上の「main に 〈ID〉 が入りました」の作業中と同じに、担当が全員終わった区切りで `git rebase 〈baseBranch〉` をし、手順5（`orca-flow verify`）を流す。競合したら直して `git rebase --continue` で終える。直せなければ `orca-flow status question` にして人間に伝える。
  - 統合待ち（integrate-wait にしたあと）：何もしない。rebase も `orca-flow verify` もしない（HEAD が動くと、integrate が使うテストの記録が使えなくなるため。main の確かめは統括役が済ませている）。
  - 「main の確かめが通りました」を含まない知らせは、上のとおりに扱う。
- 「orca-flow verify をやり直して integrate-wait に戻して」（integrate が記録を使えずに戻したとき）：上の統合待ちと同じに扱う。
- 直しの指示が来たら、担当に戻すか自分で直し、手順5〜11をやり直す。手順5の `orca-flow verify` が通ったあと（main を取り込んだあと）に codeReview を読み直す（`orca-flow config --json`。main の設定の変更を拾うため）。手順6の直しのやり直しの回数と、手順5の終了コード1の回数は、ここで数え直す（0回から）。`light` の「最初の1回」も数え直し、手順6で review を1回呼ぶ（`full` が手順6のはじめから review を流し直すのと合わせるため）。
