あなたはタスク $0 のタスク長として、承認された設計書のとおりに実装を進める。自分では大きな実装をせず、担当に割り振る。

CLI は `orca-flow` で呼ぶ（プラグインの bin が PATH に入っている）。見つからなければ `"${CLAUDE_PLUGIN_ROOT}/bin/orca-flow"` で呼ぶ。終了コードは 0＝成功、1＝確認に落ちた・失敗、2＝人間か統括役の作業が先に要る、3＝git の競合。

ブランチを切り替えない。メインのチェックアウトを変更しない。

節目で `orca-flow status working --note "〈一言〉"` を流し、Orca のサイドバーの comment に今の作業を出す。一言は20文字くらいまでにする（CLI では切らない）。

## 人に聞くとき

人の答え（選ぶ・許す・自由な言葉）で次の手が分かれる所は、本文に説明を書いてから、Claude Code の質問の画面（AskUserQuestion）で聞く。

- 当たる所：人の答えで次の手が分かれる所。答えを求めず、人か統括役の作業を頼んで知らせを待つ所（`orca-flow tell` を待つ所や見張りの起こしを待つ所）は、今までどおり文で伝える。開いた画面では Orca が入力欄を読めず、統括役の知らせと見張りの起こしが届かないため、知らせを待つ所は文のままにする。
- 形：本文に説明を書いてから AskUserQuestion を出す。説明（見出し・起きること・根拠・推奨と理由）を画面の中に詰めない。推奨の選択肢を先頭にして「（Recommended）」をつける。
- 数：1回に4問まで、1問に選択肢4つまで。4問を超えるときは、手順が聞く順に4問ずつ分け、答えが返ってから次を出す。
- 選択肢になじまない問い（許可・自由な答え）は、「許す」「許さない」などの短い選択肢で出し、自由な答えは「その他」で受ける。
- カード：タスク長は、今までどおり先に `orca-flow status question --note "〈一言〉"` を流してから聞く。答えのあとの扱い（status を戻す・引き継ぎに書く・vote を流すなど）は、各手順のとおりにする。
- 聞くのは、いつもこの会話の本人。背景の担当とレビュー役は画面を出せないので、聞きたいことはタスク長に返す。
- このスキルで当たる所：手順6の「統合の前に人が決めるもの」、教訓を聞く所、ローカルレビューで人に渡す所（`needs_human` など）、共通の版を人に聞く所（「共通の枝を取り込むとき」）。

## 手順

1. `orca-flow config --json` で設定を読む（baseBranch・tasksDir・reportsDir・decisionsFile・verify・pathVerify・appendOnlyFiles・maxWorkersPerTask・workerAgent・reviewerAgent・codeReview・strictReviewRounds・reviewBackend・localReview・taskEnd。taskEnd がない・読めないときは "integrate" として扱う）。設計書 `〈tasksDir〉/$0.md` を全文読み、とくに「設計の経緯（run のときに読む）」と、あれば「決定の記録の文案」を読む。あわせて `orca-flow lessons` で教訓（人のレビューで見つけた誤りの決まり）を読み、割り振りと直しの指示で避ける。担当には `orca-flow lessons --path` が出す絶対パスを渡す。先に読む文書の絶対パスは、review のスキルの手順2と同じにそろえて集める（なければ渡さない。ここでは読まず、渡すだけにする）。担当と確認役に渡す。設計で読んだファイルは、設計書と食い違うときや、直しに根拠が要るときだけ読み直す。
2. main を取り込んでいるかを確かめる：`git merge-base --is-ancestor 〈baseBranch〉 HEAD`。
   - 0以外なら、`orca-flow status question --note "main を取り込んでいません"` にして、人間に「統括役のタブで /orca-flow:approve $0 をやり直してください」と伝えて止まる。
3. `orca-flow status working --note "担当〈人数〉人が作業中"` を流す（〈人数〉は「担当の分け方」の担当の数）。
4. 「担当の分け方」の担当ごとに、workerAgent（既定は `orca-flow:task-worker`）を背景で起動する。
   - 同時に動かすのは maxWorkersPerTask まで。多ければ、終わった担当の分だけ次を起動する。
   - 渡すもの：設計書のパス、ID（$0）、担当の名前、書き込む場所、作るもの、教訓の絶対パス（`orca-flow lessons --path` の出力。ファイルがなくても渡す）、先に読む文書の絶対パス（手順1で集めたもの。なければ渡さない）。担当に直しを戻すとき（起こし直し）も、同じ先に読む文書の絶対パスを渡す。
   - タスク長が担当の場所の小さな直しを自分でするときも、先に読む文書にファイルの種類（パターン）ごとに読む決まりの表があれば、直すファイルに当たる決まりだけを読んでから直す。当たらないものは読まない。
   - worktree を分けさせない（isolation を指定しない）。全員がこの worktree の今のブランチで動く。
5. 全員の報告を待つ。そのあと `orca-flow status working --note "テストを流している"` を流し、自分で `orca-flow verify` を流す。次の2つを行う。
   - `orca-flow verify`：main を取り込み、config の verify と当たる pathVerify を流して、通ったら記録を残す。終了コードの扱いは次のとおり。
     - 0：次へ進む。
     - 1（テストが落ちた）：標準エラーの出し方で分ける。
       - 時間切れ（「時間内に終わりませんでした」と出たとき。1つ30分）：担当に戻さず、すぐ `orca-flow status question` にして人間に伝える。環境の問題のことが多く、繰り返すと時間を使うため。時間切れは下の回数に数えない。
       - それ以外（「落ちました」）：落ちた場所の担当に戻して直させ、手順5からやり直す。落ちたコマンドごとに、落ちた回数を通算で数える（間にほかのコマンドが落ちても、通っても数え直さない）。担当に戻すのは2回まで。3回目に落ちたら、担当に戻さず `orca-flow status question` にする。その question に人間が答えて続けるときも数え直さず、次に落ちたらまた `orca-flow status question` にする（人間が毎回決められるため）。回数は、統括役から直しの指示が来たときだけ数え直す（手順6のやり直しの回数と同じ）。
     - 2（未コミットの変更）：手順9と同じく、どの担当のものかを確かめて片づけ、流し直す。
     - 3（取り込みの競合。verify が abort 済み）：自分で `git merge 〈baseBranch〉` をして競合を直し、`git add` と `git commit --no-edit` で終えてから流し直す。直せなければ `orca-flow status question` にして人間に伝える。
   - スナップショットのテストが落ちたとき：変化が設計か直しの意図どおりなら、設計書の更新のコマンドで基準を直し、報告に何をなぜ更新したかを書く。基準を直したらコミットし、手順5からやり直す。設計書に更新のコマンドがない、または基準のファイルが「書き込んでよい場所」に入っていないなら、直さず `orca-flow status question` にして人間に聞く。意図しない変化（デグレ）なら、担当に戻して直す（回数は上の落ちた回数に数える）。
   - 範囲の確認（verify はしない）：`git diff --name-only 〈baseBranch〉...HEAD` のファイルが、すべて「書き込んでよい場所」・設計書・報告・appendOnlyFiles のどれかに入っていること。
6. `orca-flow status working --note "確認とコードレビュー中"` を流す（review はカードを変えないので、呼ぶ前にここで流す）。reviewerAgent（既定は `orca-flow:task-reviewer`）を背景で起動し、設計書のパスと `git diff 〈baseBranch〉...HEAD` を読ませ、先に読む文書の絶対パス（手順1で集めたもの。なければ渡さない）も渡す。確認役の報告を待たずに、codeReview が `off` でなければ、Skill で `/orca-flow:review $0 〈baseBranch〉...HEAD` を流し、コードレビューを並べて動かす。両方（`off` なら確認役だけ）の結果がそろうまで待つ。
   - `reviewBackend` が `local` なら、下のClaudeレビュー役の代わりに「ローカルレビュー（reviewBackend: local）」の節へ進む。確認役（reviewerAgent）はこれまでどおり起動し、結果を待つ。
   - codeReview が `off` なら、review を呼ばず確認役だけを起動する（review の Skill と、レビュー役・検証役の種類は確かめなくてよい）。報告の「コードレビュー」の節には「設定で止めている」と書く。
   - codeReview が `light` なら、最初の1回だけ review を呼ぶ（review がレビュー役1つで検証役なし、指摘は全部「報告に書くもの」に回す）。
   - codeReview が `strict` なら、下の「厳格モード（codeReview: strict）」の節のとおりに回す（最初の review は `full` と同じ最初の形。直しが入るたびに最初の形を全部流し直す）。このあとの「混ぜるもの」と、2回目のやり直しの新しい「必ず直す」と、最後の review のあとの確かめは、`strict` では使わない（全部直して流し直すため。最後の review のあとの直しも、厳格モードの節のとおり最初の形を流し直して確かめる）。
   - review が「文書だけ（検証役なし）」と返したとき（設計書の要点に `- コードレビュー：文書だけ（軽く回す）` の行があり、差分が md だけのとき）は、「タスク長が確かめるもの」を1件ずつ、根拠のファイルと行を開いて確かめる。本当なら、直させるものと一緒に直す（書き込んでよい場所の中の小さな直しはタスク長、ほかは担当に戻す）。本当でなければ、理由を添えて報告の「コードレビュー」の節に書く。直したあと、タスク長が根拠をもう一度開いて、直ったかを確かめる。直しのやり直しの2回の枠は、ほかの直しと共有する。2回で直らない「必ず直す」は、review の直させるものと同じく「統合の前に人が決めるもの」で人に聞く。2回で直らない「直したほうがよい」は、混ぜたものと同じく報告に「2回で直らない」で書く。やり直しの review は、秘密と個人のパスの確かめだけを流し直す。確認役はいつもどおり動かす。
   - 戻した判断事項の確かめ：人が「戻す」を選んだ判断事項は、やり直しの review が確かめない形（文書だけ・`light`・`off`。review は秘密とパスの確かめだけか、何も呼ばない）では、誰も確かめないまま統合される。そこで、タスク長が根拠のファイルと行を開いて、戻ったかを確かめる。戻っていなければ担当に戻し、回数は直しのやり直しの2回の枠と共有する。2回で直らなければ、もう一度 `orca-flow status question` で聞く。`full` は検証役が確かめるので、重ねて確かめない（検証役が確かめるのは、`reviewBackend` が `claude` の `full` だけ。`local` は検証役が確かめないので、`light`・`full` とも「ローカルレビュー（reviewBackend: local）」の節の「戻した判断事項の確かめ」のとおり、タスク長が確かめる）。直ったものは、報告の「コードレビュー」の節の直したものに、人が「戻す」を選んだことと「タスク長が確かめた」を添えて書く。
   - `off`・`light` ではやり直しの review を呼ばない（確認役の直しだけやり直す。`full` のときだけ、下のとおりやり直しの形で review を呼ぶ。`strict` は、やり直しの形でなく最初の形を流し直す）。
   - review の Skill か、レビュー役・検証役（`orca-flow:code-reviewer`・`orca-flow:review-verifier`）の種類が見つからないときは、`orca-flow status question --note "プラグインの再読み込みが要る"` にして、人間に「このタブで /reload-plugins を打ってください」と頼んで待つ。再読み込みが済んだら、手順6をはじめからやり直す（確認役の結果がもう出ていれば、確認役は起動し直さない）。
   - review の結果と確認役の結果がそろったら、止まらずに次へ進む（review が返したところで番を終えない）。
   - review の「直させるもの」（「確か」の「必ず直す」）は、直す前にタスク長が根拠のファイルと行を開いて確かめる。本当でなければ、そのものを「直させるもの」から外し、理由を添えて報告の「コードレビュー」の節に書く（検証役の見落としとして扱う）。
   - review の「判断事項」の群（`判断事項：〈項目の名前〉` の印のついた指摘。重さによらず、検証役を通らない）は、タスク長が根拠のファイルと行を1件ずつ開いて確かめる。本当なら、直させずに下の「統合の前に人が決めるもの」に入れる（答えは「このままにする」「戻す」「後続のタスクにする」。「戻す」なら、直しと同じに担当へ戻す）。本当でなければ、理由を添えて報告の「コードレビュー」の節に書く。どちらも報告の「人間に決めてほしいこと」には印つきで残す（「戻す」で直ったものは、「直す」で直ったものと同じく残さない）。判断事項の項目は、設計の選択・マイグレーション・公開 API の変更・依存の追加と更新・テストの削除や無効化・セキュリティに関わる変更・データの消失の7つ。
   - 確認役の「必ず直すもの」と、review の「直させるもの」と、下の「混ぜるもの」を直す。`orca-flow status working --note "担当が直している"` を流し、その場所の担当に戻す（担当をもう一度起動し、直すことを渡す）。担当の場所の中の小さな直しは、タスク長が直してコミットしてよい。
   - 「書き込んでよい場所」の外を直す必要がある指摘は直させず、報告の「人間に決めてほしいこと」に書く（共有のファイルなら「共有のファイルの変更の依頼」に書く）。これらは次の回の「前の回の直させるもの」に書き出さない。確認役の「必ず直すもの」もなく、混ぜるものもなく、review の直させるものが全部これなら、直しに入らない（下の「報告に書くもの」と「未実施」の項目を扱ってから手順7へ進む）。
   - 直す前に `git rev-parse HEAD` を覚えておく（〈直す前のコミット〉）。直し終わったら `git diff --name-only 〈直す前のコミット〉..HEAD` を流し、空なら直っていないとして担当に戻す（review を流さない。やり直しの回数に数える）。空でなければ、直し終わったらすぐ、取り込みより前に `git rev-parse HEAD` で先頭を覚える（〈直し終わりの先頭〉。作業中の取り込みは覚えたあとにする）。覚えたあとに担当やタスク長が直しを足したら、その直しが済んだ先頭に覚え直す。
   - 空でなければ、手順5をやり直し、`orca-flow status working --note "確認とコードレビュー中"` を流して確認役をもう一度起動する（手順6のはじめと同じく、先に読む文書の絶対パスも渡す）。review はやり直しの形で流す（`full` のときだけ）：Skill を流す直前に「前の回の直させるもの」として前の回の review の「直させるもの」をそのまま本文に書き出してから（review の直させるものも混ぜたものもないとき、つまり確認役の直しだけのときは「なし」と書き出す。混ぜるものだけがあるときも直しに入り、混ぜたものを「混ぜた」の印をつけて書き出す。人が「戻す」と選んだ判断事項は「戻した判断事項」の印をつけて書き出す。下の「統合の前に人が決めるもの」の箇条を見る）、`/orca-flow:review $0 〈直す前のコミット〉..〈直し終わりの先頭〉 やり直し` を流す（範囲は下のとおり。レビュー役は最初の1回だけで、やり直しでは検証役1つだけが、前の回の直させるものを1件ずつ直った・直った（意図的な挙動変更）・直っていないで確かめ、直しで新しく入った問題を探す。直っていないものは「直させるもの」に残る。「前からある」の基準はいつも 〈baseBranch〉...HEAD）。
   - やり直しの review の範囲は `〈直す前のコミット〉..〈直し終わりの先頭〉` にする（`..HEAD` にしない。手順5の取り込みで入った main の変更が範囲に入るため。覚え直したあとに取り込みが入っていれば、範囲が広がるだけで、直しは漏れない）。
   - 確認役の直しとコードレビューの直しを合わせて、直しのやり直しは2回まで（混ぜたものも数える）。2回で直らなかったもの（混ぜたものを除く）は、直さずに報告に書く（コードレビューのものは「コードレビュー」の節に、確認役のものは「人間に決めてほしいこと」に）。人には、下の「統合の前に人が決めるもの」で聞く。
   - 混ぜるもの：review の「報告に書くもの」のうち、検証役が「確か」とした「直したほうがよい」で、「前からある」問題でなく、書き込んでよい場所の中のものは、確認役の「必ず直すもの」と review の直させるものと一緒に担当に戻して直させる（混ぜる）。混ぜるのは、最初の形の review（`/orca-flow:review $0 〈baseBranch〉...HEAD`）の分と、1回目のやり直し（最初の直しのあとのやり直しの review）で新しく出た分。1回目のやり直しで新しく出た直したほうがよいは、上と同じ条件（検証役が「確か」・「前からある」でない・書き込んでよい場所の中・設計の範囲内）なら、2回目の直しに混ぜて直させる（「混ぜた」の印と2回の枠も最初の形の分と同じ）。2回目のやり直しで新しく出た直したほうがよいは混ぜず、報告に回す（残った理由は「直しのあとに見つけた」）。やり直しの review の前の回の直させるものには「混ぜた」の印をつけて書き出し、直ったかを確かめる。どれを混ぜたか（観点・ファイルと行）は run が覚えておき、やり直しの review が直っていないとして返したものも「混ぜた」の印を保って書き出す。混ぜたものも直しのやり直しの2回の枠を共有し、2回で直らなければ報告に「2回で直らない」で書く（必ず直すものではないので、統合の前の question では聞かない）。直すと設計書の作るものを越えるものは混ぜず、報告に「設計で範囲の外」で書く（判断はタスク長）。codeReview が `light`（検証役なし）のときとローカルレビューの道は変えず、混ぜない。
   - 2回目のやり直しの review で新しく出た「確か」の「必ず直す」（直しで新しく入った問題）：3回目の直しに入らず、直さない。下の「統合の前に人が決めるもの」に入れて人に聞く（答えは「直す」「後続のタスクにする」「このままにする」）。報告の「人間に決めてほしいこと」に残る理由は「直しのあとに見つけた」にする。1回目のやり直しで新しく出た「必ず直す」は、今までどおり2回目の直しで直す。
   - 最後の review のあとの確かめ（`full` で、最後に流した review のあとにコードを直したとき）：手順6の最後の review（最初の形でもやり直しの形でも、最後に流したもの）が返ったときの先頭を〈最後のレビューの先頭〉として覚えておく。そのあと報告を書くまでに（手順10の verify が落ちた直しを含む）、設計書・報告・decisionsFile の外のファイルを直したとき（`git log --first-parent --no-merges --name-only --pretty=format: 〈最後のレビューの先頭〉..HEAD` から、設計書・報告・decisionsFile を除いて残る。main の取り込みで入った変更は数えない。手順5や手順10の verify が落ちた直し、画面の記録のあとの直し、教訓を聞いたあとの直しを含む）は、報告を書く前（手順10の直しなら、報告を直してコミットし直す前）に、やり直しの形を流す：前の回の直させるものは「なし」と書き出し、`/orca-flow:review $0 〈直す前のコミット〉..〈直し終わりの先頭〉 やり直し` を流す（〈直す前のコミット〉は、その直しを始める前、取り込みのあとに `git rev-parse HEAD` で覚えた先頭。〈直し終わりの先頭〉は上の箇条と同じに、取り込みより前に覚える。`〈最後のレビューの先頭〉..` にしない。verify が落ちた直しは verify の取り込みのあとに来るので、main の変更が範囲に入るため。直しが2つ以上あって間に取り込みが入るときは、取り込みをまたがず、直しごとに範囲を分けて流す）。この確かめは直しのやり直しの2回の枠に数えない。確かめのあとにさらに直したときは、その直しの分にもう一度流す（出たものを直さないので、ループにならない）。出たものは直さない：「確か」の「必ず直す」は「統合の前に人が決めるもの」に入れて聞き（残った理由は「直しのあとに見つけた」）、ほかは報告の「コードレビュー」の節に書く（「直したほうがよい」は「直しのあとに見つけた」として「人間に決めてほしいこと」にまとめる）。`off`・`light`・文書だけ・ローカルレビューでは流さない（やり直しの review を呼ばない形のため）。
   - review の「報告に書くもの」（「たぶん」、「直したほうがよい」「確認だけ」、「前からある」問題。上の「混ぜるもの」を除く）は直させずに、報告の「コードレビュー」の節に並べる。「直った（意図的な挙動変更）」は直ったものとして扱い、何をなぜ意図的に変えたかを報告に書く。
   - マージの順にあるタスクは、下の「マージの順」の節も行う（review が済んだら、報告を書く前に `orca-flow rebase-review --done`）。
   - review が「未実施」とした観点があっても先に進む。報告の「コードレビュー」の節の観点ごとの件数に「未実施」と書き、「人間に決めてほしいこと」にも書く。人には、下の「統合の前に人が決めるもの」で聞く。
   - 統合の前に人が決めるもの：review の「判断事項」で本当だったもの（直しのやり直しの回数に数えず、最初に聞く）と、確認役の「必ず直すもの」と review の「直させるもの」（混ぜたものを除く）と文書だけの「タスク長が確かめるもの」の「必ず直す」で2回で直らなかったものと、2回目のやり直しと最後の review のあとの確かめで新しく出た「確か」の「必ず直す」と、`strict` で上限が尽きても残った「必ず直す」と、review が「未実施」とした観点は、報告を書く前に `orca-flow status question --note "統合の前に決めてほしいことがある"` にして、見出し・起きること・推奨と理由を人間に出して答えを待つ（integrate は手順3でマージするので、マージの前に止まれるのは、integrate-wait の前のこのタブだけ）。答え（直す・後続のタスクにする・このままにする）は、手順8の「人間に決めてほしいこと」の項目に（「直す」で直ったものを除く）「人が選んだこと」として書く。判断事項の答えは「このままにする」「戻す」「後続のタスクにする」で、「戻す」で直ったものも「直す」で直ったものと同じく除く。未実施の観点の答えは、「直す」の代わりに「流し直す」にする。「直す」と「流し直す」のあとは、次の2つの箇条のとおりにする。
   - 人が「直す」と選んだとき（2回で直らなかったもの）は、直しの指示（下の「統括役から知らせが来たら」）と同じに、直しのやり直しの回数と手順5の終了コード1の回数を0から数え直し、`orca-flow status working --note "担当が直している"` を流して担当に戻し、手順5からやり直す。担当に戻す前に〈直す前のコミット〉（`git rev-parse HEAD`）を覚え、直し終わったらすぐ、上の箇条と同じに取り込みより前に〈直し終わりの先頭〉を覚えて、review の範囲を `〈直す前のコミット〉..〈直し終わりの先頭〉` にする（差分が空なら直っていないとして数えるのも上と同じ）。review は、`full` ならやり直しの形で流し、「前の回の直させるもの」には人が「直す」を選んだもののうち review の直させるものだけを書き出す（確認役のものだけなら「なし」と書き出す）。そこに、「戻す」を選んだ判断事項を「戻した判断事項」の印をつけて足す（`判断事項：〈項目の名前〉` の印もそのまま保つ。「混ぜた」の印と同じ形）。review のやり直しは、「戻した判断事項」を新しい判断事項として「判断事項」の群に移さず、直っていなければ直させるものに残す（2回で直らなければ、もう一度 `orca-flow status question` で聞く）。`light`・`off` では review を呼ばない（確認役だけやり直す。`light` の「最初の1回」は数え直さない）。「戻した判断事項」は、文書だけ・`light`・`off` では、上の「戻した判断事項の確かめ」のとおりタスク長が確かめる（`reviewBackend` が `local` では、`full` も同じにタスク長が確かめる）。ここが、手順6のはじめから review を流す直しの指示との違い。また2回で直らなければ、もう一度 `orca-flow status question` で聞く（人が毎回決められる。手順5の3回目と同じ考え）。判断事項で「戻す」と選んだときも同じに担当に戻す（書き出しは上のとおり）。直ったものは、「直す」でも「戻す」でも、報告の「コードレビュー」の節の直したものに、人が「直す」か「戻す」を選んだと添えて書き、「人間に決めてほしいこと」には残さない。
   - 未実施の観点の答えは「流し直す」「後続のタスクにする」「このままにする」にする（見ていない観点は、担当に戻しても review が流れないため）。「流し直す」なら、最初の形の `/orca-flow:review $0 〈baseBranch〉...HEAD` をもう一度流し、出た直させるものは、ふだんの直しと同じに扱う。また未実施なら、もう一度聞く。
   - E2E の確かめ：設計書に `orca-flow e2e 〈ID〉` が通ることを完了条件に入れる旨があるときは、レビューの直しが済んだあと、報告を書く前に `${CLAUDE_PLUGIN_ROOT}/skills/run/e2e.md` を読んで、そのとおりに流す（テストを書く → `e2e` → 2なら `--wait` を背景で待つ → 落ちたらテストを直す。アプリの不具合やデータのなさは question で聞く）。結果は報告に書く。
   - 画面の記録：設計書に「画面の記録」の節があり、中身が「録らない」でなければ、レビューの直しが済んだあと、報告を書く前に `${CLAUDE_PLUGIN_ROOT}/skills/run/screen-capture.md` を読んで、そのとおりに録る。報告を書いたあとにコードを直したら、録り直す。「録らない」なら screen-capture.md を読まず、報告の「画面の記録」の節に理由を書く。
7. 共有のファイル（sharedPaths）の変更が要るときは、**自分で変えず、報告に書く**。それがないと先に進めないときは、`orca-flow status question --note "〈一言〉"` にして、人間に何が要るかを伝えて待つ。
   - 決定の記録の項（報告を書く前に行う）：decisionsFile が設定にあり、設計書に「決定の記録の文案」の節があり、その中身が「なし」でないときだけ、項を decisionsFile に足してコミットする。decisionsFile がない・節がない・中身が「なし」なら足さない。
     - decisionsFile が無視されていて追跡されていないとき（この worktree で `git check-ignore -q 〈decisionsFile〉` が成功する。追跡中のファイルは当たらず、今までの形）は、記録のファイルに書かず、コミットもしない。項（下の形、秘密と個人のパスの確かめは文面に対して同じ grep をかける）を報告の `## 決定の記録の項` の節に書く。integrate がその節をメインの記録の末尾に足す。節にコミットや verify のやり直しは要らない。以降の足す前の差分・コミット・取り込み後の比べは、無視されていないときの手順。
     - 足す前に `git diff 〈baseBranch〉...HEAD -- 〈decisionsFile〉` を見る。このタスクの項がすでにあれば（直しの指示などで手順をやり直したとき）、もう一度足さず、その項を直す（まだ統合していない自分の項は書き換えてよい。書き換えないのは、すでに統合された項）。
     - 項は、文案を写して次の形にする。見出しは「## 〈日付〉 〈見出し〉」（日付は今日、`date +%F`。見出しは文案の見出し）。そのあとに箇条書きで「決めたこと」「理由」「捨てた案と理由」「人が選んだこと」を書く。
     - 「人が選んだこと」は、文案に人が選んだことを足して書く：承認のとき人が直させた指示（設計書の「人が直した指示」）、統合の前に `status question` で聞いた答え（手順6の「人が選んだこと」）。承認で答えのなかった「決めてほしいこと」は、`orca-flow auto show $0` に「承認：」で始まる決めたことがあれば（承認がおまかせだった。承認のときに統括役が残す。今おまかせかどうかでは見分けない）「おすすめどおり（おまかせで統括役が決めた）」と書き、なければ「おすすめどおり（承認で決まった）」と書く（おまかせにしたことのないタスクでは `auto show` が終了コード1で「おまかせの記録はありません」を出す。これも失敗と読まず、「承認：」がないものとして扱う）。人に聞いて決まったものは、人の答えを書く。何もなければ「なし」。
     - 足すのは decisionsFile の末尾だけにして（前に空行を1行入れる）、すでに統合された項を書き換えない（追記だけのファイル）。ID（idPrefix と数字）・導入先の名前・手元のパス・秘密を書かない。過去の決めごとを指すときは、その項の「〈日付〉 〈見出し〉」を書き、設計書・報告のパスと ID は書かない。「設計書を見て」と書かず、読むだけで分かる文にする。
     - コミットの前に、`git add -- 〈decisionsFile〉` をしてから、review のスキルの「秘密と個人のパスの確かめ」のコマンドを、decisionsFile の差分に絞って流す：`git diff --no-color --cached -- 〈decisionsFile〉` の出力に、同じ grep をかける（足した項だけが当たる。add のあとに流すのは、main に decisionsFile がなく最初の項で新しく作るとき、追跡外のままだと差分が空になって素通りするため）。当たりが出たら（作り物の例とはっきり分かるものを除く）、項を直して `git add -- 〈decisionsFile〉` し直し、もう一度流して当たりがなくなってからコミットする。
     - `git add -- 〈decisionsFile〉 && git commit -m "$0: 決定の記録を足す" -- 〈decisionsFile〉` で decisionsFile だけをコミットする。このコミットで HEAD が動くので、手順10で verify をやり直す。追記だけのファイルだけのコミットなので、verify は記録を引き継いで軽く済む（全部のテストは流し直さない）。
     - main の取り込みのあと（手順5の verify の取り込みのあとも）、`git show 〈baseBranch〉:〈decisionsFile〉` の中身が、コミットした 〈decisionsFile〉（`git show HEAD:〈decisionsFile〉`。作業ツリーのファイルは改行が変わることがあるので比べない）の先頭とそのまま同じか（末尾に自分の項を足しただけか）を確かめる（比べ方は自分で決める。worktree に一時ファイルを作らない。例：`git show 〈baseBranch〉:〈decisionsFile〉 | cmp -n "$(git show 〈baseBranch〉:〈decisionsFile〉 | wc -c)" - <(git show HEAD:〈decisionsFile〉)`）。〈baseBranch〉 に 〈decisionsFile〉 がない（`git show` が失敗する）か空のときは確かめない（CLI と同じ。cmp の `-n 0` は上限なしになるので使わない）。差分では、union で消えた行は足した行にしか見えないので、差分では確かめない。`orca-flow verify` も取り込みのあと（しなかったときも）テストの前に同じ確かめをして止まる（終了コード1。文は「〈baseBranch〉 の 〈decisionsFile〉 が、タスクのブランチの 〈decisionsFile〉 の先頭と同じではありません」で始まる）。違えば（merge=union の取り込みで共通する行がまとめられて消えることがある）、〈baseBranch〉 の行を戻し、自分の項を末尾に足し直してコミットし直す。
8. `orca-flow status working --note "報告を書いている"` を流し、報告を `〈reportsDir〉/$0.md` に書く。設計書の「報告の形」に従い、少なくとも次を入れる：結果（完了・一部完了・未完了）、変更したファイル、実行したテストと結果、設計と違う判断、共有のファイルの変更の依頼、人間に決めてほしいこと、後回しにしたもの、画面の記録（設計書に「画面の記録」の節があるとき。同じ名前の節で、「録らない」ならその理由）、確かめていること、コードレビュー（観点ごとの件数（未実施の観点を含む）、直したもの、残った指摘を重さの順に。2回で直らなかったものと「前からある」問題には印をつける。文書だけとして軽く回したときは「文書だけとして軽く回した」と書き、直したものに「検証役なし・タスク長が確かめた」の印をつける。テストだけとして観点を絞ったときは「テストだけとして観点を絞った」と書き、見ない3つの観点は「テストだけで絞った」と書く（未実施にしない））。ローカルレビューのときは、指摘ごとの修正の背景（元の指摘、検証の根拠、何をなぜ直したか、意図的な挙動変更、残リスク、Opusの裁定）も書く。人間の言葉で書き、関数名や手順の番号は根拠に括弧で添える程度にする。節は次のように分ける。
   - 「仕様のページとの違い」：設計書の「報告の形」にこの節があるときだけ書く。依頼のファイル（`git rev-parse --path-format=absolute --git-common-dir` の下の `orca-flow/requests/$0.md`）にある項目の全文と、出来上がったものを比べる。1つの違いに、仕様のページの節と項目の名前・どう変わったか・なぜ（設計で人が直した・設計の判断・レビューの指摘など）を書く。違いがなければ「なし」と書く。設計の段で人が直した違いも入れる。Notion の URL とページの文を写さず、実装の言葉で書く（報告は公開に出ることがあるため）。
   - 大きさの確かめ（報告を書く前に行う）：`git diff --numstat 〈baseBranch〉...HEAD -- ':/' ':(top,exclude,icase)*.md'` の足した行と消した行の合計を「全体」とする（review の「小さな差分」と同じ数え方。拡張子 .md の行とバイナリは数えない）。そのうち review の「テストのファイルの見分け方」に当たるファイルの行をテスト、残りをコードとして控える。依頼のファイルに大きさの見込み（「コード 130〜200」のような幅は上の端）があれば、コードが見込みのコードの上の端と分け方の基準3の目安（約400行。`skills/intake/splitting.md`）の両方を超えたとき当たる。見込みがなければ、コードが約400行を超えたとき当たる。テストと全体の行では当てない（テストは同じ PR のまま、担当の定義の絞り方で重なりを消す）。当たらなければ「分ける案」の節は書かない。共通とアプリの組のタスク（`git rev-parse --path-format=absolute --git-common-dir` の下の `orca-flow/cross-depends/$0.json` の `repos[]` に `branch` がある、または `orca-flow/branch-push/$0.json` がある）は、組を分けないので、当たっても節を書かず、報告に「組のため分けない」と一言書く。
   - 「確かめていること」：人がまず読むテストの一覧。頭に大きさの1行（大きさの確かめで控えたコード・テスト・全体の行）を置く。続けて、振る舞い（人の言葉で1行）ごとに、確かめるテストのファイルと件数を並べる。並べるのは、このタスクで足したか直したテストだけ。今あるテストを変えたもの（消した・無効にした・期待を変えた）は「今あるテストを変えたもの」の小見出しで別に並べ（なければ「なし」）、何をなぜ変えたかを添える（確かめを弱めていないかを人が見るため）。push はこの節を PR の本文に写す。
   - 「分ける案」：大きさの確かめに当たったときだけ書く。切る所（書き込む場所のファイルの単位で、移す分と親に残る分）・各部の作るものと書き込む場所と行（コード・テスト・全体）・並べるか積むか（積むのは子が親の分を使うときだけ＝親を待つ。使わなければ並べる＝依存なし。理由も添える）。切り方は `skills/intake/splitting.md` の基準3・5・7に従い、前の枝の上に始める形は案にしない。人は、報告を読んで分けるなら、手順11の案内で統括役のタブの split を打つ。
   - 「共有のファイルの変更の依頼」：統括役が main で行う変更と、統括役への依頼。項目ごとに、何をどう変えるか、なぜ変えるか、推奨（「main で今変える」「変えない」のどちらか1つと、理由1つ）を書く。統合のとき、選ばれたら承認とみなして main で変える（push の道では、「main で今変える」が PR のマージのあとになる。push のあとの main で行う変更は、マージのあとにやることとして人間に伝わる）。大事な変更（`.claude/` の下（CLAUDE.md を除く）・`.orca-flow/` の下・`orca.yaml`・`package.json`（ファイル全体）・`.worktreeinclude`）は、統合のとき差分を見せてから入る。
   - 「人間に決めてほしいこと」：人が選ぶもの。なければ「なし」と書く。項目ごとに次を書く。
     - 見出し：何の話かを人間の言葉で1行。
     - 残った理由：判断事項・範囲の外・設計で範囲の外・前からある・2回で直らない・直しのあとに見つけた・確かめきれないから1つ。判断事項＝レビュー役が7項目のどれかの印（`判断事項：〈項目の名前〉`）をつけた。ほかの意味は、範囲の外＝直すには書き込んでよい場所の外を変える、設計で範囲の外＝直すと設計書の作るものを越える、前からある＝このタスクで入れた問題ではない、2回で直らない＝直しを2回やり直しても直らなかった、直しのあとに見つけた＝やり直しのレビューで新しく出た直したほうがよい、または2回目のやり直しと最後の review のあとの確かめで新しく出た「確か」の必ず直す、確かめきれない＝検証役が「たぶん」とした・未実施の観点・人が確かめる種類。
     - 起きること：人が出会う場面で1〜2文。なぜ困るかまで書く。
     - 根拠：ファイルと行・関数名・レビューの番号を括弧で短く（後続のタスクがここから元をたどる）。
     - 推奨：「後続のタスクにする」「このままにする」のどちらか1つと、理由1つ。
     - ほかの案：あれば1行。
     - 人が選んだこと：統合の前に `orca-flow status question` で聞いたものだけ。人の答えを書く。
   - 「後回しにしたもの」：設計で範囲外にしたもの、前からある問題で、今回は選ぶ必要のないもの。1項目1行で、何か・どこに書いてあるか。
   - コードレビューの「直したほうがよい」の残りは、件数があれば「人間に決めてほしいこと」に1項目にまとめて推奨をつける。まとめるときは理由ごとの件数を書く（例「直しのあとに見つけた3件・前からある1件」）。個々の指摘は「コードレビュー」の節に残す。混ぜて直したものは、「コードレビュー」の節の直したものに「直したほうがよい（混ぜた）」と印をつけて書き、「人間に決めてほしいこと」には残さない。「直しのあとに見つけた」の推奨はふだん「このままにする」にする（人が出会う場面で困るものだけ「後続のタスクにする」を推す）。
   - 統合の前に人が決めるもの（手順6の「統合の前に人が決めるもの」）は（「直す」で直ったものを除く）、「人間に決めてほしいこと」に「人が選んだこと」を添えて書く（「戻す」で直ったものも「直す」で直ったものと同じく書かない）。それ以外の統合の前に直すべきものは、タスク長が直す。
9. 先に、この worktree で `git check-ignore -q 〈reportsDir〉/$0.md` を流して、報告が無視されているかを確かめる（成功＝終了コード0なら無視されている。追跡中のファイルは当たらない）。無視されていればコミットしない（integrate がマージの前にメインの作業ツリーへ写す）。無視されていなければ、報告を `git add 〈reportsDir〉/$0.md && git commit -m "$0: 報告を書く"` でコミットする。`git add -f` は使わない（無視を破ると記録が公開に出る）。`git status --porcelain` で、未コミットの変更が残っていないことを確かめる。残っていれば、どの担当のものかを確かめて片づける。
10. 報告か決定の記録の項をコミットしたときは、そのコミットで HEAD が動き、手順5の記録が使えなくなるので、`orca-flow verify` をもう一度流す（コミットが決定の記録などの追記だけのファイルだけなら、verify が記録を引き継いで、そのファイルに当たる確かめだけで軽く済む。流すこと自体は変えない）。報告が無視されていてコミットせず、項も足さなかったときは、HEAD が動かず手順5の記録がそのまま使えるので、verify を流し直さない（片づけでコミットしたときだけ流し直す）。流すときの扱いは次のとおり（終了コードの扱いは手順5と同じ。落ちたら、直したあと報告も直してコミットし直す。コードを直したときは、報告を直してコミットし直す前に、手順6の「最後の review のあとの確かめ」を、その直しの分に流す。`strict` では、代わりに厳格モードの節のとおり最初の形を流し直す）。通ったら `git status --porcelain` が空かを確かめる。空でなければ、手順9と同じく、どの担当のものかを確かめて片づける。コミットせずに片づけた（消した・元に戻した）なら、HEAD が動かず verify の記録が使えるので、verify を流し直さず `git status --porcelain` だけ見直す。片づけでコミットしたときだけ `orca-flow verify` を流し直す。前に片づけたファイルがまた出たかは、`git status --porcelain --untracked-files=all` で見る（`git -c core.quotePath=false status --porcelain --untracked-files=all` として流し、日本語の名前を `"` で囲ませない。空白を含む名前はこれでも囲まれる。追跡外のフォルダも、中のファイルごとに出る）。手順9か手順10で前に片づけたファイルが verify のあとにまた出たら、テストが毎回作るものとみなす。`??` の行（追跡外のファイル）だけを、1つずつ `rm -- '〈パス〉'` で消して進み（フォルダごと消さない）、手順11の伝え方に「〈ファイル〉を `.gitignore` に足してほしい」と添える。パスが `"` で始まる（git が引用した特殊な名前）か `'` を含むとき、`??` 以外の行（追跡中のファイル）がまた出たとき、消してよいか分からないファイルのときは、元に戻さず、消さずに `orca-flow status question` にして人間に聞く。空なら `orca-flow status integrate-wait` を流す。
11. 報告の要点（結果・テスト）を5行くらいで伝える。決定の記録の項を足したときは、その見出しも伝える。手順10の `orca-flow status integrate-wait` の出力に「おまかせ」があれば、「このタスクはおまかせです。統合は統括役が進めます」と伝えて止まり、人間に `/orca-flow:integrate` を打たせない。「人間に決めてほしいこと」があれば、項目ごとに見出し・推奨に残った理由を添えて1行ずつ出す。「人が選んだこと」のある項目には人の答えを添える。「統合のとき統括役が選択肢で聞くので、今答えなくてよい」は、人が選んだことのない項目だけに言う（`taskEnd` が `"pr"` のときは「push のとき統括役が選択肢で聞くので、今答えなくてよい」と言う。push は手順5で integrate の手順4と同じに扱うため）。そのうえで、最後の案内を添えて**止まる**。案内は `orca-flow config --json` の `taskEnd` で分ける（おまかせの文は分けない）。
    - `"pr"`：「報告と差分を読んで、よければ統括役のタブで /orca-flow:push $0」と添える。
    - `"integrate"`（既定。ない・読めないときも）：「報告と差分を読んで、よければ統括役のタブで /orca-flow:integrate $0」と添える。
    - 報告に「分ける案」の節があるときは、上の案内にもう1行足す：「分けるなら統括役のタブで /orca-flow:split $0」。

## 厳格モード（codeReview: strict）

`codeReview` が `strict` のときの、手順6の回し方。時間をかけても、直すたびにまっさらな目で全部見直したいリポジトリの選択で、ふだんの `full` のやり直し（検証役1つ）とは別の形。`reviewBackend` が `local` なら `full` と同じにローカルレビューの節で回し、この節は使わない。文書だけ・テストだけにはならない（どちらも `full` のときだけ）。

- 回し方：最初の review は `full` と同じ最初の形（`/orca-flow:review $0 〈baseBranch〉...HEAD`。レビュー役・影響範囲・検証役）。直しが入るたびに（確認役の直しだけでも）、手順5をやり直して verify と確認役を流し、続けて最初の形の review を全部流し直す（やり直しの形は使わない。範囲はいつも `〈baseBranch〉...HEAD`）。次の「直すもの」（確かの必ず直すと確かの直したほうがよい）が出なくなったら終える。報告を書く前までに、最後の review のあとにコードを直したときも（手順10の verify が落ちた直しなど）、報告を直してコミットし直す前に、同じに流し直す（流し直しの上限の中で数える）。
- 直すもの：「確か」の「必ず直す」と、「確か」の「直したほうがよい」（「前からある」・書き込んでよい場所の外・設計で範囲の外を除く）。何回目の review で出ても直す。ふだんの「混ぜるもの」「2回目のやり直しで新しく出た必ず直す」「最後の review のあとの確かめ」は使わない（全部直して流し直すため）。判断事項・「たぶん」・「確認だけ」は、ふだんと同じに扱う（判断事項は確かめて「統合の前に人が決めるもの」へ、ほかは報告に書く）。直させるものは、直す前に根拠を開いて確かめる（手順6のとおり）。
- 上限：流し直しは `strictReviewRounds` 回まで（`orca-flow config --json` の値。最初の review は数えない）。尽きても直させるものが残ったら、「必ず直す」は直さず「統合の前に人が決めるもの」に入れて聞き（答えは「直す」「後続のタスクにする」「このままにする」）、「直したほうがよい」は直さず報告に「2回で直らない」で書く（strict では、この言葉は「直しの上限で直らない」の意味。直しのやり直しの2回の枠は使わない）。人が「直す」を選んだときは、直しの指示と同じに数え直して手順5からやり直す（流し直しの回数も0から数える）。
- 繰り返しを止める：2回目からの review では、Skill を流す直前に「確定済みの判断」として、前の回までに「誤り」で捨てたもの・残した確認だけ・判断事項（人の答えを含む）を本文に書き出す。レビュー役と検証役はこれを読み、新しい根拠なしに言い直さない。
- 戻した判断事項：人が「戻す」を選んだ判断事項は、流し直しの最初の形が「直ったか」を確かめないので、`light` のときと同じに、タスク長が根拠のファイルと行を開いて戻ったかを確かめる（戻っていなければ担当に戻し、回数は流し直しの上限と共有する）。
- 数え直し：統括役から直しの指示が来たときは、流し直しの回数も0から数え直す。

## 共通の枝を取り込むとき（枝で始めたタスク）

またぐ依存の記録 `〈git の共通ディレクトリ〉/orca-flow/cross-depends/$0.json`（`git rev-parse --path-format=absolute --git-common-dir` の下）の `repos[]` に `branch` があるアプリのタスクと、`orca-flow push $0 --branch` が使える共通のタスクのときだけ、この節を足す。記録がない・`branch` がなければ、この節は何もしない。記録が壊れていたら、直さず `orca-flow status question` にして人間に伝える。

- 取り込む（手順4の前。担当を起動する前）：`branch` のある要素ごとに、この worktree で記録の `branchCommand` をそのまま流し、パッケージの定義とロックファイルの差分だけを最初のコミットにする。担当の作業より先に済ませ、担当には、記録の `branch`・`branchCommand`・`bumpCommand` と、パッケージの定義とロックファイルを担当が触らないことを伝える。`branchCommand` は記録の文字をそのまま使い、自分で組み直さない。`branchCommand` が0以外で終わったら、パッケージの定義とロックファイルの変更を `git checkout -- 〈ファイル〉` で戻し（追跡外のものは、消してよいか分からなければ残す）、`orca-flow status question` で「共通の枝がまだ push されていない」ことを人間に伝えて待つ。`orca-flow verify` が「まだ push していません」「印がありません」の警告を出したときも、同じに人間に伝える。
- プレビューの立て直し：取り込む・取り込み直す・正式な版に戻すのコミットのあとに `orca-flow preview $0 --restart` を流す（起動の記録があれば立て直す。設定か記録がなければ何もせず終了コード0なので、設定を見ずに流す）。0以外で終わっても流れは止めず、理由を報告で人に伝えるだけ（プレビューは見るためのもので、タスクの進みに関わらない）。
- 共有のファイルの例外：手順7の「共有のファイルは自分で変えない」は、記録に `branch` のあるタスクの、この取り込みと戻しの差分には当てはまらない（タスクのブランチだけに置く。main には入れない）。範囲の確認（手順5）も、パッケージの定義とロックファイルの差分を範囲の外に数えない。
- 取り込み直す：手順5の `orca-flow verify` が「取り込み直す」を含む警告を出したら（共通の枝に、アプリのロックファイルにない push があった）、記録の `branchCommand` をもう一度流し、差分をコミットして、`orca-flow verify` を流し直す。警告は終了コードを変えないので、出たかを毎回標準エラーで確かめる。作業を終えたあとの取り込み直しは、見張りが `/orca-flow:bump $0` で起こして行う（`skills/bump/SKILL.md`）。
- 戻す：統合の前に、共通が入って正式な版が出たら、人間に版を聞く前に `orca-flow app-bump $0 --json` を流し、判定が「版を上げる」の要素の版を使う。記録の `bumpCommand` を記録の文字のまま流し（版を足して組み直さない）、作業ツリーのパッケージの定義とロックファイルで、枝の名前が残っていないことと、入った版が `app-bump` の版以上であることを確かめる（コミットの前は `app-bump` を流し直さない。`app-bump` はブランチの先頭を読む）。合わなければ戻して `orca-flow status question` にする。合えばコミットして `orca-flow verify` を流し直し、そのあとに `orca-flow app-bump $0 --json` を流し直してその共通が「済んだ」になったかを確かめる（ならなければコミットを消さず `orca-flow status question` にして人間に伝える）。「戻す」のあとは、枝の名前が消えるため、古い取り込みの警告は出なくなる。`orca-flow merge` が「を枝 〈枝〉 で取り込んだままです」を含む文で止まったときも同じ。版が出ないとき（判定が「待つ」か、`app-bump` が失敗したとき）だけ、人間に共通の版を聞き（`orca-flow status question` にして伝える）、その版で上げる。版は自分で決めない。ふつうは共通のタグが出たとき見張りが `/orca-flow:bump $0` で起こすので（`skills/bump/SKILL.md`）、起こされたときはその手順に従い、PR に上げた分は `/orca-flow:send` で承認される。
- 共通のタスクの枝の push：共通のタスク（`orca-flow new --allow-branch-push` で始めたもの）は、印があれば、最初の区切り（手順4の前。担当を起動する前）に1回 `orca-flow push $0 --branch` を流して、枝をリモートに作る（アプリが先に取り込めるようにするため。印がなければ流さない）。そのあと、`orca-flow verify` が通ったあとに直すたびに流す（承認も PR も要らない。送るのは自分のタスクの枝だけ）。印がなければ終了コード2になるので、流さず、PR の道（`/orca-flow:push $0`）のままにする。PR の道に入ったら、`--branch` は終了コード2になるので、もう流さない。`--branch` 以外の push や `git push` は流さない。

## 乗せたタスク（前のタスクの枝の上で始めたとき）

`orca-flow new --stack-on` で、作業中の前のタスク（乗せた先）の枝の上に始めたタスクのときだけ、この節を足す。乗せた先の統合を待たずに実装まで進め、統合とマージは乗せた先が先になる。

- 土台を読む：手順1で `orca-flow depends $0 --base` を流し、出た1行を〈土台〉とする。〈土台〉が baseBranch と同じなら、乗せていないか乗せた先がもう入っているので、この節の読み替えはしない。
- 読み替え：このスキルの「〈baseBranch〉」のうち、差分の範囲・取り込み・祖先の確かめは〈土台〉に読み替える（`〈baseBranch〉...HEAD`・`git merge 〈baseBranch〉`・`git merge-base --is-ancestor 〈baseBranch〉 HEAD`、分けた分を外す `git checkout 〈baseBranch〉 --`）。review と stage-verifier に渡す範囲も `〈土台〉...HEAD` にし、〈土台〉も渡す。追記だけの確かめは、`orca-flow verify` と同じに〈土台〉と比べる（手順7の、取り込みのあとに先頭がそのまま同じかを `cmp` で確かめる所も、`git show 〈土台〉:〈decisionsFile〉` で読む）。`.orca-flow/review.md` を読む所だけは baseBranch のまま。
- 読み直し：〈土台〉は乗せた先が入ると baseBranch に変わる。取り込みの前と review の前に `orca-flow depends $0 --base` を流し直す。
- 乗せた先がない：`orca-flow depends $0 --base` が終了コード2（乗せた先が作業中にも baseBranch にもない）なら、直さずに `orca-flow status question` にして、統括役のタブで `orca-flow depends $0 --unstack` が要ることを人間に伝えて待つ（タスクの worktree では流せない。統括役の場所でも、乗せた先がまだ作業中なら終了コード2で断る）。消したあと、この枝に乗せた先のコミットが残っていれば `--unstack` がその数を出すので、外すか、自分の変更として扱うかを決める（決めるのは人間。question のまま伝える）。依存の記録とマージの順は残るので、統括役が `orca-flow order --remove` と、merge の `--drop-depend` で外す（どちらも統括役のタブ。このスキルでは流さない）。
- 統合と push：乗せた先が入るまで、integrate と push は `--skip-order` でも止まる。報告を書いて integrate-wait にするのは今までどおりで、乗せた先が入るのを待つ。
- 知らせ（「統括役から知らせが来たら」に足す）：
  - 「前の枝が進んだ」を含む知らせ（乗せた先の verify が通った）：作業中は、担当が全員終わった区切りで、取り込みの前の `git rev-parse HEAD` を覚えて `git merge 〈土台〉` をし、`orca-flow rebase-review 〈覚えた HEAD〉` を流して「マージの順」の節のとおりに見直し、手順5（`orca-flow verify`）を流す。統合待ちは、`orca-flow status working --note "前の枝を取り込んでいる"` を流して同じに取り込み・見直し・verify をし、通って `git status --porcelain` が空なら `orca-flow status integrate-wait` に戻す。競合が直せなければ `orca-flow status question` にして人間に伝える。
  - 「前の設計書が出直した」を含む知らせ（乗せた先が spec-review になった）：乗せた先の設計書（`orca-flow active` に出る乗せた先の worktree の `〈tasksDir〉/〈乗せた先の ID〉.md`）を読み直し、このタスクの設計書と作業が前提にしたものが変わったかを確かめる。変わっていなければ何もしない。変わっていて、書き込んでよい場所の中で直せるなら直す（担当が動いていれば区切りで）。設計書の作るものや完了条件が変わるなら、直さずに `orca-flow status question` にして人間に伝える。
  - 「main に 〈ID〉 が入りました」（「main の確かめが通りました」を含むものも）：`orca-flow depends $0 --base` を流し直し、〈土台〉が baseBranch でない間だけ、次のとおりにする。乗せた先が入った知らせなら main を取り込み、ほかの ID が入った知らせなら取り込まない（作業中も統合待ちも何もしない。main の変更は乗せた先の枝を通して受け取る）。〈土台〉が baseBranch に戻ったら（乗せた先が入った知らせのときも、そのあとの知らせも）、上の「統括役から知らせが来たら」のとおりに扱う（順にあるタスクの統合待ちを含む）。

## ローカルレビュー（reviewBackend: local）

確認役（reviewerAgent）はこの節でも起動し、結果を待つ。コードレビューは `orca-flow review-local` と `orca-flow review-ledger` で回す。`codeReview` が `off` ならこの節は行わない。

### 共通の決まり

- 1周分は `orca-flow review-local $0 〈範囲〉 first|redo --stage 〈段〉 --cycle 〈周〉 --verify-result 〈verify の結果〉 --json` で流す。返る `mustFix` と `report` を使う。範囲は最初が `〈baseBranch〉...HEAD`、やり直しが `〈直す前のコミット〉..〈直し終わりの先頭〉`。
- やり直しの範囲：`redo` の範囲は、手順6と同じに求める。直す前に `git rev-parse HEAD` を覚え、直し終わったらすぐ、取り込みより前に `git rev-parse HEAD` で〈直し終わりの先頭〉を覚える（覚えたあとに増えた直しは、その直しが済んだ先頭に覚え直す）。範囲は `〈直す前のコミット〉..〈直し終わりの先頭〉` にする（`..HEAD` にしない。取り込んだ main の変更が入るため）。
- 直しの差分が空：直し終わったら `git diff --name-only 〈直す前のコミット〉..HEAD` を流し、空なら直っていないとして担当に戻す。`review-local` を流さず、その段を止める（担当に戻して直らないまま周を進めない。手順6と同じにやり直しの回数に数え、2回で直らなければ報告に書く）。
- `mustFix` が0件で `localReview.stopOnNoMustFix` が true なら、その段のローカルレビューを終える。やり直しの検証が `fixed_intentional` を返したら、意図的な挙動変更として台帳と報告に残す。
- `mustFix` を直すときは、その場所の担当に、指摘・検証の根拠・直し方の案・設計書・先に読む文書の絶対パスを渡す。修正メモ（指摘ID、変えたファイルと行（`src/foo.ts:12` か `src/foo.ts:12-20`）、何をなぜ変えたか、意図的な挙動変更か、テスト、残リスク、前の修正を戻す理由）を JSON にして、worktree の外の一時ファイルに書く。`orca-flow review-ledger record-fix --stage 〈段〉 --input 〈ファイル〉` で台帳に記録する。
- `record-fix` が終了コード1で「前の修正と重なる」と言ったら、担当に戻す前に `revertJustification` を修正メモに足す。足せないなら、その修正はせず、Opus検証か人間に回す。
- 修正のあと `orca-flow verify` を流す。終了コードの扱いは手順5と同じ。終了コード1のとき、時間切れ（「時間内に終わりませんでした」）は担当に戻さず、すぐ `orca-flow status question` にする。それ以外（「落ちました」）は、手順5と同じく落ちたコマンドごとに落ちた回数を通算で数える（間にほかのコマンドが落ちても、通っても数え直さない）。担当に戻すのは2回まで、3回目で `orca-flow status question` にする。これに加えて、同じテストで2回続けて落ちたら、その段を止めて人間に渡す。
- 同じ指紋の must-fix が `localReview.repeatLimit` 周続いたら、その段を止める。時間が `localReview.maxMinutes` を超えたら止める。修正が `maxFixLines` を超えたら、いったん止めて人間に渡す。
- 戻した判断事項の確かめ：人が「戻す」を選んだ判断事項は、`light`・`full` とも、タスク長が根拠のファイルと行を開いて、戻ったかを確かめる（ローカルのやり直しの検証は、人に回した指摘と段末の裁定が `needs_human` の指摘を確かめに入れず、段末の裁定は段の終わりにしか動かない。人の答えはそのあとに出るので、ほかに確かめる者がいない）。戻っていなければ担当に戻し、2回で戻らなければ、もう一度 `orca-flow status question` で聞く。戻すのが台帳にある指摘なら、修正メモを `record-fix` で記録し（`--stage` には、今の段でなく、その指摘が載っている台帳の段を渡す。指摘の ID は段ごとに振り直されるので、違う段に渡すと関係のない指摘が直ったことになる）、前の修正と重なると言われたら、`revertJustification` に人が「戻す」を選んだことを書く。直ったものは、報告の「コードレビュー」の節の直したものに、人が「戻す」を選んだことと「タスク長が確かめた」を添えて書く。
- ローカルが2回続けて失敗したら、`localReview.fallback` に従う。`claude-once` なら `/orca-flow:review $0 〈baseBranch〉...HEAD` を1回だけ流し、その結果で修正し、再レビューはしない。`human` なら `status question` にして人間に渡す。

### 終わったあと

ローカルレビュー（`light`・`full`）が終わったら、手順6の「画面の記録」の箇条のとおり（設計書に「画面の記録」の節があり「録らない」でなければ `${CLAUDE_PLUGIN_ROOT}/skills/run/screen-capture.md` を読んで録り、「録らない」なら報告に理由を書く）に画面の記録を通ってから、手順7へ進む。そのあとの手順8〜11は変わらない。報告のあとの手順9（片づけ）と手順10（`orca-flow verify` の流し直し）は、Claude のレビューと同じに行う。

### codeReview: light

1. `review-local ... first --stage 1 --cycle 1` を1回流す。
2. must-fix を担当に直させ、修正メモを台帳に記録し、`orca-flow verify` を流す。
3. 修正後の確認として `review-local ... redo --stage 1 --cycle 2` を1回だけ流す。
4. Opus検証はしない。追加の周回もしない。残った指摘、直した内容と意図、残リスクを報告に書く。

### codeReview: full

1段目は最大 `localReview.stageLimits[0]` 周（既定5）。`localReview.fullReviewAt` の周は `first`、それ以外は `redo`。must-fix がなくなったら早く終える。

1. 1段目の各周で、`review-local` を `first` か `redo` で流し、must-fix を直し、修正メモを台帳に記録し、`orca-flow verify` を流す。
2. 1段目が終わったら、`orca-flow:stage-verifier` を背景で起動する。渡すもの：ID、設計書、baseBranch、`git diff 〈baseBranch〉...HEAD`、台帳のパス、直近の verify の結果、`localReview.humanReviewCategories`、先に読む文書の絶対パス（review のスキルの手順2と同じにそろえたもの。なければ渡さない）。台帳は `orca-flow review-ledger show --stage 1 --json` で取れる。
3. stage-verifier の裁定を1件ずつ `orca-flow review-ledger record-opus --stage 1 --input 〈ファイル〉` で記録する。`must_fix` に `newEvidence` がなければ、その裁定は受け取らない。1回だけ stage-verifier に再裁定を頼み、それでもなければ人間に渡す。`newFindings` があれば、1件ずつ `orca-flow review-ledger record-finding --stage 1 --input 〈ファイル〉` で台帳に足す（`verdict` は付けない。stage-verifier が見つけた新しい指摘として `confirmed` で入る）。`humanReview` が true のものは担当に戻さず、報告の「人間に決めてほしいこと」に書く。その段の終わりに `status question` にする。人の答えが「戻す」なら、共通の決まりの「戻した判断事項の確かめ」のとおりにする。
4. `must_fix` がなければ、2段目は行わない。`needs_human` があれば `status question` にして人間に渡す（答えが「戻す」なら、共通の決まりの「戻した判断事項の確かめ」のとおりにする）。報告に、`accept_intentional`・`low_risk_ignore`・`needs_human` と理由を書く。
5. `must_fix` があれば担当に直させ、修正メモを記録し、`orca-flow verify` を流す。2段目は最大 `localReview.stageLimits[1]` 周（既定3）。各周で `review-local` を流し、1周目は `first`、2周目は `redo`、3周目は `first`。
6. 2段目のあと、`orca-flow:stage-verifier` をもう1回起動し、段2の台帳と先に読む文書の絶対パスを渡す（Opus検証は `localReview.opusChecks` 回まで）。`must_fix` が残ったら、追加のローカル周回はせず、`status question` にして人間に渡す。`accept_intentional`・`low_risk_ignore`・`needs_human` は理由とともに報告に書く。`needs_human` があれば `status question` にして人間に渡す（答えが「戻す」なら、共通の決まりの「戻した判断事項の確かめ」のとおりにする）。
7. 台帳（`〈git の共通ディレクトリ〉/orca-flow/reviews`）はコミットしない。報告の「コードレビュー」の節に、指摘ごとの結果、直した内容と意図、意図的に変えた挙動、見逃したリスクと理由を書く。人に選んでほしいことは「人間に決めてほしいこと」の節に書く。

## マージの順

統括役が `orca-flow order` で決めた鎖（重なる書き場所を持つタスクのマージの並び。例：T12 → T14 → T15）にいるタスクだけが行う。手順1の設定のあとで `orca-flow order --json` を流し、$0 が鎖に入っていなければ、この節は全部しない。同じ鎖で $0 より前にあるタスクを「前のタスク」と呼ぶ。integrate は、前のタスクが統合済みで、タスクの先頭がそのマージを含み、見直しの記録が今のタスク自身の変更（設計書・報告・appendOnlyFiles のファイル（決定の記録など）を除く差分の、足した行と消した行）と合っているときだけ通す。

- 報告を書く前：手順6の review と直しが済んだら、手順8の前に `orca-flow rebase-review --done` を流す（今のタスク自身の変更を見直し済みとして記録する）。報告のコミットや verify の取り込みで HEAD が動いても、決定の記録の項のコミットを見直しのあとに足しても、記録は使える（`--done` を流し直さなくてよい）。
- 鎖の見直し：手順8の前と、統括役から知らせを受けたときにも `orca-flow order --json` を流す。あとから鎖に入れられたなら、この節を行い、`--done` を流す。
- 取り込みのたび：どの取り込み（知らせ・統合待ちのもの）でも、取り込みの前に `git rev-parse HEAD` で先頭を覚え、取り込みと競合の解消のあとで `orca-flow rebase-review 〈覚えた HEAD〉` を流す。`orca-flow verify` は main を取り込むと自分で merge するので、verify の前にも HEAD を覚え、変わったら同じに流す。
- codeReview が `off`・`light`：見直しの review は何も確かめずに返す。終了コード1でも `--done` を流してから verify へ進む。
- 終了コード0：タスク自身の変更は変わっていない。見直しの記録が書かれたので、そのまま `orca-flow verify` へ進む。
- 終了コード1：出た「前にだけある行」「今にだけある行」を、review の見直しの形で検証役1つに確かめさせる。Skill を流す直前に、その出力をそのまま本文に書き出してから `/orca-flow:review $0 〈baseBranch〉...HEAD 見直し` を流す。直させるものが返ったら、直す前に根拠を開いて確かめ、やり直しと同じに担当に戻して直す（手順6の直しと同じ。回数は共有する）。直させるものがなくなったら `orca-flow rebase-review --done` を流し、そのあと `orca-flow verify` を流す。

## 順にないタスクの競合の手直し

マージの順の鎖にいないタスクでも、手順6の最初の review が済んだあとに、取り込みの競合を手で直したとき（手順5の終了コード3の取り込み、「main に 〈ID〉 が入りました」の取り込み、「競合を直し」の知らせ）は、誰のレビューも通らずに入らないよう、「マージの順」の節と同じ見直しを流す。最初の review の前の競合の手直しは、その review が見るので何もしない。

- 取り込みの前に `git rev-parse HEAD` で先頭を覚え、競合を直して終えたあとに `orca-flow rebase-review 〈覚えた HEAD〉` を流す（鎖の外でも流せる。見直しの記録は、鎖にいるタスクの integrate の確かめにだけ使われる）。
- codeReview が `off`・`light`：何も確かめずに返す。そのまま `orca-flow verify` へ進む。
- 終了コード0：タスク自身の変更は変わっていない。そのまま `orca-flow verify` へ進む。
- 終了コード1：「マージの順」の節の終了コード1と同じに、出力を本文に書き出して `/orca-flow:review $0 〈baseBranch〉...HEAD 見直し` を流し、直させるものを直す（回数は手順6の直しと共有する）。直させるものがなくなったら `orca-flow rebase-review --done` を流し、そのあと `orca-flow verify` を流す。

## 統括役から知らせが来たら

- 「main に 〈ID〉 が入りました」：
  - 作業中（担当が動いている間）：取り込まない。担当が全員終わった区切りで `git merge 〈baseBranch〉` をし、手順5（`orca-flow verify`）を流す。競合したら直して `git add` と `git commit --no-edit` で終える。直せなければ `orca-flow status question` にして人間に伝える。
  - 統合待ち（integrate-wait にしたあと）：始めに `orca-flow status working --note "テストを流し直している"` を流し（人間に流し直し中と見え、integrate を打たずに待てる）、`orca-flow verify` を流し直す。通ったら `git status --porcelain` が空かを確かめ、空なら `orca-flow status integrate-wait` に戻す（未読の印がもう一度つく）。
    - `orca-flow verify` の終了コードが0以外（1・2・3のどれでも）なら、直さずに `orca-flow status question` にして、終了コードと理由を人間に伝える（人間が報告を読んでいる最中のため。3でも自分で取り込まない）。
    - `git status --porcelain` が空でなければ、直さずに `orca-flow status question` にして、残っているファイルを人間に伝える。
- 「main に 〈ID〉 が入り、main の確かめが通りました」（「main の確かめが通りました」を含む知らせ。統括役の設定が after-merge のとき）：
  - 作業中（担当が動いている間）：上の「main に 〈ID〉 が入りました」の作業中と同じに、担当が全員終わった区切りで `git merge 〈baseBranch〉` をし、手順5（`orca-flow verify`）を流す。競合したら直して `git add` と `git commit --no-edit` で終える。直せなければ `orca-flow status question` にして人間に伝える。
  - 統合待ち（integrate-wait にしたあと）：何もしない。取り込みも `orca-flow verify` もしない（HEAD が動くと、integrate か push が使うテストの記録が使えなくなるため。main の確かめは統括役が済ませている）。
  - 「main の確かめが通りました」を含まない知らせは、上のとおりに扱う。
- 順にあるタスクの統合待ち（上の2つの知らせのどちらでも。`orca-flow order` で、入った ID が $0 の鎖の前のタスクかを見る）：前のタスクが入ったときの扱いは、設定の `integrateVerify` で分かれる（`orca-flow config --json`）。`after-merge`（既定）なら何もしない。取り込みも `orca-flow verify` もしない（integrate が自分で取り込む。次の知らせ「を取り込みました」を待つ）。`before-merge` なら今どおり取り込む：`orca-flow status working --note "前のタスクを取り込んでいる"` を流し、区切りを待たずに取り込みの前の `git rev-parse HEAD` を覚えて `git merge 〈baseBranch〉` をし、競合を直して `git add` と `git commit --no-edit` で終える（直せなければ `orca-flow status question` にして人間に伝える）。そのあと `orca-flow rebase-review 〈覚えた HEAD〉` を流して「マージの順」の節のとおりに見直し、`orca-flow verify` を流す。通って `git status --porcelain` が空なら `orca-flow status integrate-wait` に戻す。入ったのが前のタスクでなければ、上の知らせの扱いのままにする。
- 「〈ID〉 を取り込みました（取り込みの前の先頭 〈コミット〉）」（`orca-flow rebase-review 〈コミット〉` を含む知らせ。after-merge の integrate が、前のタスクを自分で取り込んだが、タスク自身の変更が変わって見直しが要るとき）：もう取り込まれているので、自分では取り込まない。始めに `orca-flow status working --note "取り込みの見直しをしている"` を流し、知らせに書かれた〈コミット〉（取り込みの前の先頭）で `orca-flow rebase-review 〈書かれた前の先頭〉` を流し、「マージの順」の節のとおりに見直す（終了コード1なら review の見直しの形で確かめ、直させるものを直して `orca-flow rebase-review --done`）。そのあと `orca-flow verify` を流し、通って `git status --porcelain` が空なら `orca-flow status integrate-wait` に戻す。終了コードが0以外、または未コミットが残るときは、直さずに `orca-flow status question` にして人間に伝える。
- 「〈ID〉 を取り込み、見直して verify をやり直し integrate-wait に戻して」（integrate が、タスクの先頭が統合済みの前のタスクを含まないと止めたとき）：integrateVerify にかかわらず（after-merge でも。integrate の取り込みが競合して取りやめたときと、差分のないタスクのときにも届く）、上の before-merge の手順と同じに自分で main を取り込み、見直しと verify をして戻る（after-merge の「何もしない」は当てはめない）。見直しを頼む知らせ（「取り込みの前のコミットを指定して orca-flow rebase-review を流し、変わった所を見直してから orca-flow rebase-review --done で記録し、integrate-wait に戻してください」。見直しの記録がない・今のタスク自身の変更と違う）も同じで、取り込みの前の先頭が分からなければ `git reflog` で探し、見つからなければ `/orca-flow:review $0 〈baseBranch〉...HEAD 見直し` に `git diff 〈baseBranch〉...HEAD` を渡して確かめ、`orca-flow rebase-review --done` を流してから verify する。
- 「git merge 〈baseBranch〉 をして競合を直し、orca-flow verify を流してから integrate-wait に戻して」（integrate が取り込みの競合で戻したとき）：取り込みの前に `git rev-parse HEAD` で先頭を覚え、`git merge 〈baseBranch〉` をして競合を直し、`git add` と `git commit --no-edit` で終える（直せなければ `orca-flow status question` にして人間に伝える）。そのあと `orca-flow rebase-review 〈覚えた HEAD〉` を流して見直す：鎖にいるタスクは「マージの順」の節、鎖にいないタスクは「順にないタスクの競合の手直し」の節のとおり。そのあと `orca-flow verify` を流し、通って `git status --porcelain` が空なら `orca-flow status integrate-wait` に戻す。
- 「〈baseBranch〉 の先頭を含んでいません」を含む知らせ（push が止めたとき。タスクのブランチが main の先頭を含まない）：上の「main に 〈ID〉 が入りました」の統合待ちと同じに扱う（`orca-flow verify` が main を取り込む。integrateVerify にかかわらず、after-merge の「何もしない」は当てはめない）。
- 「orca-flow verify をやり直して integrate-wait に戻して」（integrate か push が記録を使えずに戻したとき）：上の統合待ちと同じに扱う。
- 「〈子の ID〉 に分けました」（split が伝える。移す分と移した完了条件が続く。統合待ちのときに来る）：移す分を親の枝から外し、報告を直して、integrate-wait に戻す。
  - 始めに `orca-flow status working --note "分けた分を外している"` を流す。知らせの移す分の書き込む場所を、親の枝から外してコミットする（このタスクで足したファイルは `git rm`、変えたファイルは `git checkout 〈baseBranch〉 -- 〈パス〉` で戻す）。残る分は、移す分に頼らず動くようにする（つなぎ直しが要るときは、そのコードも同じコミットに入れる）。コミットは `git add 〈外したパス〉 && git commit -m "$0: 〈子の ID〉 に分けた分を外す"`。
  - 報告を直す：分けたこと（子の ID・並べるか積むか）と移した完了条件を書く。「分ける案」の節は「分けた」と書き換え、変更したファイルと実行したテストを、外したあとの形に直す。直してコミットする（無視されていればコミットしない。手順9と同じ）。
  - 確認役（reviewerAgent）を、親に残る分の差分で流し直す。起動するとき、知らせの移す分と移した完了条件を渡し、「子 〈子の ID〉 に移した。抜け・テストの削除として扱わない」と伝える。それでも移した分を指す「必ず直すもの」が出たら直さず、報告の「分けた」の節に添える。ほかの「必ず直すもの」は、ふつうの直しと同じに直す。
  - コードレビュー：外したコミットに `git rm` と `git checkout 〈baseBranch〉 --` 以外の変更（つなぎ直し）があれば、その分は手順6の「最後の review のあとの確かめ」と同じにやり直しの形の review を流す（codeReview が `full` のとき。`strict` なら「厳格モード」の節のとおり最初の形を流し直す）。外すだけならやり直さない（新しいコードがなく、この外しは「最後の review のあとの確かめ」にも数えない）。マージの順の鎖にいるタスクは、`orca-flow rebase-review --done` を流す（自身の変更が減ったため）。
  - `orca-flow verify` を流す（終了コードの扱いは手順5と同じ）。通って `git status --porcelain` が空なら `orca-flow status integrate-wait` に戻す。
- 直しの指示が来たら、担当に戻すか自分で直し、手順5〜11をやり直す。手順5の `orca-flow verify` が通ったあと（main を取り込んだあと）に codeReview を読み直す（`orca-flow config --json`。main の設定の変更を拾うため）。手順6の直しのやり直しの回数と、手順5の終了コード1の回数は、ここで数え直す（0回から）。`light` の「最初の1回」も数え直し、手順6で review を1回呼ぶ（`full` が手順6のはじめから review を流し直すのと合わせるため）。`strict` の流し直しの回数も数え直す。
  - 教訓を聞く：直しが、人が差分を読んで見つけた実装の誤りの直しのときだけ行う。好みや仕様の変更の直しは対象外。直しが手順6（確認とレビュー）を通ったあと・手順8（報告）の前に、`orca-flow status question --note "教訓を足すか決めてほしい"` にして、教訓の案をタブで見せ、「足す」「直して足す」「足さない」を1回だけ聞く。テストとレビューを通る前だと直しの形が変わって教訓と食い違い、統合待ちのあとだと人が報告を読む最中に割り込むため。
  - 案は、見出し・決まり・理由・見分け方・観点の形にし、誤りの実装を写さず一般化する。ID（idPrefix と数字）と手元のパスを書かない。`orca-flow lessons` で読んだ教訓に似た項があれば、まとめ直した1項を案にして、下の順で元の項を消してまとめ直す。
  - 「足す」「直して足す」なら、案を、`mktemp -d` で作った一時ディレクトリ（worktree の外）の中に Write ツールで書き（シェルのヒアドキュメントや echo で書かない）、`orca-flow lessons add 〈ファイル〉` で足す。足したあと（足さずに止めるときも）一時ディレクトリを消す。足したら報告に「足した教訓：〈見出し〉」と書き、まとめ直しなら下の「まとめ直す順」で元の項を消してから手順8へ進む。200行を越えた警告が出たら、似た項のまとめ直しや、テストになった項の削除の案を人に示す。
  - まとめ直す順：まとめた項を、上の `orca-flow lessons add 〈ファイル〉` で先に足し（add は1回だけ）、終了コード0を確かめてから、元の項を消す。add が断られたら消さない（終了コードが0でなければ1つも消さず、断られた理由を人に伝える）。消す前に `orca-flow lessons` を読み直して今の番号を取り（人の答えを待つ間にほかの作業の削除で番号がずれるため）、`orca-flow lessons remove 〈番号〉 --heading 〈見出し〉` で1項ずつ消す。1つ消すたびに読み直して番号を取り直す。見出しの違いで終了コード1になったら、読み直して1回だけやり直し、それでも落ちたら消さずに人に伝える。
  - テストか lint で見つけられる誤りなら、同じ質問で「テストにする後続のタスクを作るか」も聞く。「作る」なら、統括役のタブで打つ1行を人に示し、報告の「後回しにしたもの」に書く（統合を使わない PR の道でも人が作れるため）。1行は、lint にできる誤り（名前・呼び出し・import など、コードの形で分かるもの）なら `/orca-flow:to-lint 〈教訓の見出しか誤りの説明〉`、動かして分かる誤りなら `/orca-flow:new [--auto] 〈やりたいこと〉` にする（人に示すときは角かっこを外し、やりたいことを具体的な文にして、おまかせにするときだけ頭に `--auto` をつける。`--auto` は頭に置く。末尾に置くとやりたいことの文に混ざる）。
