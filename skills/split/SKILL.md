argument-hint: "[ID]"

あなたは統括役として、タスク $0（以下、親）の大きくなった PR を、人が選んで子のタスクに分ける。分けるのは、親の報告に run が書いた「分ける案」があるときだけ。分けた分は、子の ID の新しいタスクにする（push の記録・見張り・後始末・`merged` が「1つの ID に PR 1つ」で作られているため、同じ ID のまま PR を積まない）。このスキルは push も PR の作成もしない。

CLI は `orca-flow` で呼ぶ（プラグインの bin が PATH に入っている）。見つからなければ `"${CLAUDE_PLUGIN_ROOT}/bin/orca-flow"` で呼ぶ。終了コードは 0＝成功、1＝確認に落ちた・失敗、2＝人間か統括役の作業が先に要る、3＝git の競合。

ブランチを切り替えない。親の worktree のファイルを書き換えない（外す手直しは、親のタスク長に `orca-flow tell` で頼む）。

## 人に聞くとき

人の答え（選ぶ・許す・自由な言葉）で次の手が分かれる所は、本文に説明を書いてから、Claude Code の質問の画面（AskUserQuestion）で聞く。

- 当たる所：人の答えで次の手が分かれる所。答えを求めず、人か統括役の作業を頼んで知らせを待つ所（`orca-flow tell` を待つ所や見張りの起こしを待つ所）は、今までどおり文で伝える。開いた画面では Orca が入力欄を読めず、統括役の知らせと見張りの起こしが届かないため、知らせを待つ所は文のままにする。
- 形：本文に説明を書いてから AskUserQuestion を出す。説明（見出し・起きること・根拠・推奨と理由）を画面の中に詰めない。推奨の選択肢を先頭にして「（Recommended）」をつける。
- 数：1回に4問まで、1問に選択肢4つまで。4問を超えるときは、手順が聞く順に4問ずつ分け、答えが返ってから次を出す。
- 選択肢になじまない問い（許可・自由な答え）は、「許す」「許さない」などの短い選択肢で出し、自由な答えは「その他」で受ける。
- カード：タスク長は、今までどおり先に `orca-flow status question --note "〈一言〉"` を流してから聞く。答えのあとの扱い（status を戻す・引き継ぎに書く・vote を流すなど）は、各手順のとおりにする。
- 聞くのは、いつもこの会話の本人。背景の担当とレビュー役は画面を出せないので、聞きたいことはタスク長に返す。
- このスキルで当たる所：手順4の分けるか、手順4の並べ方、手順9の続けるか片付けるか。

## 手順

1. `orca-flow config --json` で設定を読む（baseBranch・reportsDir・idPrefix・tasksDir・progress）。`orca-flow active` で $0 のブランチ・worktree・カードを調べる。`git rev-parse --path-format=absolute --git-common-dir` を〈共通〉と呼ぶ。
2. 止まる所を確かめる。1つでも当たれば、何も作らず、理由を人間に伝えて止まる。
   - 報告に「分ける案」の節がない：`${CLAUDE_PLUGIN_ROOT}/skills/integrate/SKILL.md` の手順2と同じに報告を読む。節がなければ、run が大きさを確かめて案を書いたものだけを分けるので、止まる。
   - カードが統合待ちでない：`orca-flow active` の $0 の「カード：」が `in-review` でない（作業中・設計中・質問中）、または一言が「統合待ち」で始まらない（統合待ちのあとの質問中も `in-review` のままなので、一言も見る）。タスク長が報告を書いて統合待ちにしてから分ける。
   - 親の push の記録に PR がある：`〈共通〉/orca-flow/push/$0.json` があり、`pr` が null でない。PR を送ったあとは、PR とブランチが分かれてしまうので分けない。
   - 組のタスク：`〈共通〉/orca-flow/cross-depends/$0.json` の `repos[]` に `branch` があるか、`〈共通〉/orca-flow/branch-push/$0.json`（共通の枝の印）がある。組は、どちらの形でも枝の名前と版上げがそろわないので今回は分けない。記録が壊れていて読めないときも止まる。
3. 子の ID を決める。親の ID の後ろに、使われていない英字を a から1つ足す（例：T12 の子は T12a、T12a が使われていれば T12b）。使われているかは、`orca-flow active`、進捗表（progress.file）、`git branch --list 'task/〈ID〉*'`、`〈共通〉/orca-flow/requests/〈ID〉.md`、`git for-each-ref refs/orca-flow/split/` で確かめる。slug は、移す分の中身から短い英語（小文字・数字・ハイフンだけ、3語くらいまで）で決める。
4. 報告の「分ける案」を人間に示して聞く。本文に、切る所・移す分（作るもの・書き込む場所・行）・親に残る分・並べるか積むか（理由つき）を書いてから、AskUserQuestion で次を聞く。
   - 分けるか：「分ける（Recommended）」「分けない」。分けないなら、何も作らず止まる。
   - 並べ方：報告の案を推奨の選択肢にして「（Recommended）」をつける。選択肢は「並べる」（子が親の分を使わない。依存なしで始める）と「積む」（子が親の分を使う。親を待つ）。
5. 後続を先に調べる：`orca-flow depends --on $0` で、$0 を依存に持つ作業中のタスクを控える（手順9で子を足す相手。子は、まだ始めていないのでこの一覧に出ない）。終了コードが0以外なら（関係ないタスクの記録が1つ壊れていても1になる）、何も作らず、メッセージを人間に伝えて止まる。
6. 親の枝の今の先頭に参照を付ける：`git update-ref refs/orca-flow/split/〈子の ID〉 〈親のブランチの先頭〉`（先頭は `git rev-parse refs/heads/〈親のブランチ〉`）。子のコードはここから取り出す。親の後始末で枝が消えても、参照は残る。
7. 親の依頼のファイルに仕様のページの URL があるときだけ、先に `${CLAUDE_PLUGIN_ROOT}/skills/split/spec-page.md` を読み、その「子のページを作る」のとおりに、子のタスクのページを作る（依頼のファイルの「仕様」の URL を、親でなく子のページにするため。統合の戻しが子のページを見つけられる）。「仕様のページを見つける」で次へ進めないとき（前の形のページを含む）や子のページを作れないときは、子のページを作らず、子の依頼のファイルから「仕様」の URL を除く（直す中身は会話で人に渡す）。
8. 子の依頼のファイルを書く。`mktemp -d` で一時ディレクトリを作り、`${CLAUDE_PLUGIN_ROOT}/skills/new/SKILL.md` の手順5と同じに、中身を Write ツールで書く（シェルのヒアドキュメントや echo で書かない）。書くもの：
   - 親の依頼（`〈共通〉/orca-flow/requests/$0.md` の全文の写し。Notion の URL と中身を公開に出るファイルに書かない、の1行も残す）。
   - 移す分：報告の「分ける案」から、移す作るもの・書き込む場所・完了条件。手順7で子のページに写した QA 項目（あれば。人の直しのまま文で写す）。手順7で子のページを作ったときは、子に効く QA 項目はこれだけ（上の親の依頼の写しにある QA 項目と「QA の筋書き：」は親のもので、子の完了条件の候補にしない）。子のページを作らなかったときは、この限りを書かない（親の依頼の写しの QA 項目が、前と同じに子の完了条件の候補になる）。
   - 取り出し方：子の worktree で、`git diff 〈baseBranch〉...refs/orca-flow/split/〈子の ID〉 -- 〈移す書き込む場所〉`（3点。親の変更だけが出る）で中身を読み、`git diff --binary 〈baseBranch〉...refs/orca-flow/split/〈子の ID〉 -- 〈パス〉 | git apply --3way` で親の変更だけを当てて取り出す（`--binary` がないと、バイナリのファイルが1つあるだけで全部が当たらない）（`git checkout 〈参照〉 -- 〈パス〉` はファイル全体を親の時点で上書きし、参照のあとに main に入った変更を消すので使わない）。当たらなければ（競合）手で直す。
   - 並べ方：並べる（親を待たない）か積む（親を待つ）か。積むときは「親が baseBranch に入ってから run する」と書く。
9. 子を始める：`orca-flow new --title '〈タスク名〉' --slug 〈slug〉 --id 〈子の ID〉 --request-file 〈一時ファイル〉 --read-first-from $0` を流す（タスク名は一重引用符で囲み、中の ' は '\'' にする）。`--read-first-from $0` はいつも付ける（new が親の先に読む文書の記録を子に写し、子のタスク長とレビュー役に届く。親に記録がなくても付けてよい。そのときは子の記録を作らない）。親の記録が壊れていると、new は Orca を呼ばず worktree も作らずに終了コード1で止まる（下の「new が落ちたとき」の、worktree ができていない場合として片付ける）。依頼のファイルの「## 先に読む文書」の節から読む文書を決めて渡す道はとらない。`--depends 〈親の ID〉` は、積むときだけ足す。並べるときは足さない。終了コードの扱いと、終わったあとに一時ディレクトリを消すことは、`${CLAUDE_PLUGIN_ROOT}/skills/new/SKILL.md` の手順5・6と同じ。new が落ちたら（`maxActiveTasks` の上限の終了コード2など）、続けるとき以外は手順10以降に進まない。続けるか片付けるかは、下の「new が落ちたとき」で決める。
   - 成功したら、手順5で控えた後続ごとに `orca-flow depends 〈後続〉 --add 〈子の ID〉` を流す（後続は親と全部の子を待つ）。終了コードが0以外なら、メッセージを人間に伝え、足せなかった後続を知らせる。
   - new が落ちたとき：まず `git worktree list` と `orca-flow active` で、子の worktree とタスクが残っているかを見る。new のメッセージの「/orca-flow:new を流す」は、「/orca-flow:split 〈親〉 を流し直す（同じ子の ID になる）」に読み替える（new は split から呼ばれたことを知らない）。
     - 子の worktree ができていなければ、または `orca-flow active` に子が出ない（ブランチ名の直しで落ちた・worktree が消えた）：続けられないので、聞かずに片付ける（下の「片付ける」）。
     - `orca-flow active` に子が出る（子のタスク長がもう動いている）：本文に、new が終えなかったこと（進捗表の行など）と、続けるか片付けるかで起きることを書いてから、AskUserQuestion で「続ける（Recommended）」「片付けてやり直す」を聞く。推奨は続ける（タスク長が動いていて、欠けたのは進捗表の行などだけのため）。
     - 続ける：子が参照から取り出すので、参照を消さずに残す。new が終えなかったこと（進捗表の行など）を人間に伝え、手順9の成功のあとの `depends --add` と、手順10・11・12を流す。
     - 片付ける：子のタスク長が動いていれば、人間に Orca で止めてもらい、止めた知らせを文で待つ（答えを求める所ではないので、画面では聞かない）。そのあと、new のメッセージに片付けのコマンドがあればそれを、なければ、子の worktree と子のブランチのうち残っているものだけを消す（`git worktree list` と `git branch --list` で見る。何も作られていなければ流さない）。続けて `git update-ref -d refs/orca-flow/split/〈子の ID〉` と、`〈共通〉/orca-flow/requests/〈子の ID〉.md` の削除を流す（依頼のファイルは new が worktree を作る前に書くので、消さないと使われた ID と数えられる）。終わりに、手順3と同じ確かめで子の ID がどれにも出ないことを確かめる。残っていれば（進捗表の行など）、残ったものを人間に伝えて止まる。
     - 片付けたとき、手順7で子のページを作っていれば、その URL を人間に伝え、消すか、やり直しで使い回すかを任せる。片付けたあとは、メッセージを人間に伝えて止まる。
10. 手順7で子のページを作ったときだけ、`spec-page.md` の「親のページを直す」のとおりに、親のページを直す。URL がなければ飛ばす。
11. 親のタスク長に伝える：`orca-flow tell $0 '〈子の ID〉 に分けました。移す分：〈書き込む場所〉。移した完了条件：〈条件〉'`（引用符の中の ' は '\'' にする）。親のタスク長が、移す分を親の枝から外して報告を直す。`orca-flow tell` が終了コード2で落ちたとき（見つからない・1つに決まらない・打ちかけ・bash モード・入力欄を確かめられない）は、CLI が出した送れなかった文と候補のタブを人間に伝え、親のタブで伝えてもらう（子はもう始まっているので止めて消さない）。
12. 人間に伝える：子の ID とブランチ、並べるか積むか、後続に足した依存、仕様のページを直したか（人に渡した分があればその中身）。親が分けた分を外して統合待ちに戻るまで、親を統合しない。子は設計から始まる。積む子は、親が baseBranch に入ってから run される。
