# 仕様のページの形

intake の手順6で下書きを書くときと、手順8の子ページを作るときに読む。仕様のページを、全体を見る親のページ1つと、タスクごとのページに分ける。親で全体と順を読み、タスクのページでそのタスクの中身を読む。人が読んで判断しやすいことと、AI がもれなく読むことは別の目的なので、各ページの上は人の言葉、下（細部）は ADR の中身にする。

前の形（ステップと組の形、1ページの形、土台のページと単位のページ、上の所のない古い形）の読み方は `${CLAUDE_PLUGIN_ROOT}/skills/intake/page-format-prev.md` に移した。今ある前の形のページを読むときだけそちらを読み、書き換えない。新しく作るページはこの文書に従う。

## ページの置き方

- チケットの「自動で追記」の節の下に、親のページを1つ作る。親の子ページとして、項目ごとのタスクのページを作る（項目はリポジトリごとに1つ。ブランチの中の1リポジトリが1項目）。
- ブランチ（同じ ID と短い名前で始めるリポジトリのまとまり）が1つで項目が1つでも、親とタスクのページの2枚にする（形を1通りにして、読み戻しを分けないため）。
- 見分けの印の行は、親にもタスクのページにも入れる。

## 親のページの並び

上から次の順に置く。「何が変わるか」から「出典」までの見出しの名前はこのとおりにする。1・2（印の行・読み方の行）は見出しのない地の文で置く。

1. 見分けの印の行
2. 読み方の行
3. 何が変わるか
4. 分け方
5. ブランチ
6. 同時に作るタスクの間で使い合うもの（単位が2つ以上で契約があるときだけ）
7. 決めてほしいこと
8. 区切りの線と、細部（AI 向け）
9. 出典（統合が足す「実装で変わったこと」「実装後の画面」は、タスクのページの出典の後ろに足される）

## タスクのページの並び

上から次の順に置く。

1. 見分けの印の行
2. つながりの行
3. 要点
4. 決めてほしいこと
5. QA 項目
6. 区切りの線と、細部（AI 向け）
7. 出典（統合が足す「実装で変わったこと」「実装後の画面」は、その後ろに足される）

- タスクのページには、状態も ID も書かない（「状態と ID」のとおり）。

## 見分けの印の行

- 本文の先頭に、地の文の一行で置く。書くのは印「要件から自動で作った仕様のページ」。
- 前の印「orca-flow の intake が作った仕様のページ」も印とみなす。前の印を書き換えない。
- Notion に書く文には orca-flow の語を入れない。親にもタスクのページにも効く。例は架空の要件にする。

## 読み方の行

- 親のページの印の次に1行だけ置く。質問は選ぶものにチェックを入れること、直すのは各ページの上の所だけでよく細部は自動で合わせること、開始済みのタスクには直しが届かないことを書く。
- 例：

> 質問は、選ぶものにチェックを入れてください。直すのは各ページの上の所だけでよく、下の細部は自動で合わせます。「開始済み」のタスクには、ここを直しても届きません。

## 何が変わるか

- 使う人から見て何が変わるか、なぜやるかを、数行で書く。
- 関数の名前やコードの行は書かない。人の言葉で書き、初めて出る言葉はその場で短く説明する。
- ブランチが2つ以上あるときは、「ブランチ」（同じ ID と短い名前で、いっしょに始めるリポジトリのまとまり）の短い説明を、ページで最初に出る所（ふつうはここ）に1回だけ書く。共通を含むブランチがあるときは、「共通を含むブランチ」（共通とアプリをいっしょに進める）の説明も同じ所に1回だけ書く。ほかの所では説明を繰り返さない。

## 分け方

- なぜこの粒度で分けたかを、数行で書く（分け方の基準は `splitting.md`）。
- 単位が2つ以上のときも、「単位」の言葉は出さない。ブランチの間の待ちは「待つもの」の行と図で見せる。
- ワークスペースの道だけ、読んだが項目にしなかったリポジトリを1行ずつ足す。見出しは足さない。
  - 読んだが変えない：「〈リポジトリ〉は読んだが変えない：〈理由〉」
  - 読めなかった：「〈リポジトリ〉は読めなかった：〈理由〉」

## ブランチ

- 待つものの順にブランチを番号（1から通し）で並べる。
- ブランチ1つに、太字の行「ブランチ〈番号〉 〈slug〉」と、概要の2〜3文、「待つもの：… ／ 出す順：…」の行、項目の行を置く。ブランチは見出しにしない（Notion の見出しは3段までのため）。一覧は表にせず、段落と箇条書きにする。
  - slug：ブランチの全部の項目が同じ slug で始まる（1ブランチ1つ）。`new --slug` に渡す前に `guards.md` の形の確かめにかける。
  - 待つもの：「ブランチ〈番号〉」か「なし」。待つ先は、ブランチの番号で書く（項目やリポジトリの番号では書かない）。2つ以上なら読点で並べる。ワークスペースの道でも同じ（`〈名前〉:〈ID〉` は項目の状態の行にだけ出る）。
  - 出す順：ブランチのリポジトリが2つ以上のときだけ、同じ行に「出す順：」を足す。1リポジトリのブランチには置かない。共通を含むブランチは、「共通の PR をマージ → 共通の版を出す（人が行う）→ 見張りがアプリのタスク長を起こして正式な版に上げる → アプリの PR をマージ」の順を、リポジトリの名前で書く（人が行う段の末尾に「（人が行う）」を付ける）。共通のないブランチは「順なし」と書く（PR のマージの順がない、という意味。共通のないブランチの項目は互いに独立したアプリで、ブランチの中のマージの順を決める元も効かせる仕組みもないため。消せないマージの順が要るときだけブランチを分け、下の「入れる順：」で表す。本番に出す順と人の手順は、下の「出すときの手順：」に書く）。E2E の項目を足したブランチは、共通がなくても「順なし」にせず、E2E の項目をアプリより後の段に置き、「アプリの PR をマージ → E2E の PR をマージ」のように E2E の PR のマージを最後に書く。
  - 出すときの手順：どのブランチにも置ける（リポジトリが1つでも、共通のないブランチでも）。本番に出す順と人が行う手順（データの投入、機能を ON にする、など）を、人の言葉で、番号つきで書く。人が行う段の末尾に「（人が行う）」を付ける。手順がなければ行ごと置かない。「出す順：」は PR のマージの順なので、同じことを両方に書かない。「待つもの」の行の下に、行「出すときの手順：」と番号つきの箇条書きで置く。
  - 項目の行：ブランチの中の1リポジトリが1行（箇条書き）。「〈リポジトリ〉：〈項目名〉（タスクのページへのリンク） ／ 大きさ：… ／ 状態：」の形にする。1ブランチの中は1リポジトリ1項目（同じリポジトリで同じブランチ名は2つ作れないため）。リポジトリはワークスペースの道だけに書き、書くのはワークスペースの名前だけ（道は書かない）。1つのリポジトリの道では、リポジトリを書かない。
  - 大きさ：小・中・大のどれか。コード・テスト・全体の行の内訳はタスクのページの要点に書く。目安（`splitting.md` の基準3）を超える項目には「目安超え」を添える。
  - 状態：始める前は空。始めたら「開始済み 〈ID〉」と書く（「状態と ID」のとおり）。
  - QA の筋書き：項目が2つ以上のブランチだけに、項目の行の下に行「QA の筋書き：」を置き、項目をまたいで確かめる一続きの動きを、1行1項目のチェックボックスで書く（形はタスクのページの「QA 項目」と同じ）。1つの項目だけで確かめられることは、そのタスクのページの QA 項目に書き、ここに写さない。項目が1つのブランチには置かない（タスクのページの QA 項目と重なるため）。反映と打ち直しで書き換えない（「QA 項目」と同じ）。
- E2E を足さないブランチ（ワークスペースの道。設定の `companion` の `apps` のアプリがあるのに、条件に当たらず E2E の項目を足さなかったとき）には、そのブランチの行（概要の下）に1行「〈リポジトリ〉は変えない：〈理由〉」を足す。〈リポジトリ〉は設定の名前、〈理由〉は how の答えから画面の動きが変わらない旨を一言で書く。コマンドの印のアプリがそのブランチにないことは、E2E の項目を足さない理由にも、この1行の理由にもしない（ブランチにないアプリは、E2E を流すときに依存元のタスクか baseBranch の版の画面で埋める）。状態の行ではないので、反映で書き換えない。
- 入れる順があるブランチには、「入れる順：ブランチ〈番号〉のあと」の行を足す。値は、契約で並べて作る、待つものでつながっていないブランチの間にだけ書く。待つものでつながる間は「待つもの」で書く（`splitting.md` の「契約で並べて入れる順を決める」）。入れる順は「待つもの」には書かない（`merged` にも渡さない）。始めてよいかは `guards.md` のとおり。
- 例：

> **ブランチ1 notify-base**
> 通知の送り先を設定できるようにする。送り先の保存と読み出しだけで、送信はまだしない。
> 待つもの：なし
> 出すときの手順：
>
> 1. アプリAを本番に出す
> 2. 通知の設定の初期値を入れる（人が行う）
>
> - アプリA：通知の下地（タスクのページへのリンク） ／ 大きさ：小 ／ 状態：
>
> **ブランチ2 notify-send**
> 設定した送り先に知らせが届くようにする。共通のパッケージの処理を使う。
> 待つもの：ブランチ1 ／ 出す順：共通のパッケージの PR をマージ → 共通の版を出す（人が行う）→ 見張りがアプリのタスク長を起こして正式な版に上げる → アプリAの PR をマージ
>
> - 共通のパッケージ：送る処理（タスクのページへのリンク） ／ 大きさ：中 ／ 状態：
> - アプリA：送る処理の呼び出し（タスクのページへのリンク） ／ 大きさ：小 ／ 状態：
>
> QA の筋書き：
>
> - [ ] 必須：アプリAで送り先にメールを設定し、知らせを送る操作をする → 設定したメールに知らせが1通だけ届く

## 並びと図

- ブランチは、待つものの順に番号を振る。待たないブランチを先にし、ほかは、待つ先のブランチの番号より後にする。番号はブランチの順に、親全体で1から通しで振る。タスクのページの番号も、この通しの番号と同じにする。
- ブランチが2つ以上のときだけ、「ブランチ」の節の頭に Mermaid の図を1つ置く。ブランチが1つなら図は置かない（待ちは「待つもの」の行にもあり、図が3か所目の書き場所になるため）。
  - 箱はブランチ（番号・slug・リポジトリ。共通を含むブランチは「共通」と印をつける）、矢印は待つもの（待つ先から待つブランチへ引く）。
  - 箱の文字は、`guards.md` の形の確かめを通した slug と、設定のリポジトリの名前だけから作る。人が直せる文字（ブランチの概要や項目名）は図に入れない。Mermaid の文として壊れないよう、文字は引用符で囲む。
  - 図は人が直さない。反映のたびに、ブランチの「待つもの」から作り直す。人が図を直しても、反映で上書きし、待つものに合わせる。
- 例：

> ```mermaid
> flowchart TD
>   B1["ブランチ1 notify-base<br>アプリA"]
>   B2["ブランチ2 notify-send<br>共通（共通のパッケージ）・アプリA"]
>   B1 --> B2
> ```

## 要点

タスクのページの要点。

- 何をするか（人の言葉）と、大きさの内訳を書く。関数の名前やコードの行は書かない。
- 大きさの内訳は「中（コード 130〜200・テスト 100〜180・全体 230〜380）」の形で、コード・テスト・全体の行を書く。移すだけの行があれば「移すだけ 約〈行〉」を添える。目安（`splitting.md` の基準3）を超えるタスクには「目安超え」を添える。
- 内訳の中身の形は、手順10と反映で確かめない。親の「大きさ：」は小・中・大だけでよい。「小」「中」だけの形も、そのまま読み、書き換えない。
- 例：

> 大きさ：中（コード 130〜200・テスト 100〜180・全体 230〜380）

## 同時に作るタスクの間で使い合うもの

- 分け方で単位が2つ以上になり、単位の間に契約があるときだけ置く。なければ節を置かない。
- 中身は契約（名前・形・呼び方）。使う側は契約どおりの偽物で試す。
- 「単位」は分け方を決める内部の言葉で、Notion のページには出さない。入れる順は、ブランチの「入れる順：ブランチ〈番号〉のあと」の行で見せる。

## 決めてほしいこと

- 質問ごとに1つの吹き出し（コールアウト）に入れる。質問がなければ「なし」とだけ書く。
- 吹き出しには、問い・いつまでに要るか・効く所（どのブランチか）・おすすめと理由1つ・選択肢のチェックボックス・「答え・補足：」の行を書く。おすすめの選択肢には印をつける。
- 選択肢のチェックボックスの下に、「これからも同じにする（後の要件にも効かせる）」のチェックボックスを1つ足す。このチェックは選択肢と分けて置き、答えのチェックの数に数えない。
- 親のページには、2つ以上のブランチに効く質問を置く。1つの項目だけに効く質問は、その項目のタスクのページに置く。
- 質問の番号は、ページごとに1から振る。細部から指すときは、同じページの質問は「決めてほしいこと〈番号〉」、親の質問は「親の決めてほしいこと〈番号〉」と書く。
- タスクのページの質問が親の質問と関わるときは、タスクのページに「親のページの質問〈番号〉もこのタスクに効く」の1行を置き、質問の文は写さない。
- 決めてほしいことは上の所に置き、ページの末尾に別に足さない。
- 例：

> 問い：通知の送り先は、メールだけにしますか。
> いつまでに要るか：最初のタスクを始める前
> 効く所：ブランチ2
> おすすめ：メールだけ（理由：送り先を足すのは後からでも小さな変更で済む）
>
> - [ ] メールだけ（おすすめ）
> - [ ] メールとチャット
>
> - [ ] これからも同じにする（後の要件にも効かせる）
>
> 答え・補足：

## QA 項目

タスクのページの QA 項目。そのタスクを QA で確かめる項目を、決めてほしいことのあと、区切りの線の前に置く。親のページには置かない（項目をまたぐ確かめは、親の「ブランチ」の「QA の筋書き：」に置く）。

- 1行1項目のチェックボックスで、「必須：〈操作〉 → 〈期待する結果〉」か「できれば：〈操作〉 → 〈期待する結果〉」の形で書く。必須を先に並べ、できればを後に並べる。
- 期待する結果が見た目（そろい方・見やすさ・色・間隔など、画面の文字・値・出る出ないでは決まらないもの）の項目は、「必須（目で見る）：〈操作〉 → 〈期待する結果〉」か「できれば（目で見る）：〈操作〉 → 〈期待する結果〉」の形にする（AI が判定せず、前と後の画面を並べて人が見る項目の印）。人は印を足す・消して分け方を直してよい。印のない「必須：」「できれば：」の今の形もそのまま読み、そのときは AI が期待する結果から分ける。
- 項目は、変更の場所ごとに変わる動きから洗い出す（洗い出し方と重要度の付け方は `guards.md` の手順6）。数の目安を置かない。要る分だけ書き、変わらない動きは並べない。確かめる動きがなければ「なし」とだけ書く。
- 操作と期待する結果は人の言葉で書き、関数の名前やコードの行は書かない。期待する結果は、要件と、前からある動き・同じ製品のほかの画面とのそろい方で決める。
- AI が書くのは最初の下書きだけ。人は項目を足す・直す・消してよい。反映と打ち直しでは書き換えない（合わなくなった項目は見直しの候補として示すだけ。`guards.md` の手順10）。
- チェックボックスは QA で確かめた印で、質問の答えに数えない（「決めてほしいこと」の選択肢のチェックとは別）。
- 例：

> - [ ] 必須：通知の設定で送り先のメールを入れて保存する → 開き直しても同じメールが出る
> - [ ] 必須：送り先に「@」のないメールを入れて保存する → 欄の下に形の誤りが出て、保存されない
> - [ ] 必須：設定を変える権限のない人で通知の設定を開く → 保存のボタンが出ない
> - [ ] できれば：スマートフォンの幅で通知の設定を開く → 欄とボタンが画面からはみ出さない
> - [ ] できれば（目で見る）：通知の設定を開く → 欄とボタンの並びが、ほかの設定の画面とそろって見える

## 細部（AI 向け）

- 各ページの上の所と区切りの線で分け、見出し「細部（AI 向け）」を置く。
- 親の細部：全体の状況、分け方の捨てた案（単位が2つ以上なら、単位の分け方も）、2つ以上のブランチに効く決定と結果を置く。リポジトリが2つ以上のブランチの決定は、見出しに「ブランチ1（slug：〈slug〉）」と書いて置き、これをブランチの slug の正とする。単位ごとの決定は、見出しで単位の名前を添える。
- タスクのページの細部：そのタスクの状況・決定・結果・捨てた案と、タスクの中身（`splitting.md` の「1項目に書くこと」の1項目。リポジトリが2つ以上のブランチの項目は、親のブランチごとの決定と同じ slug も書く）を置く。親の細部の決定が効くときは「親の細部の〈見出し〉が効く」と書き、写さない。
- 中身は、ADR の4つの節（状況・決定・結果・捨てた案）と、タスクへの分け方。今の決まり（`guards.md` の手順6）の中身を置く。
- 節ごとに折りたたみ（トグル）にする。
- 質問を指すときは、質問の文は写さない。同じページの質問は「決めてほしいこと〈番号〉」、親の質問は「親の決めてほしいこと〈番号〉」と書く。
- リポジトリが2つ以上のブランチは、親の細部のブランチごとの決定の見出しに「ブランチ1（slug：〈slug〉）」と書き、親の太字の行「ブランチ1 〈slug〉」と細部の slug をつなぐ。タスクのページの1項目にも同じ slug を書く。食い違えば、細部を正とし、直さず人に聞く。

## 出典

- 読んだイシューとチケットの出典を、最後に置く。親にもタスクのページにも置く。
- 統合が足す「実装で変わったこと」「実装後の画面」は、タスクのページの出典の後ろに足される。

## 状態と ID

- 状態と ID は、親のブランチの項目の行の「状態：」だけに書く（「開始済み 〈ID〉」。ワークスペースの道では「開始済み 〈名前〉:〈ID〉」）。
- 書く場所は、太字の行「ブランチ〈番号〉 〈slug〉」と項目のリポジトリで選ぶ（1ブランチの中は1リポジトリ1項目なので、ブランチの番号とリポジトリで1つに決まる。1つのリポジトリの道では、ブランチの番号だけで決まる）。状態の行の文だけで選ばない（同じ文になりやすいため）。
- タスクのページには、状態も ID も書かない。細部の見出しの横にも書かない（2か所に書くとずれるため）。
- 「項目の横」の ID は、この親の状態の行を指す。
- 書いたあとの読み直しは `${CLAUDE_PLUGIN_ROOT}/skills/intake/guards.md` の「手順10：始める前の守り」の「new が通るたびに」の項のとおり。

## 依存の書き方と解き方

- 依存は「待つもの：ブランチ〈番号〉」で書く。
- 始めるとき、「ブランチ〈番号〉」を、親のそのブランチの全部の項目の状態の行の ID に解く。全部の項目に ID があり、全部が `merged` で入ったときだけ、そのブランチを入ったとし、待つ項目を印なしで始める。入っていない待つ先があれば、前を待つ印をつけて始める（`guards.md` の手順10）。解いた ID を、今の ID の形の確かめと `merged` にかける。1つでも状態の行にまだ ID がなければ、入っていないとして始めない。
- 解いた ID のうち、`new --depends` に渡すのは、始める項目と同じリポジトリの ID だけ。ほかのリポジトリの ID は渡さない（ほかのリポジトリの待つ先は前を待つ印で待つので、ほかのリポジトリの ID を `--cross-depends` に渡すと、共通にアプリへのまたぐ依存が付いて止まるため。`--cross-depends` は同じブランチの共通とアプリの間だけ）。
- 入れる順の行も、親の状態の行から前のブランチの開始済みを読む。

## 親に1回だけ置くもの

- 2つ以上のブランチに効くもの（質問・決定・結果）は、親に1回だけ置く。タスクのページは指すだけにして、写さない（写すと答えがずれるため）。
- 同じブランチの2つ以上の項目に効くものも、これに当たる。
- 1つの項目だけに効くものは、その項目のタスクのページに置く。

## 依頼のファイルに写すもの

- 依頼のファイルに写す「仕様」の URL は、そのタスクのページの URL にする（親の URL は写さない）。
- 親の質問と答え、親の細部のうちそのタスクに効く決定と結果、同時に作るタスクの間で使い合うもの、入れる順、そのブランチの「出すときの手順：」（あれば）は、文で写す。

## 形の見分け

- 新しい形（ブランチの形）の親のページは、見出し「ブランチ」と見出し「何が変わるか」があるもので見分ける。
- 新しい形のタスクのページは、「親のページ：」で始まるつながりの行に「このページはブランチ〈番号〉」があるもので見分ける。
- つながりの行は、1つのリポジトリの道では「親のページ：〈リンク〉 ／ このページはブランチ〈番号〉」、ワークスペースの道では「親のページ：〈リンク〉 ／ このページはブランチ〈番号〉の〈リポジトリ〉」にする。
- 渡された URL がタスクのページなら、つながりの行のリンクから親をたどり、親と同じに扱う（親の全部の項目を、待つ先が前になる順に始めるため。始める範囲は `guards.md` のとおり）。
- 親をたどったら、始める前に確かめる：たどった親に見分けの印と見出し「何が変わるか」と見出し「ブランチ」があり、親とタスクのページが互いを指すこと（親のブランチ〈番号〉のそのリポジトリの項目の行のリンクがそのタスクのページで、タスクのページのつながりの行がその親を指し、番号とリポジトリが同じ）。外れたら、どの new も流さず止まり、渡された URL・たどった親の URL・外れた点を人に示す（ページを複製して別のチケットの下に置くと、つながりの行が元の親を指したまま残るため）。
- URL はページの ID で比べる。ページの ID は URL の末尾の16進の32文字（ハイフンは除く）で、URL の頭や名前の部分は比べない（道具や貼り方で変わるため）。
- ID を取る前に、URL の `?` と `#` から後ろを除く。残ったパスの末尾の16進の32文字（ハイフンは除く）をページの ID とする（人が貼った URL には問い合わせの部分や `#` がつきやすく、そのままだと正しい親でも別の ID と読んで止まるため）。
- ステップと組の形（見出し「タスク」があり、見出し「ブランチ」がない親。つながりの行が「このページはタスク〈番号〉」のタスクのページ）は、前の形として `page-format-prev.md` で読み、書き換えない。「親のページ：」で始まるつながりの行も、見出し「何が変わるか」もない、それより前の形も同じ（前の形の単位のページ（「つながり：」の行がある）も前の形に当たる）。この3つ（新しい形・ステップと組の形・それより前の形）は、見出しとつながりの行だけで分け、混ぜて読まない。ステップと組の形にも、上の親のたどり方とたどった親の確かめ（互いを指すか）を、ブランチをタスクに、見出し「ブランチ」を見出し「タスク」に読み替えて同じに効かせる（`guards.md` の手順10と `page-format-prev.md` の「ステップと組の形」のとおり）。

## 統合の戻し

- 依頼のファイルの「仕様」の URL のタスクのページの印を確かめ、つながりの行から親を読む。親のそのブランチのそのリポジトリの項目の状態の行にこの ID があるときだけ戻す。
- 直すのはタスクのページ。親は、そのブランチの概要だけを直してよい。ただしブランチの項目が1つのときだけ（項目が2つ以上のブランチの概要は、ほかのリポジトリの項目にも関わるので直さず人に渡す）。状態の行は変えない。親の細部・質問・図や、ほかのタスクのページに届く違いは直さず、「戻せなかったとき」と同じく会話で人に渡す。
- 画面の記録も同じ見分けで、タスクのページの末尾に足す。
- 前の形のページ（ステップと組の形を含む）は、`page-format-prev.md` の見分けで今までどおり戻す。

## 質問のチェックの読み方

- 質問のチェック・「これからも」・補足の読み方は、前の形と同じ（`guards.md` の手順10のとおり）。

## 作れないときの代わり

- 道具が吹き出し・チェックボックス・折りたたみを作れないときは、同じ並びを見出しと箇条書きで書く。子ページを作れず下書きを人に示すときも同じ。
- チェックの代わりに「答え：」の行にする。「これからも同じにする」のチェックの代わりは、「これからも：」の行（「同じにする」か空）にする。この行も答えの数に数えない。
- 状態は、親のブランチの項目の行の「状態：開始済み 〈ID〉」で書く（項目の行は箇条書きのままでよい）。
- QA 項目と「QA の筋書き：」のチェックボックスが作れないときは、同じ「必須：〈操作〉 → 〈期待する結果〉」の行を箇条書きにする。この箇条書きも質問の答えに数えない。
- 図は、Mermaid の図が作れなければ、ブランチの待ちを「ブランチ2 ← ブランチ1」の箇条書きで示す。この箇条書きも人が直さず、反映で待つものから作り直す。
- 子ページを作れないときは、親とタスクのページの全文を、親が先、タスクのページがブランチの番号の順（同じブランチの中は項目の順）で人に示し、親の下にタスクのページを置くよう頼む。人が貼った親の URL とタスクのページの URL をもらってから進む。もらった親の URL を、各タスクのページのつながりの行に「親のページ：〈リンク〉」として書き足し（書けなければ人に頼み）、各タスクのページを読み直して、つながりの行が親を指していることを確かめる。
- 子ページを作れないときは、もらった各タスクのページの URL を、親のそのブランチの項目の行にリンクとして書き足し（書けなければ人に頼み）、親を読み直して、互いを指すことを確かめる。
