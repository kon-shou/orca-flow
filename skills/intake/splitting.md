# 分け方の基準

intake が要件をタスクに分けるときに読み、新しいレビュー役にも渡す。分けた1項目が、orca-flow のタスク1つ（1つのブランチ）になる。

根拠は、Google の Small CLs（https://google.github.io/eng-practices/review/developer/small-cls.html）。小さい変更が、レビューの速さと質、戻しやすさにつながる、という考え方を使う。数字は目安であり、原典の文は写さない。

## 基準

1. 既定は1つ。分けてよいのは、次の「ブランチの単位」の節の4つの場合だけ。項目に、どの場合に当たるかと「なぜ分けたか」を書く。理由が書けなければ分けない。2〜6は、その場合の細かい決まり。
2. 種類：振る舞いを変えない整理（リファクタ）は、先の別の項目にする。整理と機能が1つの差分に混ざると、人も AI も、どこが動きの変わる所かを見分けにくい。テストは、振る舞いを変える項目と同じ項目に入れる。ただし、テストの共通の部品（準備・偽物・表の形）を作るのは振る舞いを変えない整理なので、先の項目にしてよい。本体の動きの確かめは、本体の項目に残す。これは「ブランチの単位」の整理の場合に当たる。
3. 大きさ：人と AI のレビューが一度に読める大きさを超えそうなら分ける。目安は、テストを除く差分（コード）で約400行、触るモジュールは2〜3つ。超えたら必ず分ける。これは「ブランチの単位」の目安を超える場合に当たる。
   - どちらかの目安（コードで約400行、またはモジュール2〜3つ）を超える項目は、理由を書いても大きいまま残さない。残してよいのは、ファイルを移すだけの変更（移すだけ）と、自動で作るファイルだけ。
   - 分けるときは、リポジトリや層で切らず、QA の筋書き（1回の QA で確かめる一続きの動き）で切る。2つ以上の筋書きが使う部分は、下地のブランチに置く。下地のブランチは複数のリポジトリを含んでよい。共通（共有のリポジトリ）の下地は、今までどおり（基準8）使うアプリと同じブランチにまとめる。
   - 分けた案は、元の要件（目安を超える見込みだったもの）をどの項目に分けたかを書く。どこで切るか・増える待ちや版の回数を添える。
   - テストの行は分ける理由にしない。テストを含む全体の行が大きくても、コードとモジュールの数が目安に収まれば分けない（分けても、各部分がテストで大きいままになる）。テストは本体と同じ項目のまま、PR の大きさに関わらず、担当の定義（`agents/task-worker.md` の手順5）のテストの絞り方で、重なりを消して書く。
   - 見込みが幅（例：130〜200）のときは、上の端で目安と比べる。
   - 数え方はレビューの「小さな差分」と同じにする（`skills/review/SKILL.md`。しきい値の数はそこだけに書き、ここには写さない）。行は足す行と消す行の合計で、拡張子が .md のファイルの行は数えない。テストの行は、レビューの「テストのファイルの見分け方」に当たるファイルの行。コードの行は残りの行。全体はその2つを足したもの。ファイルを動かすだけの行は全体に足さず、「移すだけ 約〈行〉」と別に添える。
   - レビューとの関係：PR 全体が「小さな差分」のしきい値までなら、レビュー役は1つで済む。超えれば、観点ごとに分けた5つの見込みになる。分け方を決めるときに、この違いも見込みに入れる。
   - 新しいレビュー役は、移すだけ・自動で作るファイルの行を除いて目安を超える項目が下書きに残っていれば指摘し、分けた案を求める。分けた案があるかを見る（案を添えただけで大きいまま残した項目は通さない）。
4. 切る向き：縦（機能ごとに、入口から出口まで通す）を先に考える。横（層ごと）に切るのは、共有の型やインタフェースを先の項目で入れ、あとの項目が並べられるときだけ。
5. main を毎回動く形にする。フラグで閉じて先に入れるか、積む（前の項目の統合を待つ）か、乗せる（下）かは、項目ごとに選び、理由を書く。決め打ちしない。
   - 選ぶ目安：未完成のまま入れたいならフラグ。後ろを早く始めたいなら、フラグか乗せる。前のコードがそろえば完成し、待ちが短いなら積む。
   - フラグの仕組みは、導入先のものを探して使う。なければ、作る項目を先に立てるか、積むほうにするかを、同じく選ぶ。
   - 乗せる：後ろが前の項目のコードを使い、2つが同じリポジトリにあるときは、前の項目のブランチの上に後ろを始めてよい（`orca-flow new --stack-on`）。前が入るのを待たずに、後ろを実装まで進められる。後ろは前の統合のあとにしか入らないので、main に入る順と中身は積むときと同じになる。そのため、フラグで閉じていない要件でも乗せてよい。リポジトリをまたぐ依存には乗せない（前の枝を取り込めないため）。乗せる先は1つだけ。乗せるときも理由を書く。
6. 互換を壊す変更は、「新しいものを足す→呼び手を移す→古いものを消す」の3つに分ける。3つを別のブランチにするのは、3つの間に消せないマージの順があるとき（呼び手がほかのリポジトリにある、など。「ブランチの単位」のマージの順の待ちに当たる）だけ。それ以外は、1つの差分（1つのブランチ）の中で足す→移す→消すにする（「順はまずコードの書き方で消す」）。
7. 依存：分け目をモジュールの公開の境界に置き、依存を一方向にして輪を作らない。「積む」は前の項目の統合を待つこと、「並べる」は依存がなく同時に進められること、「乗せる」は前の項目の枝の上で後ろを始め、統合は前のあとにすること（基準5）。
8. 共通とアプリ：ワークスペースの道で共通とアプリを両方変える要件は、分ける単位を共通を含むブランチ（共通とアプリの項目を同じブランチ名で始めるまとまり）にする。PR を分けるときもブランチごとに分け、共通だけの項目を先に分けて出さない（共通だけが先に入ると、使う側のないままの変更が出回る）。

## ブランチの単位

- ブランチは QA の単位。1回の QA で確かめる筋書きに入る項目は、互いに独立していても同じブランチに入れる。リポジトリが違えば PR は別になるので、独立していることは、ブランチを分ける理由にしない。
- ブランチを分けてよいのは、次の4つの場合だけ。
  - マージの順の待ち：マージの順の待ちがあり、下の「順はまずコードの書き方で消す」で消せないとき。
  - 時期をずらす：出す時期や QA の時期を、わざとずらしたいとき。
  - 目安を超える：基準3の目安を超えるとき。
  - 整理：振る舞いを変えない整理（リファクタ）。基準2のとおり、機能と別のブランチにする。
- 順番は、次の3種類に分けて考える。
  - マージの順：CI と開発環境に効く。
  - 本番に出す順：デプロイの順。
  - 人の手順：データの投入、機能を ON にする、など。
  - ブランチの待ちで守るのは、消せないマージの順だけ。本番に出す順と人の手順は、ブランチの中の「出すときの手順」に書く（`page-format.md`）。
- 順はまずコードの書き方で消す。古いものと新しいものが並んでも動く書き方にできれば、順の縛りはなくなる。たとえば、機能が閉じている間は新しい形を読み書きしない（基準5のフラグ）、新しいものを足す→呼び手を移す→古いものを消す（基準6）。これで消せないマージの順だけが、ブランチの待ちになる。

## 独立の単位

独立していることは、ブランチを分ける理由にしない（上の「ブランチの単位」）。ここでの単位は、4つの場合で分けたあとに、ブランチの間の依存を消すための考え方として読む。

「ブランチの単位」の4つの場合で分けると決めたら、そのあと単位を決め、単位の中のタスクに分ける。単位は、ほかの単位を待たずに作って入れられるタスクのまとまり。単位どうしは依存を持たない。待つのは下地のタスクだけで、積む（前の項目の統合を待つ）のは単位の中だけにする。単位をまたいで積まない。

単位どうしの依存は、次の4つの道を、上から順に当てて消す。上の道で消せるなら、下の道は使わない。

- 並べる：書く場所だけが重なる（同じファイルの別の所・登録の行）なら、別の単位にして並べて作る。入れる順は overlap が自動で足す（今の仕組み）。
- 契約で並べて入れる順を決める：使うコードがほかの単位にあるなら、契約（名前・形・呼び方）を親のページの「同時に作るタスクの間で使い合うもの」に書き、両方を並べて作り、入れる順を決める。使う側は契約どおりの偽物で試す。
- 下地：多くの単位が同じ下地（共有の型・ファイルの分け目・登録の口）を要るなら、下地を小さなタスクにして、待つものがないブランチに置く。単位はその統合だけを待つ。
- まとめる：それでも切れないなら、1つの単位にまとめる。単位の中では積んでよい。

- 既定は1つのまま。分ける理由がなければ、1単位1タスクにする。単位が1つでも、仕様のページは親のページとタスクごとのページ（タスクが1つなら2枚）にする。「単位」は分け方を決める内部の言葉で、Notion のページには出さない。親のページでは、ブランチを待つものの順に並べ、待ちを図で見せる（`page-format.md`）。
- 共通を含むブランチは1つの単位の中に置き、単位をまたがせない（上の基準の8）。共通のないブランチも、リポジトリが2つ以上なら同じ ID と slug でそろえて始める。
- 入れる順は1本の列に並べる（扇形・合流・3段になっても、関わる項目を、前が後より前になる1本の並びにして決める。CLI は、すでにある鎖の一部だけを含む並びを断るため。流し方は `guards.md` の手順10のとおり）。
- 単位が2つ以上のときは、単位ごとに名前（「単位1」「単位2」…）・入るタスク・待つもの（下地のタスク〈番号〉か、なし）・入れる順を示す。

## 1項目に書くこと

タスク名・slug（小文字・数字・ハイフンだけ、3語くらいまで）・作るもの・種類（機能・整理・足す・移す・消す、など）・なぜ分けたか・依存と積むか並べるか（積むなら理由）・閉じ方（フラグか、そのまま入れるか）・見込みの大きさ（コード・テスト・全体の行とモジュールの数。移すだけの行は「移すだけ 約〈行〉」と別に添える）・見込みの根拠（コードを読んで分けたときは、読んだ場所と追い切れなかった点。読んでいない場所には「推し量り」と添える。pstack か how の SKILL.md がなく読めなかったときは「pstack なし（要件から推し量った）」、how が落ちて終わらなかったときは「how が使えなかった（要件から推し量った）」）・書き込みそうな場所・同じブランチの項目（同じ ID と slug で始める、ほかのリポジトリの項目。なければ「なし」。ブランチの中では1つのリポジトリの項目は1つにする）・入れる順（「ブランチ〈番号〉のあと」。なければ「なし」）。1項目には単位の名前を書かない（親の細部の見出しに単位の名前を添えるのは `page-format.md` のとおり）。
