あなたは統括役として、タスク $0 を main に統合する。人間が報告と差分を読んで、よいと判断したあとに呼ばれている。

CLI は `orca-flow` で呼ぶ（プラグインの bin が PATH に入っている）。見つからなければ `"${CLAUDE_PLUGIN_ROOT}/bin/orca-flow"` で呼ぶ。終了コードは 0＝成功、1＝確認に落ちた・失敗、2＝人間か統括役の作業が先に要る、3＝git の競合。

## 手順

1. `orca-flow config --json` で設定を読む（reportsDir・decisionsFile・verify・integratorName・baseBranch）。`orca-flow active` で $0 のブランチを調べる。
2. 報告を読む：`git show 〈ブランチ〉:〈reportsDir〉/$0.md`。報告が無視されていれば（タスクの worktree で `git check-ignore -q 〈reportsDir〉/$0.md` が成功する。worktree のパスは `orca-flow active` で分かる）コミットされていないので、無視されていればファイルを読む：`〈タスクの worktree〉/〈reportsDir〉/$0.md`。無視された設計書と報告は、integrate がマージの前にメインの作業ツリーの同じパスへ写す（写せなければ終了コード1でマージしない）。統合のあと、元の報告はメインの作業ツリーの `〈reportsDir〉/$0.md` で読める。
   - 仕様のページへの追従：依頼のファイル `〈git の共通ディレクトリ〉/orca-flow/requests/$0.md`（`git rev-parse --path-format=absolute --git-common-dir` の下）に「Notion の URL と中身を、決定の記録など公開に出るファイルに書かない」の行（intake の1行）があり、報告の「仕様のページとの違い」が「なし」でないときだけ、`${CLAUDE_PLUGIN_ROOT}/skills/integrate/spec-page.md` を読む（手順4と手順5で使う）。1行がない・節がない・「なし」なら読まず、何もしない。
3. `orca-flow integrate $0` を流す。終了コードごとに次をする。
   - 0：手順4へ。
   - 1 で、標準エラーに「マージの順のファイルが壊れています」が入る：タスク長には送らない（`orca-flow tell` は流さない。直し方の `order --clear` はタスクの worktree では終了コード2で止まるため）。統括役が main で行う。`orca-flow order` で順を見て（壊れていて読めないこともある）、`orca-flow order --clear` で消し、`${CLAUDE_PLUGIN_ROOT}/skills/approve/SKILL.md` の「重なりの question が来たら」の手順1〜3で順を決め直す。そのあと、もう一度 `orca-flow integrate $0` を流す。
   - 1：範囲外のファイル、決定の記録の抜け（下の箇条）、テストの失敗、タスクの worktree に未コミットの変更がある、報告がない、など。出た一覧か出力から直し方を決め、`orca-flow tell $0 "〈直し方〉。直したら報告を直し（報告が無視されていればコミットしない。git add が失敗しても -f で足さない。無視されていなければコミットする）、orca-flow verify を流して integrate-wait に戻して"` を流す。人間に、何が落ちたかと、タスク長に送った直し方を伝えて止まる。
   - 3：rebase が競合した。`orca-flow tell $0 "git rebase 〈baseBranch〉 をして競合を直し、orca-flow verify を流してから integrate-wait に戻して"` を流し、人間に伝えて止まる。
   - 1 で、標準エラーに「設計書に決定の記録の文案がありますが、差分に 〈decisionsFile〉 がありません」が入る（止めたときだけ出る文。「マージしていません」で終わる。節がないときの警告や `--skip-decision` の警告にも「決定の記録」は入り、`--skip-decision` の警告にはこの文も入るので、「決定の記録」だけで見分けない。止めの文が「警告：」で始まらない行に入るときだけ、項の抜けとして扱う。「警告：」で始まる行にあるときは止めではなく、人が飛ばすと決めた項なので、ほかの理由で止まっていても、その項を足させない。decisionsFile が設定にあり、設計書の文案が「なし」でないのに、タスクの差分に decisionsFile がない）：マージはされていない。直し方は、タスク長に項を足させる（文案を写し、人が選んだことを足して、タスクのブランチで decisionsFile に足してコミットする）ことで、上の終了コード1と同じに `orca-flow tell` で送る。文案が「なし」でないのに本当に残すことがないと人間が判断したときだけ、人間が頼んだときに `orca-flow integrate $0 --skip-decision` で警告にして通す。文案の節がない設計書は、警告が出るだけで止まらない。decisionsFile がない設定では、この確かめはない。
   - 1 で、標準エラーに「〈baseBranch〉 の 〈decisionsFile〉 が、タスクのブランチの 〈decisionsFile〉 の先頭と同じではありません」が入る（追記だけの確かめ。rebase のあと、マージの前に出る。「マージしていません」で終わる。rebase で記録の行が消えたか、すでにある項を書き換えている。merge=union の rebase で共通する行がまとめられて消えることがある）：マージはされていない。タスク長に、タスクのブランチで 〈baseBranch〉 の 〈decisionsFile〉 の行を戻し、自分の項を末尾に足し直してコミットし、orca-flow verify を流して integrate-wait に戻すよう、上の終了コード1と同じに `orca-flow tell` で送る。`--skip-decision` ではこの確かめは飛ばない。
   - 2 で、標準エラーに `orca-flow verify` の文字が入る：CLI が出した理由は、テストの記録がない、記録のあとにタスクのブランチが動いた、記録のあとに main でテストに関係するファイルが変わった（CLI がそのファイルを添える。記録の main のコミットが見つからない・今の main の祖先でない、も含む）、テストに関係しないファイルだけ動いて rebase したが競合した、記録のあとに流すコマンドが変わった、のどれか。テストはタスクのコンソールで流す決まりで、CLI がすでにタスク長に「orca-flow verify をやり直して integrate-wait に戻して」を送っている。`orca-flow tell` は送り直さない。人間に「$0 のコンソールでテストを流し直しています。integrate-wait に戻ったら、もう一度 /orca-flow:integrate $0」と伝えて止まる。CLI の警告に「verify のやり直しの知らせを送れませんでした」が入っていたら、CLI は verify のやり直しを送れていない（始めに出る「main が進んだ知らせを送れませんでした」の警告とは別の知らせ。それは verify のやり直しとは関係ない。警告は「警告：〈ID〉 のタスク長に verify のやり直しの知らせを送れませんでした：〈理由〉。〈すること〉」の形で、理由は、ターミナルが見つからない、1つに決まらない、入力欄に打ちかけがある、bash モード、入力欄を確かめられない、Orca の送信の失敗、のどれか）。タスク長に `orca-flow verify` をやり直して integrate-wait に戻すよう、人間から伝えてもらう（入力欄に打ちかけなら、人間にその文を送るか消してもらってから `orca-flow tell` で送ってもよい）。
   - 2 で、標準エラーに「マージの順」が入る（`orca-flow verify` の文字は入らない。順を決めた鎖で、前のタスクがあるタスクだけ（鎖の先頭は対象外）。上のテストの記録の止まりとは別）：マージはされていない。文で3つに分かれる。「先に 〈ID〉 を統合してください」は、前のタスクがまだ統合済みでない（CLI はタスク長に何も送っていない。`orca-flow tell` は送らない）。人間に、先に `/orca-flow:integrate 〈ID〉` を打つこと、順から外すなら人間が頼んだときだけ `orca-flow integrate $0 --skip-order` か `orca-flow order --remove $0` を使えることを伝えて止まる。「取り込み」を求める文（タスクの先頭が統合済みの前のタスクを含まない。`integrateVerify` が `before-merge` のときと push の道の文。after-merge は下の2つ）と、見直しを求める文（見直しの記録がない・今のタスク自身の変更と違う）は、CLI がタスク長に送り済みなので `tell` は送り直さない。人間に「$0 のコンソールで取り込みか見直しをしています。integrate-wait に戻ったら、もう一度 /orca-flow:integrate $0」と伝えて止まる。警告に「送れませんでした」が入っていたら送れていない。CLI が出した送れなかった文と候補のタブを人間に伝え、タスク長に取り込みか見直しをして integrate-wait に戻すよう、人間から伝えてもらう。
     - 取り込んで進んだ（`integrateVerify` が `after-merge` のとき。終了コード0）：前のタスクを CLI が自分で取り込み、タスク自身の変更が同じだったので、見直しとテストの記録を使ってそのままマージした。標準出力にそう出る。見直しは要らない。タスク長には何も送られていない。手順4へ進む。人間への伝え（手順5）に、取り込んだ前のタスクの ID を添える。`before-merge` のときと push の道では、この道は動かない。
     - 「を取り込みました（rebase の前の先頭 〈コミット〉）」と「orca-flow rebase-review 〈コミット〉」が入る文を CLI が送った（`integrateVerify` が `after-merge` のとき。終了コード2。標準エラーに「マージの順」が入る）：前のタスクを CLI が自分で取り込んだが、タスク自身の変更が変わったので、タスク長に見直しを頼んだ。タスクの worktree は rebase したままで、マージはされていない。CLI がタスク長に送り済みなので `orca-flow tell` は送らない。人間に「$0 のコンソールで取り込みのあとの見直しをしています。integrate-wait に戻ったら、もう一度 /orca-flow:integrate $0」と伝えて止まる。送れなかったときの警告（「送れませんでした」）は、上の「取り込み」「見直し」の文と同じに扱う。前のタスクの取り込みが競合したときは、CLI が rebase を取りやめて元の先頭に戻し、競合したと添えて従来どおりの取り込みの文を送る。この場合は上の「取り込み」を求める文と同じに扱う。
   - 2 で、標準エラーに「main の確かめが 〈ID か件名〉 の時点（〈短いコミット〉）で落ちています」が入る（先頭に「orca-flow: 」がつき、前に警告が並ぶことがある。`orca-flow verify` の文字は入らない。上の verify のやり直しとは別。CLI はタスク長に何も送っていない）：原因が分かっている。main の先頭が、前のマージのあとの確かめで落ちている（上で直すタスクの確かめが流れていても確かめられていなくても、落ちた結果が下にあれば止まる。CLI が上のコミットを添える）。マージはされていない。`orca-flow tell` は送らない。人間に、原因のタスク（ID か件名）・短いコミット・落ちたコマンド・戻すコマンド `git revert -m 1 〈コミット〉`・直すタスクを `--fixes-main` で入れる道・確かめ直しの `orca-flow main-check run` を本文に出し、AskUserQuestion で「戻す」「直すタスクを作る」「今は決めない」を聞く。
     - 原因が手での取り込み（cherry-pick や Mac からの束）で、落ちたのが決定の記録の整形（見出しが前の行にくっついている）なら、「戻す」の前にこちらを勧める。統括役が main で decisionsFile の見出しの前に空行を戻し（コードの囲みの中は除く。main の前からある部分は変えない）、`git add -- 〈decisionsFile〉 && git commit -m "〈integratorName〉: マージで欠けた決定の記録の空行を戻す" -- 〈decisionsFile〉`（CLI の直しと同じ件名）で decisionsFile だけをコミットして、`orca-flow main-check run` で確かめ直し、結果を人間に伝える。通れば、もう一度 /orca-flow:integrate $0 を打てると添える。CLI のコマンドはない（CLI が戻すのは integrate と push の道の取り込みと verify だけ）。
     - 「戻す」：統括役が main で `git revert -m 1 〈コミット〉` をし、`orca-flow main-check run` を流して、結果（通ったか、落ちたか）を人間に伝える。通れば、もう一度 /orca-flow:integrate $0 を打てると添える。
     - 「直すタスクを作る」：`${CLAUDE_PLUGIN_ROOT}/skills/new/SKILL.md` の手順（/orca-flow:new と同じ）で、落ちた main を直すタスクを作る（依頼のファイルに、落ちた main の原因・コミット・落ちたコマンドを写す）。直すタスクを統合するときは `orca-flow integrate 〈ID〉 --fixes-main` を使う（落ちた main の上でも止まらずにマージする）。作ったことを人間に伝えて止まる。$0 は統合しない。
     - 「今は決めない」：何もせず、落ちたままであること（次の統合も止まる）を伝えて止まる。
   - 2 で、標準エラーに「main の確かめが落ちています（…）」が入るが、「の時点」と短いコミットは入らず、`git revert` も出ない（先頭に「orca-flow: 」がつき、`orca-flow verify` の文字は入らない）：原因が分かっていない。文の終わりで3つに分かれる。「原因のコミットを探している途中です」は二分探索が続いている、「原因を探していたプロセスがもういません」は探す途中で止まった、「確かめられないコミットがあって、原因が分かりません」は途中のコミットを確かめられなかった。マージはされていない。`orca-flow tell` は送らない。先頭のマージが原因とは限らないので、戻すコマンドを作らず、「戻す」も聞かない。CLI の文をそのまま人間に伝え、探している途中なら `orca-flow main-check` で様子を見る、プロセスがいないなら `orca-flow main-check run` で確かめ直す、分からないなら `orca-flow main-check` のログを見る（直すタスクを `--fixes-main` で入れる道もある）と添える。AskUserQuestion では「直すタスクを作る」「今は決めない」だけを聞き、選ばれたあとの扱いは上の同じ名前の箇条と同じ。
   - 0 で、標準エラーに「警告：main の確かめができませんでした（…）」が入る：落ちたのではなく、確かめられなかっただけで、マージは済んでいて、止まらない。括弧の中が「準備の失敗：…」なら確かめ用の作業ツリーの切り替えか setup.sh が失敗している。「原因の1つ前も今の環境で落ちました。環境の不調かもしれません：…」なら、二分探索の原因の1つ前も今の環境で落ちたので、環境（node_modules の破損など）を疑う。どちらも人間に、ログのパスと、直してから `orca-flow main-check run` で確かめ直せることを伝える。
   - 1・3 の段で流した `orca-flow tell` が終了コード2を返したとき（タスク長のターミナルが見つからない・1つに決まらない・入力欄に打ちかけがある・bash モード・入力欄を確かめられない、のどれか。`orca-flow tell` の Orca の送信の失敗は終了コード1）：CLI が出した送れなかった文と、候補のタブ（題名とハンドル）を人間にそのまま伝えて止まる。送り直しは、人間が入力欄の文を送るか消す、bash モードを抜ける、タブを入力欄に戻すなどしてから行う。
   - 2 で、標準エラーに「main を書き換えています」が入る（「〈相手〉が main を書き換えています（ロック：〈パス〉）」。相手は integrate・push の道の後始末・approve・new のどれか、種類のない古いロックは「別の処理」。何も変えずに止まっている）：CLI の文を人間にそのまま伝え、少し待ってもう一度 `/orca-flow:integrate $0` を打つよう伝える。ロックが残ったままのときは、文のロックのパスのファイルを、持ち主の処理がもう動いていないと確かめてから消してもらう。自分では消さない。
   - 2 で、それ以外（統括役の場所でない、など）：メッセージを人間に伝え、何をすればよいかを添えて止まる。

   決定の記録の項の抜けの確かめを飛ばす逃げ道として `orca-flow integrate $0 --skip-decision` がある（上の項の抜けの終了コード1を警告にして通す。追記だけの確かめは飛ばない）。人間が頼んだときだけ使う。項を足し忘れた場合は、飛ばさずにタスク長に足させる。

   記録が使えないときの逃げ道として `orca-flow integrate $0 --verify-here` がある（integrate の中で rebase とテストを流す）。人間が頼んだときだけ使う。

   順の門を飛ばす逃げ道として `orca-flow integrate $0 --skip-order` がある（「マージの順」の3つの確かめを全部飛ばす）。人間が頼んだときだけ使う。統合したら（`--skip-order` で通したときも）、順に統合済みの印をつける。

   記録を使ってマージしたときは、CLI が「〈時刻〉に 〈ID〉 のコンソールで通った記録を使います」と出す。差分がすべて設定の `verifySkipPaths` の中なら、テストを飛ばしてマージする。

   記録のあと main がテストに関係しないファイル（`verifySkipPaths`・`.orca-flow/config.json`・進捗表のファイル）だけ動いていたときは、CLI が「記録のあと main で変わったテストに関係しないファイル：…」を添える。この場合 CLI は記録を使い続け、タスクの worktree で rebase してからマージする（テストは流し直さない）。rebase が競合したときは、上の verify のやり直しの終了コード2になる。

4. 報告の3つの節（「共有のファイルの変更の依頼」「人間に決めてほしいこと」「後回しにしたもの」）を読み、統括役の仕事として扱う。古い報告の「人間に確認が必要なこと」も同じに読む。古い報告は、項目を3つの節に振り分け、推奨がなければ統括役がつける。残った理由がない項目（古い報告）は、差分とコードから統括役が6つの言葉（範囲の外・設計で範囲の外・前からある・2回で直らない・直しのあとに見つけた・確かめきれない）の1つをつけ、一覧に「統括役がつけた」と添える。
   - 統括役は、タスク長の推奨をそのまま信じず、差分とコードを読んで推奨を確かめる。違う考えなら統括役の推奨を既定にし、「タスク長は〇〇を推した」と添える。
   - 報告に「人が選んだこと」がある項目（run が統合の前に聞いたもの。「人間に決めてほしいこと」の節の項目だけ。ほかの節に書いてあっても聞く）は、決まったものとして扱い、聞き直さない。一覧には「統合の前に決まり済み：〈答え〉」として出し、選択肢では聞かない。答えが「後続のタスクにする」なら下の箇条どおりに作り、「このままにする」なら何もしない。
   - 一覧（番号・見出し・残った理由・起きること・推奨と理由）を本文に出し、AskUserQuestion で「すべて推奨どおり（おすすめ）」「項目ごとに選ぶ」「今は決めない」を聞く。
   - 仕様のページに戻す：手順2で `spec-page.md` を読んだときだけ、報告の「仕様のページとの違い」を、一覧に1つの項目として出す。選択肢は「仕様のページに戻す（Recommended）」「戻さない」「後で決める」。起きること（戻さないと、続きの項目が古い仕様から始まる）と、違いの中身を出す。選ばれたら、`spec-page.md` のとおりに戻す。「後で決める」は手順5の残りに入れる。「すべて推奨どおり」なら戻す。
   - 戻す・戻さないの選択は決定の記録に足さない（Notion の中身を公開に出さないため。違いの理由は run の項と報告にある）。
   - 後続のタスクの作り方：一覧に、後続のタスクになりうる項目（「人間に決めてほしいこと」の項目で、「このままにする」に決まり済みでないもの）があるときだけ、この一覧の AskUserQuestion と同じ呼び出しの2問目に「後続のタスクの作り方」を足す（聞く回数を増やさないため）。選択肢は「ふつうに作る（Recommended）」「おまかせで作る」で、ふつうに作るを先頭にする（後続の設計書を人が読まずに進むのは、人が選んだときだけにするため）。後続のタスクにする項目がなかったとき（「今は決めない」・全部「このままにする」など）は、この答えを使わない（new が止まったときは下の箇条のとおり使う）。
   - 画面の記録：依頼のファイル（`git rev-parse --path-format=absolute --git-common-dir` の下の `orca-flow/requests/$0.md`）に「Notion の URL と中身を、決定の記録など公開に出るファイルに書かない」の1行があり、同じ下の `orca-flow/captures/$0/` に GIF があるときだけ、`${CLAUDE_PLUGIN_ROOT}/skills/integrate/spec-page-capture.md` を読む。一覧に「画面の記録を仕様のページに載せる」の項目を出す（推奨は「載せる」、ほかは「載せない」「後で決める」）。おまかせでは推奨どおりにし、`orca-flow auto log $0 '〈決めたこと〉'` に残す。「載せない」なら、`orca-flow/captures/$0/` の記録の場所を消す。「後で決める」なら、手順5の残りに記録の場所を会話で示す（ファイルには書かない）。載せる・載せないの選択は決定の記録に足さない（Notion の中身を公開に出さないため）。
   - 「項目ごとに選ぶ」なら、AskUserQuestion で項目ごとに聞く（1回4問まで。多ければ分ける）。推奨を先頭にして「（Recommended）」をつけ、「後で決める」も入れる。
   - 共有のファイルの変更の項目の選択肢は「main で今変える」「変えない」「後で決める」。一覧に、項目ごとに何をどう変えるかを出す。選んだこと（「すべて推奨どおり」を含む）を承認とみなし、聞き直さない。実際の変更が一覧に出した中身と違ってしまうときだけ、もう一度聞く。ファイルを変えない依頼（/reload-plugins など）は聞かずに、手順5で伝える。大事な共有のファイルの項目には、一覧に「差分を見てから入れる」と添える（次の箇条）。
   - 大事な共有のファイル（`.claude/` の下（CLAUDE.md を除く）・`.orca-flow/` の下・`orca.yaml`・`package.json`（ファイル全体）・`.worktreeinclude`）の「main で今変える」の項目は、「変える → 差分を見せる → 「入れる」なら verify → コミット」の順にする。main で変えたあと、コミットの前に実際の差分を本文に出す（追跡中のファイルは `git diff`、新しいファイルは中身全体）。そのうえで AskUserQuestion で「入れる」「入れない」を聞く。「入れない」なら、変えたファイルを戻し、新しく足したファイルも消して、手順5の残りに入れる。「入れる」の前に verify を流さない（人が見る前に、書き換えたコマンドを main で動かさないため）。この範囲に当たらない共有のファイルは、選べば承認とみなす。
   - 「main で今変える」の変更は、後続のタスクを作る new より前に済ませる（new は main に未コミットの変更があると止まるため）。verify を通し、変えたファイルだけを `〈integratorName〉: $0 の依頼（〈要点〉）` でコミットする。verify が落ちたら、変えたファイルを戻し、手順5の残りに入れる。大事な共有のファイルは、「入れる」と答えたものだけをコミットする。
   - 「後続のタスクにする」に決まった項目は、統括役が1つのタスクにまとめ、`${CLAUDE_PLUGIN_ROOT}/skills/new/SKILL.md` の手順で作る。「後続のタスクの作り方」が「おまかせで作る」なら、new の手順を `--auto` つきで流し、作れたら `orca-flow auto log 〈後続の ID〉 '〈決めたこと〉'` を残す（一重引用符で囲み、中の ' は '\'' にする。理由はおまかせの決まりの4と同じ）。「ふつうに作る」なら今までどおり `--auto` をつけない。auto log は残さない（後続に記録がないため）。依頼のファイルに、項目ごとの全文（見出し・起きること・根拠・推奨と理由・人が選んだこと）と、元の報告の場所と項目の番号を写す。場所は、報告が無視されていなければ `git show 〈baseBranch〉:〈reportsDir〉/$0.md`（〈baseBranch〉と〈reportsDir〉には config の実際の値を入れる。例：baseBranch が main なら `main`）、無視されていれば（メインの作業ツリーで `git check-ignore -q 〈reportsDir〉/$0.md` が成功する）メインの作業ツリーの `〈reportsDir〉/$0.md` のパスにする。要約しない。タスク名は、変わること（中身）で名づけ、「〈ID〉 の残り」としない（Orca の左の名前から中身が分かるように）。依頼のファイルには、項目の残った理由と、前のタスクで直さなかった理由（なぜ別のタスクか）も写す。
   - new の手順の「止まる」は、ここでは「手順5へ進む」と読む（マージはもう済んでいるため）。new が終了コード1か2（終了コード2は作業中のタスクが上限など）なら、作り直さず、人が打つ /orca-flow:new の文を手順5の残りに入れて手順5へ進む。「後続のタスクの作り方」が「おまかせで作る」なら、人が打つ文を `/orca-flow:new --auto 〈やりたいこと〉` にする（選んだことを落とさないため）。一時ディレクトリは new の手順どおり消す。
   - new が worktree を作ったあとに失敗したとき（出力に残っているものか片付けの案内が出ているとき）は、それも手順5の残りに入れる。new の出力の案内をそのまま写す（「先にタスク長を止めてから」の前置きと、コマンドのない形（フォルダだけ残る・ブランチが分からない）も含む。前置きが落ちると、動いているタスク長の worktree を人が消しうるため）。片付けのコマンドは統括役が流さず、人に伝えるだけにする（new のスキルの手順5と同じ）。人には、片付けてから /orca-flow:new を打つよう添える。
   - 統合のときに決まった選択（一覧で人が選んだこと、「後続のタスクにする」「このままにする」「main で今変える」「変えない」「おまかせで作る」「ふつうに作る」などの答え）は、decisionsFile が設定にあるときだけ、統括役が main で decisionsFile の末尾に項として足す。統合の前に決まり済みのもの（報告の「人が選んだこと」）は、run がタスクのブランチで項に足してあるので、足し直さない。足すのは、統合のときに決まった選択がある場合だけ。ただし、載せる・載せないの選択と、戻す・戻さないの選択は足さない（Notion の中身を公開に出さないため）。
     - 項は「## 〈日付〉 〈見出し〉」と、決めたこと・理由・捨てた案と理由・人が選んだことの箇条書き（見出しは何の話かを人間の言葉で。日付は今日、`date +%F`）。すでにある項を書き換えず、末尾に足すだけにする。ID・導入先の名前・手元のパス・秘密を書かない。過去の決めごとを指すときは、その項の「〈日付〉 〈見出し〉」を書き、設計書・報告のパスと ID は書かず、「設計書を見て」と書かずに読むだけで分かる文にする。
     - マージのあとに足してコミットする：`git add -- 〈decisionsFile〉 && git commit -m "〈integratorName〉: $0 の決定の記録（〈要点〉）" -- 〈decisionsFile〉`（decisionsFile だけをコミットする）。追記だけのファイルへの足しなので、verify は流し直さない。ただし verify のかわりに、コミットの前に `git diff -- 〈decisionsFile〉` の `+` の行を見て、idPrefix と数字の形（ID）がないか、見出しが「## 〈日付〉 〈見出し〉」で「決めたこと」「理由」があるかを確かめ、足りなければ直してからコミットする。足したことを手順5で伝える。
   - 「このままにする」に決まった項目は何もしない。「後回しにしたもの」は聞かず、手順5で1行ずつ伝える。「後で決める」「今は決めない」は手順5の残りに入れる。
5. 人間に次を伝える：マージしたこと、テストの結果（CLI が出した、どの記録を使ったか・飛ばしたか・ここで流したか）、残り（依頼のうち済んでいないもの、「後で決める」「今は決めない」としたもの、後続のタスクにしたもの（おまかせで作ったか、ふつうに作ったか）、「後回しにしたもの」の1行ずつ）。最後に「push はあなたが行ってください」と添える。
   - 設定の `integrateVerify` が `after-merge`（既定）のとき、マージのあと CLI が main の確かめを背景で始める。CLI の出力に、確かめを背景で始めたこと、または記録と同じ木で済んだこと（「記録と同じ木なので、main の確かめは通ったことにしました」。このときも背景の確かめは起動し、まだ送っていない「main が進んだ知らせ」だけを送る。「main が進んだ知らせは、確かめが通ってから送ります」と出る）が出るので、人間に伝える。確かめの様子と結果は `orca-flow main-check` で見られると添える。落ちていれば次の統合が手順3の終了コード2（main の確かめが落ちています）で止まる。after-merge では「main が進んだ知らせ」はマージの直後には送られず、背景の確かめのあと、通っていれば CLI が作業中のタスクに送る（落ちたときは送らない）。`before-merge` のときは今までどおり、マージの中ですぐ送る。
   - 終了コード0でも、CLI の警告（「警告：〈ID〉 のタスク長に main が進んだ知らせを送れませんでした：〈理由〉。〈すること〉」。after-merge では、確かめが通ったあとの `orca-flow main-check` か次の integrate が同じ形で出す）に「main が進んだ知らせを送れませんでした」が入っていたら、作業中のほかのタスクへの「main が進んだ」知らせが届いていない。警告の文から、どのタスクに届いていないかを人間に伝え、そのタスクが作業中なら区切りで main を取り込む（`git rebase`）よう、人間から伝えてもらう。統合待ちのタスクなら何もしなくてよい（rebase も verify もしない）と添える（入力欄の状態が直ってから `orca-flow tell` で送ってもよい）。

## おまかせの決まり

`/orca-flow:auto` の番が来て、おまかせのタスク $0 を統合するときの決まり（人が `/orca-flow:integrate` を打ったときは、この節を使わず、上の手順のまま）。

1. 手順4の報告の3つの節は、「すべて推奨どおり（おすすめ）」を選んだものとして扱い、一覧を出して聞かない。聞くのは次の2つだけ：統括役が推奨を決めきれない項目（差分とコードを読んでも決められないもの）と、大事な共有のファイル（手順4の箇条の範囲）の「入れる」「入れない」。大事な共有のファイルは、これまでどおり変えたあとに差分を見せて聞く。「人が選んだこと」のある項目は、今までどおり決まったものとして扱う。
2. 手順3の終了コード1・3と「main の確かめが 〈ID か件名〉 の時点（…）で落ちています」「main の確かめが落ちています（…）」は、今の扱いのうえで、おまかせを外す：`orca-flow auto off $0 --reason '〈止まった理由の一言〉'`（文は設計書・報告・CLI の標準エラーから写すので、一重引用符で囲み、中の ' は '\'' にする。二重引用符だと、バッククォートや $(…) がコマンドとして動く）。外したことを人間に伝える。そのあとは人が `/orca-flow:integrate $0` を打つ。
3. 手順3の「orca-flow verify」のやり直しと、マージの順の「取り込み」「見直し」（after-merge の「を取り込みました」を含む）の終了コード2は、おまかせのまま外さない。人間に状況（タスク長のコンソールで直している）だけを伝えて止まり、「戻ったらもう一度 /orca-flow:integrate を打って」とは伝えない（打たなくてよい）。タスク長が integrate-wait に戻れば、番が立ち直り、統括役が続けます。「先に 〈ID〉 を統合してください」は別で、CLI がタスク長に何も送らず、番も立たない：人間に、前のタスク 〈ID〉 が先に統合されることを伝えて止まる（前のタスクもおまかせなら、その番で統括役が統合する）。前のタスクを統合したあと、順の次のタスクが統合待ちでおまかせなら、`orca-flow auto on 〈次の ID〉` で番を立て直す。
4. 決めたことは、1項目ずつ `orca-flow auto log $0 '〈決めたこと〉'` に残す（一重引用符で囲み、中の ' は '\'' にする。理由は2と同じ）。
   - 手順4の決定の記録の項に足す選択のうち、統括役が聞かずに推奨どおりに決めたものは、項の「人が選んだこと」に「おすすめどおり（おまかせで統括役が決めた）」と書く（聞かずに決めたものを、人が選んだように書かない）。人に聞いて決まったものは、人の答えを書く。
5. 手順5の人への伝え方に、決めたことを並べ、`orca-flow auto show $0` で読み返せると添える。
6. 後続のタスクを作るときは、聞かず、`--auto` をつけない（ふつうに作る。人の知らないまま後続が後続を生み続けないため）。作れたら `orca-flow auto log $0 '後続の 〈ID〉 をふつうに作った'` を残し、手順5で `/orca-flow:auto on 〈ID〉` でおまかせにできると添える。
7. 手順4の「仕様のページに戻す」は、推奨どおりに戻す。聞かず、`orca-flow auto log $0 '仕様のページに戻した（〈違いの数〉件）'` を残す（戻せなかったときは、その旨を残す）。

## 守ること

- push はしない。ブランチは消さない。
- タスクの worktree の中のファイルを、統括役のタブから書き換えない。直しはタスク長に `orca-flow tell` で頼む。
