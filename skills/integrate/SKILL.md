あなたは統括役として、タスク $0 を main に統合する。人間が報告と差分を読んで、よいと判断したあとに呼ばれている。

CLI は `orca-flow` で呼ぶ（プラグインの bin が PATH に入っている）。見つからなければ `"${CLAUDE_PLUGIN_ROOT}/bin/orca-flow"` で呼ぶ。終了コードは 0＝成功、1＝確認に落ちた・失敗、2＝人間か統括役の作業が先に要る、3＝git の競合。

## 手順

1. `orca-flow config --json` で設定を読む（reportsDir・verify・integratorName・baseBranch）。`orca-flow active` で $0 のブランチを調べる。
2. 報告を読む：`git show 〈ブランチ〉:〈reportsDir〉/$0.md`。報告が無視されていれば（タスクの worktree で `git check-ignore -q 〈reportsDir〉/$0.md` が成功する。worktree のパスは `orca-flow active` で分かる）コミットされていないので、無視されていればファイルを読む：`〈タスクの worktree〉/〈reportsDir〉/$0.md`。無視された設計書と報告は、integrate がマージの前にメインの作業ツリーの同じパスへ写す（写せなければ終了コード1でマージしない）。統合のあと、元の報告はメインの作業ツリーの `〈reportsDir〉/$0.md` で読める。
3. `orca-flow integrate $0` を流す。終了コードごとに次をする。
   - 0：手順4へ。
   - 1：範囲外のファイル、テストの失敗、タスクの worktree に未コミットの変更がある、報告がない、など。出た一覧か出力から直し方を決め、`orca-flow tell $0 "〈直し方〉。直したら報告を直し（報告が無視されていればコミットしない。git add が失敗しても -f で足さない。無視されていなければコミットする）、orca-flow verify を流して integrate-wait に戻して"` を流す。人間に、何が落ちたかと、タスク長に送った直し方を伝えて止まる。
   - 3：rebase が競合した。`orca-flow tell $0 "git rebase 〈baseBranch〉 をして競合を直し、orca-flow verify を流してから integrate-wait に戻して"` を流し、人間に伝えて止まる。
   - 2 で、標準エラーに `orca-flow verify` の文字が入る：CLI が出した理由は、テストの記録がない、記録のあとにタスクのブランチが動いた、記録のあとに main でテストに関係するファイルが変わった（CLI がそのファイルを添える。記録の main のコミットが見つからない・今の main の祖先でない、も含む）、テストに関係しないファイルだけ動いて rebase したが競合した、記録のあとに流すコマンドが変わった、のどれか。テストはタスクのコンソールで流す決まりで、CLI がすでにタスク長に「orca-flow verify をやり直して integrate-wait に戻して」を送っている。`orca-flow tell` は送り直さない。人間に「$0 のコンソールでテストを流し直しています。integrate-wait に戻ったら、もう一度 /orca-flow:integrate $0」と伝えて止まる。CLI の警告に「verify のやり直しの知らせを送れませんでした」が入っていたら、CLI は verify のやり直しを送れていない（始めに出る「main が進んだ知らせを送れませんでした」の警告とは別の知らせ。それは verify のやり直しとは関係ない。警告は「警告：〈ID〉 のタスク長に verify のやり直しの知らせを送れませんでした：〈理由〉。〈すること〉」の形で、理由は、ターミナルが見つからない、1つに決まらない、入力欄に打ちかけがある、bash モード、入力欄を確かめられない、Orca の送信の失敗、のどれか）。タスク長に `orca-flow verify` をやり直して integrate-wait に戻すよう、人間から伝えてもらう（入力欄に打ちかけなら、人間にその文を送るか消してもらってから `orca-flow tell` で送ってもよい）。
   - 2 で、標準エラーに「main の確かめが 〈ID か件名〉 の時点（〈短いコミット〉）で落ちています」が入る（先頭に「orca-flow: 」がつき、前に警告が並ぶことがある。`orca-flow verify` の文字は入らない。上の verify のやり直しとは別。CLI はタスク長に何も送っていない）：原因が分かっている。main の先頭が、前のマージのあとの確かめで落ちている（上で直すタスクの確かめが流れていても確かめられていなくても、落ちた結果が下にあれば止まる。CLI が上のコミットを添える）。マージはされていない。`orca-flow tell` は送らない。人間に、原因のタスク（ID か件名）・短いコミット・落ちたコマンド・戻すコマンド `git revert -m 1 〈コミット〉`・直すタスクを `--fixes-main` で入れる道・確かめ直しの `orca-flow main-check run` を本文に出し、AskUserQuestion で「戻す」「直すタスクを作る」「今は決めない」を聞く。
     - 「戻す」：統括役が main で `git revert -m 1 〈コミット〉` をし、`orca-flow main-check run` を流して、結果（通ったか、落ちたか）を人間に伝える。通れば、もう一度 /orca-flow:integrate $0 を打てると添える。
     - 「直すタスクを作る」：`${CLAUDE_PLUGIN_ROOT}/skills/new/SKILL.md` の手順（/orca-flow:new と同じ）で、落ちた main を直すタスクを作る（依頼のファイルに、落ちた main の原因・コミット・落ちたコマンドを写す）。直すタスクを統合するときは `orca-flow integrate 〈ID〉 --fixes-main` を使う（落ちた main の上でも止まらずにマージする）。作ったことを人間に伝えて止まる。$0 は統合しない。
     - 「今は決めない」：何もせず、落ちたままであること（次の統合も止まる）を伝えて止まる。
   - 2 で、標準エラーに「main の確かめが落ちています（…）」が入るが、「の時点」と短いコミットは入らず、`git revert` も出ない（先頭に「orca-flow: 」がつき、`orca-flow verify` の文字は入らない）：原因が分かっていない。文の終わりで3つに分かれる。「原因のコミットを探している途中です」は二分探索が続いている、「原因を探していたプロセスがもういません」は探す途中で止まった、「確かめられないコミットがあって、原因が分かりません」は途中のコミットを確かめられなかった。マージはされていない。`orca-flow tell` は送らない。先頭のマージが原因とは限らないので、戻すコマンドを作らず、「戻す」も聞かない。CLI の文をそのまま人間に伝え、探している途中なら `orca-flow main-check` で様子を見る、プロセスがいないなら `orca-flow main-check run` で確かめ直す、分からないなら `orca-flow main-check` のログを見る（直すタスクを `--fixes-main` で入れる道もある）と添える。AskUserQuestion では「直すタスクを作る」「今は決めない」だけを聞き、選ばれたあとの扱いは上の同じ名前の箇条と同じ。
   - 0 で、標準エラーに「警告：main の確かめができませんでした（…）」が入る：落ちたのではなく、確かめられなかっただけで、マージは済んでいて、止まらない。括弧の中が「準備の失敗：…」なら確かめ用の作業ツリーの切り替えか setup.sh が失敗している。「原因の1つ前も今の環境で落ちました。環境の不調かもしれません：…」なら、二分探索の原因の1つ前も今の環境で落ちたので、環境（node_modules の破損など）を疑う。どちらも人間に、ログのパスと、直してから `orca-flow main-check run` で確かめ直せることを伝える。
   - 1・3 の段で流した `orca-flow tell` が終了コード2を返したとき（タスク長のターミナルが見つからない・1つに決まらない・入力欄に打ちかけがある・bash モード・入力欄を確かめられない、のどれか。`orca-flow tell` の Orca の送信の失敗は終了コード1）：CLI が出した送れなかった文と、候補のタブ（題名とハンドル）を人間にそのまま伝えて止まる。送り直しは、人間が入力欄の文を送るか消す、bash モードを抜ける、タブを入力欄に戻すなどしてから行う。
   - 2 で、それ以外（統括役の場所でない、など）：メッセージを人間に伝え、何をすればよいかを添えて止まる。

   記録が使えないときの逃げ道として `orca-flow integrate $0 --verify-here` がある（integrate の中で rebase とテストを流す）。人間が頼んだときだけ使う。

   記録を使ってマージしたときは、CLI が「〈時刻〉に 〈ID〉 のコンソールで通った記録を使います」と出す。差分がすべて設定の `verifySkipPaths` の中なら、テストを飛ばしてマージする。

   記録のあと main がテストに関係しないファイル（`verifySkipPaths`・`.orca-flow/config.json`・進捗表のファイル）だけ動いていたときは、CLI が「記録のあと main で変わったテストに関係しないファイル：…」を添える。この場合 CLI は記録を使い続け、タスクの worktree で rebase してからマージする（テストは流し直さない）。rebase が競合したときは、上の verify のやり直しの終了コード2になる。

4. 報告の3つの節（「共有のファイルの変更の依頼」「人間に決めてほしいこと」「後回しにしたもの」）を読み、統括役の仕事として扱う。古い報告の「人間に確認が必要なこと」も同じに読む。古い報告は、項目を3つの節に振り分け、推奨がなければ統括役がつける。残った理由がない項目（古い報告）は、差分とコードから統括役が6つの言葉（範囲の外・設計で範囲の外・前からある・2回で直らない・直しのあとに見つけた・確かめきれない）の1つをつけ、一覧に「統括役がつけた」と添える。
   - 統括役は、タスク長の推奨をそのまま信じず、差分とコードを読んで推奨を確かめる。違う考えなら統括役の推奨を既定にし、「タスク長は〇〇を推した」と添える。
   - 報告に「人が選んだこと」がある項目（run が統合の前に聞いたもの。「人間に決めてほしいこと」の節の項目だけ。ほかの節に書いてあっても聞く）は、決まったものとして扱い、聞き直さない。一覧には「統合の前に決まり済み：〈答え〉」として出し、選択肢では聞かない。答えが「後続のタスクにする」なら下の箇条どおりに作り、「このままにする」なら何もしない。
   - 一覧（番号・見出し・残った理由・起きること・推奨と理由）を本文に出し、AskUserQuestion で「すべて推奨どおり（おすすめ）」「項目ごとに選ぶ」「今は決めない」を聞く。
   - 「項目ごとに選ぶ」なら、AskUserQuestion で項目ごとに聞く（1回4問まで。多ければ分ける）。推奨を先頭にして「（Recommended）」をつけ、「後で決める」も入れる。
   - 共有のファイルの変更の項目の選択肢は「main で今変える」「変えない」「後で決める」。一覧に、項目ごとに何をどう変えるかを出す。選んだこと（「すべて推奨どおり」を含む）を承認とみなし、聞き直さない。実際の変更が一覧に出した中身と違ってしまうときだけ、もう一度聞く。ファイルを変えない依頼（/reload-plugins など）は聞かずに、手順5で伝える。大事な共有のファイルの項目には、一覧に「差分を見てから入れる」と添える（次の箇条）。
   - 大事な共有のファイル（`.claude/` の下（CLAUDE.md を除く）・`.orca-flow/` の下・`orca.yaml`・`package.json`（ファイル全体）・`.worktreeinclude`）の「main で今変える」の項目は、「変える → 差分を見せる → 「入れる」なら verify → コミット」の順にする。main で変えたあと、コミットの前に実際の差分を本文に出す（追跡中のファイルは `git diff`、新しいファイルは中身全体）。そのうえで AskUserQuestion で「入れる」「入れない」を聞く。「入れない」なら、変えたファイルを戻し、新しく足したファイルも消して、手順5の残りに入れる。「入れる」の前に verify を流さない（人が見る前に、書き換えたコマンドを main で動かさないため）。この範囲に当たらない共有のファイルは、選べば承認とみなす。
   - 「main で今変える」の変更は、後続のタスクを作る new より前に済ませる（new は main に未コミットの変更があると止まるため）。verify を通し、変えたファイルだけを `〈integratorName〉: $0 の依頼（〈要点〉）` でコミットする。verify が落ちたら、変えたファイルを戻し、手順5の残りに入れる。大事な共有のファイルは、「入れる」と答えたものだけをコミットする。
   - 「後続のタスクにする」に決まった項目は、統括役が1つのタスクにまとめ、`${CLAUDE_PLUGIN_ROOT}/skills/new/SKILL.md` の手順で作る。依頼のファイルに、項目ごとの全文（見出し・起きること・根拠・推奨と理由・人が選んだこと）と、元の報告の場所と項目の番号を写す。場所は、報告が無視されていなければ `git show 〈baseBranch〉:〈reportsDir〉/$0.md`（〈baseBranch〉と〈reportsDir〉には config の実際の値を入れる。例：baseBranch が main なら `main`）、無視されていれば（メインの作業ツリーで `git check-ignore -q 〈reportsDir〉/$0.md` が成功する）メインの作業ツリーの `〈reportsDir〉/$0.md` のパスにする。要約しない。タスク名は、変わること（中身）で名づけ、「〈ID〉 の残り」としない（Orca の左の名前から中身が分かるように）。依頼のファイルには、項目の残った理由と、前のタスクで直さなかった理由（なぜ別のタスクか）も写す。
   - new の手順の「止まる」は、ここでは「手順5へ進む」と読む（マージはもう済んでいるため）。new が終了コード1か2（終了コード2は作業中のタスクが上限など）なら、作り直さず、人が打つ /orca-flow:new の文を手順5の残りに入れて手順5へ進む。一時ディレクトリは new の手順どおり消す。
   - new が worktree を作ったあとに失敗したとき（出力に残っているものか片付けの案内が出ているとき）は、それも手順5の残りに入れる。new の出力の案内をそのまま写す（「先にタスク長を止めてから」の前置きと、コマンドのない形（フォルダだけ残る・ブランチが分からない）も含む。前置きが落ちると、動いているタスク長の worktree を人が消しうるため）。片付けのコマンドは統括役が流さず、人に伝えるだけにする（new のスキルの手順5と同じ）。人には、片付けてから /orca-flow:new を打つよう添える。
   - 「このままにする」に決まった項目は何もしない。「後回しにしたもの」は聞かず、手順5で1行ずつ伝える。「後で決める」「今は決めない」は手順5の残りに入れる。
5. 人間に次を伝える：マージしたこと、テストの結果（CLI が出した、どの記録を使ったか・飛ばしたか・ここで流したか）、残り（依頼のうち済んでいないもの、「後で決める」「今は決めない」としたもの、後続のタスクにしたもの、「後回しにしたもの」の1行ずつ）。最後に「push はあなたが行ってください」と添える。
   - 設定の `integrateVerify` が `after-merge`（既定）のとき、マージのあと CLI が main の確かめを背景で始める。CLI の出力に、確かめを背景で始めたこと、または記録と同じ木で済んだこと（「記録と同じ木なので、main の確かめは通ったことにしました」。このときも背景の確かめは起動し、まだ送っていない「main が進んだ知らせ」だけを送る。「main が進んだ知らせは、確かめが通ってから送ります」と出る）が出るので、人間に伝える。確かめの様子と結果は `orca-flow main-check` で見られると添える。落ちていれば次の統合が手順3の終了コード2（main の確かめが落ちています）で止まる。after-merge では「main が進んだ知らせ」はマージの直後には送られず、背景の確かめのあと、通っていれば CLI が作業中のタスクに送る（落ちたときは送らない）。`before-merge` のときは今までどおり、マージの中ですぐ送る。
   - 終了コード0でも、CLI の警告（「警告：〈ID〉 のタスク長に main が進んだ知らせを送れませんでした：〈理由〉。〈すること〉」。after-merge では、確かめが通ったあとの `orca-flow main-check` か次の integrate が同じ形で出す）に「main が進んだ知らせを送れませんでした」が入っていたら、作業中のほかのタスクへの「main が進んだ」知らせが届いていない。警告の文から、どのタスクに届いていないかを人間に伝え、そのタスクが作業中なら区切りで main を取り込む（`git rebase`）よう、人間から伝えてもらう。統合待ちのタスクなら何もしなくてよい（rebase も verify もしない）と添える（入力欄の状態が直ってから `orca-flow tell` で送ってもよい）。

## 守ること

- push はしない。ブランチは消さない。
- タスクの worktree の中のファイルを、統括役のタブから書き換えない。直しはタスク長に `orca-flow tell` で頼む。
