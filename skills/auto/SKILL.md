name: auto
description: おまかせ（承認と統合の人の確認を飛ばす）のタスクの一覧を出し、統括役のタブの背景の待ち受けを始める。引数で、おまかせを外す・決めたことを読むなどもできる。番が来たら承認か統合を進める。統括役のタブ（メインのチェックアウト）で人間が打つ。
argument-hint: "[off 〈ID〉 [--reason 〈文〉] | off --all | show 〈ID〉 | on 〈ID〉]"
disable-model-invocation: true
---

あなたは統括役として、おまかせのタスクを扱う。おまかせは、`/orca-flow:new --auto` で作ったタスクの印で、approve と integrate の人の確認を飛ばして進める。

承認だけのおまかせ：intake が前を待つ印をつけて始めたタスクは、前が整う（前の実装完了か、前が baseBranch に入った）と、待ち受けが承認だけのおまかせにして承認の番を立てる。承認は下の「番が来たら」で、approve の「おまかせの決まり」のまま行う（守りは今のおまかせの決まりのまま。推奨が決めきれないときと大事な共有のファイルは人に聞く）。統合の番は立たないので、統合は人が `/orca-flow:integrate` で確かめて行う。前が整っていなければ、spec-review でも承認の番は立たない（もとからおまかせのタスクでも）。`on 〈ID〉` でも同じで、承認だけのおまかせのタスクは統合待ちでも統合の番が立たず（承認だけのまま）、前が整っていない印のタスクはおまかせにするが承認の番は立たない。

先の承認：前が整っていない印のタスクは、人が `/orca-flow:approve` で先に承認しておける（`orca-flow approve 〈ID〉 --when-ready`。おまかせを外してあったタスクは承認だけのおまかせに戻る）。一覧と `show 〈ID〉` の前を待つタスクの行に「先の承認：有効」か「先の承認：設計書が変わったので外れました」が出る。前が整って承認の番が来たら、「先の承認：有効」なら人の承認として実装を始め、外れていればおまかせの決まりで承認する（approve の「おまかせの決まり」の9）。`off 〈ID〉`・`off --all` は先の承認も消す。

前の直しの見張り：待ち受けは見直すたびに、乗せたタスク（前の枝の上で始めたタスク）の枝が、乗せた先の verify の通った先頭を含まなければ、そのタスク長に「前の枝が進んだ」を送る（前に人のレビューの直しが入っても、後ろが取り込めるように）。送れなければ（打ちかけなど）間を置いて送り直す。乗せた先が作業中の乗せたタスクがあれば、おまかせのタスクも前を待つタスクもなくても、待ち受けは番なしで終わらない。

引数：$ARGUMENTS

CLI は `orca-flow` で呼ぶ（プラグインの bin が PATH に入っている）。見つからなければ `"${CLAUDE_PLUGIN_ROOT}/bin/orca-flow"` で呼ぶ。終了コードは 0＝成功、1＝失敗、2＝人間か統括役の作業が先に要る、3＝git の競合。

## 手順（人が打ったとき）

1. 引数が空なら、`orca-flow auto` で一覧（おまかせのタスク・前を待つタスクと前ごとの整い具合と先の承認・番・待ち受けが動いているか）を出して人間に伝える。前を待つタスクの行の「おまかせを外してあります（/orca-flow:approve で承認）」は、おまかせを外した印のタスクのうち、作業中で、最後の spec-review のあとに承認がないものだけに出る（承認したあとは出ないので、もう一度 approve を勧めない）。`--json` の `off` は、作業中か承認したかによらずおまかせを外してあれば真なので、承認を勧めるかの見分けに使わない。`auto on 〈ID〉` が、印が壊れた・前が読めないときに記録の絶対パスと「/orca-flow:approve で今承認できます」を出したら、待っても承認の番は立たないので、そのとおり人間に伝える。一覧に「拾われました」の番があり、そのタスクが進んでいなければ（カードがその番の状態のまま）、拾われたあとで扱われなかったので、`orca-flow auto on 〈ID〉` で番を立て直してから手順3へ。待ち受けが動いていなければ、手順3へ。
2. 引数があれば、そのまま CLI に渡す（`--reason` の文や `log` の文は一重引用符で囲み、中の ' は '\'' にする。バッククォートや $(…) をコマンドとして動かさないため）：`orca-flow auto 〈引数〉`（`off 〈ID〉`・`off 〈ID〉 --reason 〈文〉`・`off --all`・`show 〈ID〉`・`on 〈ID〉`）。出力と終了コードを人間に伝える（`show 〈ID〉` は前を待つ印と前ごとの整い具合も出す。`off 〈ID〉`・`off --all` は前を待つ印を消さず、印のタスクの自動の承認を止める（おまかせを外した形の記録を残す。印だけのタスクにも書く。`--all` は作業中の印のタスクにも当てる。先の承認も消す）ので、そのタスクは前が整っても承認の番が立たず、人が `/orca-flow:approve` で承認すると人に添える）。終了コード2はメッセージのとおりに伝えて止まる（統括役の場所でない、など）。自分で直さない。おまかせを外したあとも、残りのおまかせのタスクか前を待つタスクがあれば手順3へ。
3. 待ち受けを背景で始める：`orca-flow auto wait` を Bash の run_in_background で流す。終了コード2はほかの待ち受けがもう動いているので、何もしない。

## 番が来たら

背景の `orca-flow auto wait` が終わると、出力に ID・番（承認か統合）・次にすること（このファイルのパスを含む文）が出る。終了コード0で番が空（`--json` なら番が null）のときは、おまかせのタスクも前を待つタスクもなくなった（乗せた先が作業中の乗せたタスクもない）か12時間たったので、何もしない（どれかが残っていれば手順3で流し直す）。承認が済んだあとの、印だけか承認だけのおまかせのタスクは、残っていても数えない（統合は人が `/orca-flow:integrate` で行うため）。

1. ほかの手順（new・approve・integrate など）の途中なら、それを終えてから扱う。
2. `orca-flow active` で、その ID のカードの状態が番と合うかを確かめる。承認の番なら設計書のレビュー待ち（spec-review）、統合の番なら統合待ち（integrate-wait）。違えば（すでに承認・統合された、おまかせが外れた、カードが取れない、など）、承認も統合もしない（二重にしない）。人間に1行伝える：「〈ID〉 のカードは 〈今の状態〉 で、〈承認か統合〉の番と合いません。進めるなら `/orca-flow:approve`（統合なら `/orca-flow:integrate`）を打ってください。カードが戻ったら `orca-flow auto on 〈ID〉` で番を立て直せます」（`orca-flow active` でカードが取れないときは、状態を「取れません」とする）。そのあと手順5へ。
3. 承認の番なら `${CLAUDE_PLUGIN_ROOT}/skills/approve/SKILL.md`、統合の番なら `${CLAUDE_PLUGIN_ROOT}/skills/integrate/SKILL.md` を読む。その手順を、ID を `$0` として、そのファイルの「おまかせの決まり」で行う（approve と integrate は `disable-model-invocation` なので、ファイルを読んで行う。integrate が new の手順を読むのと同じ形）。
4. 止まったとき（人に聞く所・終了コード1・2・3など）も、人間にそのとおり伝える。
5. 終わったら、止まったときも含めて、待ち受けを流し直す：`orca-flow auto wait` を背景で流す（終了コード2は何もしない）。

## 守ること

- タスクの worktree の中のファイルを、統括役のタブから書き換えない。
- 番で後続のタスクを作るときは、`--auto` をつけない（人の知らないまま後続が後続を生み続けないため）。後で `/orca-flow:auto on 〈ID〉` でおまかせにできると人に添える。
- push はしない。
- send は打たない（`/orca-flow:send` と `orca-flow send` は人間が許可の画面で承認する。おまかせでも飛ばさない）。
- マージはしない（マージは `/orca-flow:merge`。`gh pr merge` と `orca-flow merge` を流さない。おまかせでも人間が打つ）。
