あなたは統括役として、タスク $0 の設計を承認する。人間が設計書を読んで、よいと判断したあとに呼ばれている。

CLI は `orca-flow` で呼ぶ（プラグインの bin が PATH に入っている）。見つからなければ `"${CLAUDE_PLUGIN_ROOT}/bin/orca-flow"` で呼ぶ。終了コードは 0＝成功、1＝確認に落ちた・失敗、2＝人間か統括役の作業が先に要る、3＝git の競合。

重なりの question（タスク長が `orca-flow status question --note "〈ID〉 と重なる"` で止まったこと。overlap が自動で順に足せなかったとき。つなぐ鎖で統合済みの項目が未統合の項目の後ろにあるときなど）を持ち込まれたときは、手順1〜4を流さず、下の「重なりを自動で決めきれなかったとき」の節へ進む（人が `/orca-flow:approve 〈ID〉` で持ち込んでも、設計中のタスクを承認しない）。

## 手順

1. `orca-flow config --json` で設定を読む（tasksDir・verify・integratorName）。`orca-flow active` で $0 のブランチを調べる。
2. タスクのブランチの設計書を読む：`git show 〈ブランチ〉:〈tasksDir〉/$0.md`。設計書が無視されていれば（タスクの worktree で `git check-ignore -q 〈tasksDir〉/$0.md` が成功する。worktree のパスは `orca-flow active` で分かる）コミットされていないので、無視されていればファイルを読む：`〈タスクの worktree〉/〈tasksDir〉/$0.md`。以降の「設計書の blob」は、無視されていなければ `git rev-parse 〈ブランチ〉:〈tasksDir〉/$0.md`、無視されていれば `git hash-object -w 〈タスクの worktree〉/〈tasksDir〉/$0.md` の値にする（ブランチの blob と同じ値。-w で blob を保存するので、あとで `git show 〈blob〉` で読める。どこからも参照されないので push されない）。
   - 人間が承認のとき、設計書の「要点」の「決めてほしいこと」や文案の「人が選んだこと」に、設計書と違う答え（選び直し・足した指示）を言ったときは、承認の前に設計書を直させる。`orca-flow tell $0 "〈直し方〉。設計書を直してコミットし（無視されていればコミットしない）、spec-review に戻して"` を流し、戻ったと言われたら、この手順の1から読み直す。設計書が人の答えと違うまま承認しない（run と決定の記録の項は設計書を正として進むため）。答えのなかった決めてほしいことは直さない（run が項の「人が選んだこと」に、人の承認なら「おすすめどおり（承認で決まった）」、おまかせなら「おすすめどおり（おまかせで統括役が決めた）」と書く）。
3. 「main への事前変更」を見る。
   - 「なし」なら：`orca-flow approve $0` を流す。
   - 変更があれば：まず `git log main --first-parent --format='%s%x09%H'` で、main の first-parent のコミット（マージで入ったタスクのコミットは除く）を、件名を行の頭に出して探す。正規表現 `^〈integratorName〉: $0 の事前変更` は、件名（行の頭）に当てる。当たるものが2つ以上なら、いちばん上（いちばん新しい）ものを使う。
     - 見つかったら、「〈integratorName〉: $0 の事前変更」のコミットがすでにある。本文は `git show -s --format=%b 〈ハッシュ〉` で読み、その「設計書：〈blob〉」の行と、今の設計書の blob（`git rev-parse 〈ブランチ〉:〈tasksDir〉/$0.md`。無視されていれば `git hash-object -w 〈タスクの worktree〉/〈tasksDir〉/$0.md`）を比べる。
       - blob が同じなら、入れ直さず `orca-flow approve $0 --prechanges-done` を流す（手順4へ）。
       - blob が違えば、2つの blob（`git show 〈blob〉`）の「main への事前変更」の節を比べる。節が同じなら、入れ直さず `orca-flow approve $0 --prechanges-done` を流す（手順4へ）。
       - 節が違うか、本文に「設計書：」の行がない（古いコミット）なら、入れ直さず人間に、前の事前変更と今の事前変更の差を見せて、どうするか聞いてから進める。
       - 前の blob が `git show 〈blob〉` で読めない（gc など）とき、〈blob〉が16進の形でないときも、同じく入れ直さず人間に聞く。
     - 見つからなければ、統括役が main で行う。
     1. 書かれたとおりに共有のファイルを変える。書き方があいまいで決めきれないときは、人間に聞いてから行う。ロックファイルは手で直さず、パッケージマネージャーで作り直す。
     2. config の verify のコマンドを順に流し、すべて通ることを確かめる。落ちたら直す。直せなければ人間に伝えて止まる。
     3. 変えたファイルだけを `git add` し、`〈integratorName〉: $0 の事前変更（〈要点〉）` でコミットする。本文に「設計書：〈blob〉」の1行を入れる（〈blob〉は `git rev-parse 〈ブランチ〉:〈tasksDir〉/$0.md` の値。無視されていれば `git hash-object -w 〈タスクの worktree〉/〈tasksDir〉/$0.md` の値。-w でないと blob が保存されず、あとで `git show 〈blob〉` で読めない）。
     4. `orca-flow approve $0 --prechanges-done` を流す。
4. 終了コードごとに次をする。
   - 0：人間に「$0 の実行を始めました。統合待ちになったら未読の印がつきます」と伝える。
   - 2：メッセージ（統括役の場所でない、事前変更が済んでいない、タスク長のターミナルが1つに決まらない、タスク長の入力欄に打ちかけがある、タスク長のターミナルが bash モードになっている、タスク長の入力欄を確かめられない、など）を人間に伝え、何をすればよいかを添えて止まる。標準エラーに「送れませんでした」が入るときは、CLI が出した送れなかった文と候補のタブ（題名とハンドル）をそのまま伝え、入力欄に打ちかけなら、その文を送るか消してもらい、直ったら下の流し直しをする。
   - 2 で、標準エラーに「main を書き換えています」が入る（「〈相手〉が main を書き換えています（ロック：〈パス〉）」。相手は integrate・push の道の後始末・approve・new のどれか、種類のない古いロックは「別の処理」。何も変えずに止まっている）：CLI の文を人間にそのまま伝え、少し待ってもう一度 `/orca-flow:approve $0` を打つよう伝える。ロックが残ったままのときは、文のロックのパスのファイルを、持ち主の処理がもう動いていないと確かめてから消してもらう。自分では消さない。
   - 終了コード2で止まったあと（`--prechanges-done` で流していたときも、「なし」で流していたときも）：人間が原因（打ちかけ、bash モード、入力欄を確かめられない、など）を直したと言ったら、スキルを打ち直してもらわず、前と同じ引数で CLI を流し直す。`--prechanges-done` で流していたなら、事前変更はすでに main に入っているので入れ直さず、`orca-flow approve $0 --prechanges-done` を流し直す。「なし」なら `orca-flow approve $0` を流し直す。approve は送る直前にもう一度入力欄を確かめるので、取り込みと進捗表のコミットのあとでも終了コード2になりうる。流し直せば続きから進む。
   - `orca-flow tell` を流して終了コード2が返ったとき（見つからない・1つに決まらない・打ちかけ・bash モード・入力欄を確かめられない）：CLI が出した送れなかった文と候補のタブを人間に伝えて止まる。
   - 3：取り込みが競合した。`orca-flow tell $0 "git merge 〈baseBranch〉 をして競合を直し、spec-review に戻して"` を流し、人間に「$0 のタスク長に競合を直すよう伝えました。spec-review に戻ったら続けます」と伝えて止まる。人間が戻ったと言ったら、前と同じ引数で CLI を流し直す（`--prechanges-done` で流していたなら事前変更は入れ直さない）。
   - 1：メッセージ（設計書がコミットされていない、タスクの worktree に未コミットの変更がある、確認に落ちた、など）を人間に伝えて止まる。

## おまかせの決まり

`/orca-flow:auto` の番が来て、おまかせのタスク $0 を承認するときの決まり（人が `/orca-flow:approve` を打ったときは、この節を使わず、上の手順のまま）。人の確認を飛ばす代わりに、次の所では止まって人間に聞く。

1. 設計書の「決めてほしいこと」の項目は、推奨どおりにする。推奨がない項目、統括役が読んで推奨が決めきれない項目が1つでもあれば、承認せずに止まり、人間に聞く。
2. 「main への事前変更」に大事な共有のファイル（`.claude/` の下（CLAUDE.md を除く）・`.orca-flow/` の下・`orca.yaml`・`package.json`・`.worktreeinclude`）があれば、手順3の変更を main で行ったあと、コミットの前に、変える中身（追跡中のファイルは `git diff`、新しいファイルは中身全体）を本文に出し、AskUserQuestion で「入れる」「止める」を聞く。「止める」なら、変えたファイルを戻し、新しく足したファイルも消して、承認せずに止まる。「入れる」の前に verify を流さない。ほかの事前変更は、今の手順のまま聞かずに入れる。
3. 決めたことは、1項目ずつ `orca-flow auto log $0 '〈決めたこと〉'` に残す（一重引用符で囲み、中の ' は '\'' にする。設計書から写した文のバッククォートや $(…) をコマンドとして動かさないため。例：「決めてほしいことの1は推奨どおり：〈推奨〉」）。
   - 決めてほしいことを推奨どおりにした決めは、`orca-flow approve` が終了コード0で終わったあとに、「承認：」で始めて `auto log` に残す（例：`orca-flow auto log $0 '承認：決めてほしいことは推奨どおり'`）。承認できなかったとき（終了コードが0でないとき）は残さない。run は、これがあれば承認がおまかせだったと見分け、項の「人が選んだこと」に「おすすめどおり（おまかせで統括役が決めた）」と書く（今おまかせかどうかでは見分けない）。
4. 人への伝え方（手順4の0の文）に、決めたことを並べ、`orca-flow auto show $0` で読み返せると添える。
5. 後続のタスクを作るときは `--auto` をつけない。
6. 止まったときは、聞いた内容を人間に伝える。答えを受けたあとは、人が `/orca-flow:approve $0` を打つ（おまかせの番は拾われ済みで返らない）。
7. 手順4の終了コード2と3で人間に伝える「直したと言って」「戻ったら続けます」の文は、おまかせでは使わない。終了コード3（競合）は、タスク長が直してカードが spec-review に戻れば番が立ち直り、統括役が続けます（人は打たなくてよい）と伝える。終了コード2（入力欄の打ちかけ・bash モード・入力欄を確かめられない、など）はカードが動かないので番は立ち直らない。原因を直したら、統括役のタブで `/orca-flow:auto` を打ってください（拾われたまま進んでいない番を立て直して続けます）と伝える。前と同じ引数での流し直しも、人が言ったときではなく、番が来たときに行う（番が来る前に流し直さない。run の途中のタスク長に /clear が送られうるため）。

## 重なりを自動で決めきれなかったとき

重なりだけが問題なら、設定 `autoOrderOnOverlap` が true（既定）のとき overlap が自動でマージの順に足す（重なる鎖は1本につないで足すので、鎖にいない相手や別々の鎖の相手とも止まらない。自動で足せたとき、タスク長は question で止まらず、統括役の仕事はない。順は `orca-flow order` と `orca-flow active` で時刻つきで読め、順を変えたいときは統括役のタブで orca-flow order を足し直す）。この節に来るのは、自動で決めきれなかったとき。つまり、タスク長が `orca-flow status question --note "〈ID〉 と重なる"` で止まったこと（つなぐ鎖が2つ以上で、未統合の項目の後ろに統合済みの項目がある鎖があるとき。または設定が false）が統括役に届いた（人間が持ち込んだ）とき。統括役が順を決めれば、前のタスクの統合を待たずに並行で進められる。

1. 重なるタスクの設計書とブランチの差分を読み、どちらを前のタスクにするかを決める（先に入れたいほうを前に置く）。`orca-flow order` で今の鎖を見る。1つの ID は1つの鎖にだけ入る。すでに鎖にいる ID を含めるなら、その鎖を全部含めて伸ばす（統合済みの ID は作業中でなくてよく、前に置く。例：T12（統合済み）→ T14 のとき `order T12,T14,T15`）。
2. 人間に確かめず、統括役が決める。鎖の並び（例：T12 → T14 → T15）と理由は、流したあとで人間に伝える（手順3・4のあとでよい）。
3. `orca-flow order 〈ID〉,〈ID〉,…`（前のタスクから順に）を流す。終了コード1（作業中でない ID・重複・一部だけ重なる鎖）は、メッセージのとおりに直す。
4. 止まっているタスク長に `orca-flow tell 〈ID〉 "overlap を流し直して進めて"` を流す（タスク長は overlap の警告で前後を読める）。終了コード2は、手順4と同じに人間に伝えて止まる。

## 守ること

- タスクの worktree の中のファイルを、統括役のタブから書き換えない。
- push はしない。
