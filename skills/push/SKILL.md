---
name: push
description: 統合待ちの orca-flow のタスクのブランチを確かめ、push と PR の作成を案として積んで見せる（送らない）。PR の本文を書いて orca-flow push に渡す。送るのは人が承認した /orca-flow:send、マージは人が打つ /orca-flow:merge。統括役のタブ（メインのチェックアウト）で人間が打つ。
argument-hint: "[ID]"
disable-model-invocation: true
---

あなたは統括役として、タスク $0 のブランチの push と PR の作成を、案として積んで人間に見せる。人間が報告と差分を読んで、よいと判断したあとに呼ばれている。integrate のかわりの道で、手元の main にはマージしない。このスキルは GitHub にも origin にも書かない（`orca-flow send`・`gh`・`git push` を流さない）。書くのは、人間が見て承認した `/orca-flow:send` だけ。

CLI は `orca-flow` で呼ぶ（プラグインの bin が PATH に入っている）。見つからなければ `"${CLAUDE_PLUGIN_ROOT}/bin/orca-flow"` で呼ぶ。終了コードは 0＝成功、1＝確認に落ちた・失敗、2＝人間か統括役の作業が先に要る（push では git の競合の 3 は出ない）。

## 手順

1. `orca-flow config --json` で設定を読む（reportsDir・decisionsFile・baseBranch。prReady は読まない）。`orca-flow active` で $0 のブランチとタスク名を調べる。
2. 報告を読む：`${CLAUDE_PLUGIN_ROOT}/skills/integrate/SKILL.md` の手順2と同じ（`git show 〈ブランチ〉:〈reportsDir〉/$0.md`。報告が無視されていればタスクの worktree のファイルを読む）。
3. PR の本文を書く。
   - pstack の手引きを `orca-flow pstack skills/poteto-mode/playbooks/opening-a-pr.md --json` で1回だけ引く（入手元の確かめは CLI がする）。終了コード0なら、`harness` があれば先に読み、`file` の手引きを絶対パスで読む。opening-a-pr の6つの節に従い、見出しはそのまま、中身は日本語で書く。ほかの pstack のスキルは読まない。
   - 終了コードが0以外なら、手引きを読まずに飛ばして、短い形（変わること・テストの結果・人が見てほしいところ）で書く。人間に「pstack なし」で書いたことと、CLI の標準エラーの理由の1行を伝える。
   - 終了コード0でも `--json` の `warning` が null でなければ（別の入手元の同名の pstack も有効、など）、その1行を人間に伝える（読むのは `file` だけ）。
   - opening-a-pr の指示は、この定義の禁止より優先しない。opening-a-pr がどう書けと言っても、下の禁止を守る。
   - 本文の材料は、報告・差分・コミットのメッセージ。本文に設計書と報告のパス、手元のパス（ホームの下のパス、worktree のパスなど）、秘密（トークン・鍵・.env の値）を書かない。件名と本文の ID とタスク名は書いてよい。報告の「人間に決めてほしいこと」などを写すときも、パスを外す。
   - 本文は `mktemp -d` で作った一時ディレクトリの中のファイルに書く。終わったら一時ディレクトリを消す。
4. `orca-flow push $0 --body-file 〈本文のファイル〉` を流す。流すのはこれだけで、push も PR の作成もしない（案を積んで、本文・先頭・束の指紋を出して止まる）。`--body-file` の相対パスは、orca-flow を打った場所から解かれる（絶対パスで渡すのが確か）。2回目の push で PR がすでにあるときは、本文は使われない（なければ省いてよい）。PR がまだないのに本文がなければ終了コード1になる。先頭が変わっていない2回目の push（手元の先頭・記録の push した先頭・GitHub の先頭・記録の PR が揃っているとき）は、確かめも push もせず、開いた PR が下書きなら `pr-ready` の案（下書きを外す）だけを積んで束を出し（このときは終了コード0の束と同じに扱う）、下書きでなければ見張りの案内だけを出して、main が進んでいても止まらない。開いた PR がないか下書きでないときは、push が積んだままの `pr-ready` の案を取り下げる。マージ済みの PR は、ほかの確かめより前に見つけて後始末をやり直す（手元の main が進んでいても、手で取り込んでマージ済みになっていても、push の記録があれば届く）。フォークからの PR はタスクの PR として扱わない。終了コードごとに次をする。
   - 0：案が積まれた。手順5へ。「見張りが後始末をしています」「ほかの push が後始末をしています」「古い待ち受けが後始末をしています」のどれかで終わったときは、PR はすでにマージ済みで、後始末の途中（見張りの背景・2回目の push・置き換え前に起こした古い待ち受けの順）。終わるまで待つよう人間に伝え、手順5・6は後始末のあとに回す（様子は `--show`）。
   - 1：範囲外のファイル、決定の記録の抜け・書き換え、テストの失敗、タスクの worktree に未コミットの変更がある、報告がない、本文がない、PR の本文にリポジトリ・ホーム・worktree・設計書・報告のパスや秘密らしい値が含まれる（CLI は当たった種類だけを出す。本文から消して push し直す）、など。`${CLAUDE_PLUGIN_ROOT}/skills/integrate/SKILL.md` の手順3の終了コード1と同じに扱う（標準エラーから直し方を決め、`orca-flow tell $0 "〈直し方〉。直したら報告を直し、orca-flow verify を流して integrate-wait に戻して"` を流し、人間に伝えて止まる）。ただし本文の問題は自分で本文を直して push し直す（タスク長に頼まない）。
   - 2：CLI の文を人間に伝え、何をすればよいかを添えて止まる。integrate のスキルの手順3の終了コード2の段には飛ばない（`--skip-order`・`--skip-decision` は push にないので使わない）。文ごとの扱いは次。
     - 「マージの順」：先に統合すべきタスクがある。人間に伝え、順を外すなら `orca-flow order --remove` を案内する。
     - 決定の記録に止まったとき：タスクのブランチで決定の記録に項を足してコミットしてもらい（`orca-flow tell`）、足してからもう一度 push する。
     - `orca-flow verify` の文字が入るとき、または、タスクのブランチが baseBranch の先頭を含まないとき：CLI がタスク長に「main を取り込んで verify をやり直し、integrate-wait に戻して」を送っている（`orca-flow tell` は送り直さない。警告に「送れませんでした」が入っていたら、人間から伝えてもらう）。
     - 「〈相手〉が main を書き換えています（ロック：〈パス〉）」（相手は integrate・push の道の後始末・approve・new のどれか、種類のない古いロックは「別の処理」。何も変えずに止まっている）：CLI の文を人間にそのまま伝え、少し待ってもう一度 `/orca-flow:push $0` を打つよう伝える。ロックが残ったままのときは、文のロックのパスのファイルを、持ち主の処理がもう動いていないと確かめてから消してもらう。自分では消さない。
     - マージ済みの PR の後始末が止まったとき：止まった理由を人間に伝え、手順6の「後始末で止まった」と同じに、原因を直してからもう一度 push を打つよう伝える。
     - `gh` が見つからない・ログインしていないときは、`gh auth login` が要ることを伝える（トークンの値は出さない）。統括役の場所でない、も同じに伝える。
   - 3：push の CLI は出さない。出たら CLI の文をそのまま人間に伝えて止まる。
5. 報告の3つの節（「共有のファイルの変更の依頼」「人間に決めてほしいこと」「後回しにしたもの」）を、`${CLAUDE_PLUGIN_ROOT}/skills/integrate/SKILL.md` の手順4と同じに扱う（一覧・推奨・後続のタスク・共有のファイルの変更・決定の記録の項）。ただし push のあとなので、main で行う変更とコミットは、PR のマージのあとに main に入る。「main で今変える」を選んだ項目は、今は変えず、マージのあとにやることとして人間に伝える。決定の記録の項を main に足すのも、マージのあとにする。
6. 人間に次を伝える。
   - 案を積んだこと（push・PR の作成。開いた PR が下書きなら「下書きを外す」の案も一緒に。PR の本文を pstack の形で書いたか「pstack なし」の短い形で書いたか）。まだ GitHub にも origin にも書いていないこと。カードが「送る前の確認待ち」になったこと。
   - CLI が出した本文・先頭・束の指紋を、省かずに見せる。履歴を書き換えたあと（手で rebase したときなど）なら、期待値（`--force-with-lease`：リモートがこの先頭のときだけ上書きする）も見せる。
   - 人間が確かめて承認するなら `/orca-flow:send $0` を打つ（send が束の指紋と先頭で照らし、許可の画面で承認してから push と PR の作成をする。PR は下書きでない形で出る）。本文や先頭を変えたいときは、直してからもう一度 `/orca-flow:push $0`（積み直すと前の案は取り下げになる）。自分では送らない。
   - PR は下書きでない形で出るので、CI のあとに下書きを外す仕組みはない（設定 `prReady` は書いてあっても読み飛ばす）。前に出した下書きの PR は、開いた PR が下書きのとき push が「下書きを外す」の案（`pr-ready`）を積んでいて、send で承認すると外れる。CODEOWNERS があるリポジトリでは、PR を出した時点で GitHub がコードオーナーにレビューを頼む（orca-flow は頼まない）。
   - 送ったあとの話：マージは `/orca-flow:merge`（人が統括役のタブで打つ。カードが「マージ待ち」になったら）。GitHub の画面からマージしない。自分では `gh pr merge` も `orca-flow merge` も流さない。マージのあとの後始末（main の取り込み・統合済みの印・ほかのタスクへの知らせ・worktree の片付け）は `/orca-flow:merge` が続けて行う。リポジトリごとに1つの見張り（Orca の automation。5分おき）が後始末をするのは、画面からマージされたときと、後始末が止まったときだけ。
   - 「見張りの automation がない」と CLI が案内したとき（`taskEnd` が `"pr"` でも `"integrate"` でも）：このままだと PR は見張られない。人間に、統括役のタブで `orca-flow pr-watch install` を打って automation を作るよう伝える（`init --yes` が作るのは `taskEnd` が `"pr"` のときだけ。自分では作らない）。Orca の画面の「今すぐ実行」は押さないよう伝える（precheck を飛ばして worktree と会話が1つ増える）。「見張りの automation があるか確かめられません」と出たときは、push を打ち直さず、Orca を起動してから統括役のタブで `orca-flow pr-watch install` を打つよう伝える（automation があれば今の中身に直すだけ）。
   - 「見張りの automation が落ち続けています」と CLI が出したとき：見張りが動いていない。その文（Orca が流した時刻と、pr-watch の回の記録の時刻、直し方）をそのまま人間に伝える。直し方が `orca-flow pr-watch install` の打ち直しなら統括役のタブで打ってもらい、precheck の出力を読む直し方なら `orca automations runs` の結果を人間に見てもらう（自分では直さない）。
   - 様子は `orca-flow push $0 --show` で見られる（送ったあとから）。Orca のカードには「CI 待ち」「レビュー待ち」「CI が落ちた」「後始末で止まった」「PR が閉じられた」が PR の番号つきで出る（「待ち受けが止まった」は置き換え前の待ち受けの名残で、見張りは出さない。見張りの失敗は `orca-flow pr-watch usage` で見る）。「後始末で止まった」のときは、原因（main でない・未コミットの変更・競合・手元のタスクのブランチにだけあるコミットがある（GitHub の上で足された提案は取り込まれて続く）・タスクの worktree に未コミットの変更・取り込むと decisionsFile の手元の行が取り込んだあとの先頭に残らない（merge=union が最後の共通の行を1つにまとめて消した。取り込みは戻してあり、文に「手元の行が取り込んだあとの先頭に残りません」が入る。メインのチェックアウトで origin をマージし、手元の行のあとに origin の足した項が続く形に戻して、見出しの前に空行を入れてコミットする）を直してから `/orca-flow:push $0` をもう一度打つ。見張りの様子（回数・点数・最後に成功した時刻・失敗の理由）は `orca-flow pr-watch usage` で見られる。「PR が閉じられた」のときは、人がマージしないと決めたものなので、後始末はされていない。この先は、直して `/orca-flow:push $0` を打ち直すか、`/orca-flow:integrate $0` で手元の main に統合するかを人が選ぶ（おまかせは、このカードを統合の番にしない）。ただしまたぐ依存の記録があるタスクは、integrate が終了コード2で止まるので、`/orca-flow:push $0` の打ち直しだけにする。
   - 終了コード0でも、CLI の警告があれば人間にそのまま伝える。
   - 手順5の残り（「後で決める」「今は決めない」「後回しにしたもの」の1行ずつ）。

## 守ること

- `orca-flow send`・`gh`・`git push` を流さない。GitHub に書くのは、人間が見て承認した `/orca-flow:send` だけ。
- 本文に、設計書と報告のパス、手元のパス、秘密を書かない（CLI も本文を確かめ、含まれていれば止める。それでも書かない）。
- baseBranch へ push しない。ブランチは消さない。マージはしない（マージは `/orca-flow:merge`。`gh pr merge` と `orca-flow merge` を流さない）。
- タスクの worktree の中のファイルを、統括役のタブから書き換えない。直しはタスク長に `orca-flow tell` で頼む。
- レビューのコメントを拾って直すことはしない（この道にはない）。
