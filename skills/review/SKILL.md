あなたはタスク $0 のタスク長として、差分にコードレビューをかける。自分では指摘を探さず、レビュー役と検証役に割り振り、結果をまとめる。

差分の範囲：$1（2つ目の引数がなく、ここが空か、ドル記号と数字のままなら、`〈baseBranch〉...HEAD`）

設定の `reviewBackend` が `local` のときは、下のClaudeのレビュー役・検証役の手順を使わず、`orca-flow review-local` を1回呼ぶ（最初の形は `first`、やり直しの形は `redo`。`--json` で受け取り、must-fixと報告を返す）。`full` の周回（1段目5周・2段目3周）と `light` の1周は run が決める。このスキルは1周分だけを返す。codeReview が off のときは今までどおり止める。ローカルが失敗したときは、run が設定の `fallback` に従う（このスキルではClaudeのレビュー役を勝手に起動しない）。

形：$2（3つ目の引数が「やり直し」のときだけ「やり直しの形」。「見直し」のときは「見直しの形」（下の「見直しの形」の節）。それ以外（空や、ドル記号と数字のまま）は「最初の形」）

CLI は `orca-flow` で呼ぶ（プラグインの bin が PATH に入っている）。見つからなければ `"${CLAUDE_PLUGIN_ROOT}/bin/orca-flow"` で呼ぶ。終了コードは 0＝成功、1＝確認に落ちた・失敗、2＝人間か統括役の作業が先に要る、3＝git の競合。

ブランチを切り替えない。メインのチェックアウトを変更しない。このスキルの中ではファイルを変更しない（直すのは run の手順に戻ってから）。Orca のカードの状態と comment は変えない（run が review を呼ぶ前に一言を流す。人間が統合待ちのタブでこのスキルを打ってもカードを壊さないため）。

## 5つの観点

観点の名前と、主に見ることの一言の一覧。詳しくはレビュー役の定義（`orca-flow:code-reviewer`）に書いてある。

| 観点         | 主に見ること                                             |
| ------------ | -------------------------------------------------------- |
| 正しさ       | 論理の誤り、境界と異常系、呼び出し元への影響、並行の競合 |
| セキュリティ | コマンドの組み立て、パスの扱い、秘密の値、入力、依存     |
| 設計         | 責務の分け方、既存コードの再利用、一貫性、仕様との整合   |
| テスト       | 抜けた場合、弱い確かめ、壊れやすさ、偽物の使い方         |
| 運用と互換性 | 失敗時の後始末とメッセージ、性能、今の利用者を壊さないか |

整形と好みの問題は扱わない（lint が見る）。設計書との照合と範囲の確認は、確認役（reviewerAgent）が見る。

重さは確認役と同じ3つ：「必ず直す」「直したほうがよい」「確認だけ」。このタスクで入れたものではない問題は「前からある」と印をつける。「前からある」の基準は、やり直しでもいつも `〈baseBranch〉...HEAD`（タスク全体の差分）で、そこに入っていないものだけを「前からある」とする。

## 小さな差分

小さな差分のしきい値：変わった行の数（`git diff --numstat 〈範囲〉 -- ':/' ':(top,exclude,icase)*.md'` の足した行と消した行の合計。拡張子が .md のファイル（大文字・小文字を問わない）の行は数えない。バイナリのファイルは数えない）が 300 行まで。

しきい値はここだけに書く。手順ではこの名前で指す。

md も今までどおりレビューする。変わるのはレビュー役の数だけ。md だけの差分は、手順1の「差分なし」にはならず、数えると0行なので、レビュー役1つと検証役1つで流れる。

## codeReview（コードレビューの設定）

設定の `codeReview` が、このスキルの動きを決める。値は3つ。やり直しの形で呼ばれても、run の外で呼ばれても、同じに従う。

- `full`（既定。書かれていないときも）：このあとの手順のとおり（しきい値で1つか5つ、検証役1つ）。
- `light`：しきい値によらずレビュー役を1つだけ起動し（5つの観点を全部見させる）、検証役を起動せず、全部の指摘を「たぶん」として「報告に書くもの」に回す（直させない。検証役が未実施のときと同じ扱い）。件数には「軽くする設定（codeReview: light）で検証役なし」と書く。やり直しの形のときは、何も起動せず「軽くする設定のため、やり直しの確かめはしない」と返して終わる。
- `off`：レビュー役も検証役も起動せず、「設定（codeReview: off）でコードレビューを止めている」と返して終わる。報告の「コードレビュー」の節には「設定で止めている」と書く。

確認役（reviewerAgent）は、codeReview によらず run が動かす。このスキルが決めるのはコードレビューだけ。

## 文書だけ（軽く回す）

設計書で「文書だけ」としたタスクは、codeReview が full のとき、検証役を呼ばずに軽く回す。

見分け方：次の全部に当たるときだけ文書だけとする。1つでも外れたら、今までどおりの full で回す。

- 設計書の要点に `- コードレビュー：文書だけ（軽く回す）` の行がある（この文字のとおり）。
- codeReview が full（書いていないときも）で、reviewBackend が claude（ローカルは Opus を使わないので今のまま）。
- `git diff --name-only --no-renames 〈baseBranch〉...HEAD` のファイルが全部、拡張子 .md（大文字・小文字を問わない。小さな差分のしきい値と同じ数え方）。
- どのファイルも sharedPaths と pathVerify の場所に当たらない（CLAUDE.md やスキルの定義を軽くしないため）。
- 判定はやり直しの形でも、いつも `〈baseBranch〉...HEAD` でし直す。

軽い回し方（最初の形）：手順3〜5の代わりに、次のとおりにする。

- レビュー役（`orca-flow:code-reviewer`）を1つだけ背景で起動し、5つの観点を全部見させる。検証役は起動しない。
- レビュー役の「必ず直す」「直したほうがよい」（「前からある」を除く）は、「タスク長が確かめるもの」として返す（run が根拠を開いて確かめる）。「確認だけ」と「前からある」は「報告に書くもの」に回す。
- 件数に「文書だけ（検証役なし）」と書く。
- 確認役はいつもどおり動く（文書だけでも止めない）。

秘密と個人のパスの確かめ：`git diff --no-color 〈baseBranch〉...HEAD | grep -E '^\+(.*[^A-Za-z0-9_.~-])?(/(Users|home)/[A-Za-z0-9._-]+([^A-Za-z0-9._-]|$)|(ghp_|github_pat_|sk-|xox[bap]-)[A-Za-z0-9_-]{20,}|AKIA[0-9A-Z]{16})|^\+.*([A-Za-z0-9._%+-]+@[A-Za-z0-9-]+\.[A-Za-z]{2,}|-----BEGIN [A-Z ]*PRIVATE KEY-----)'`

- 文書だけのとき、足した行をこのコマンドで探す（ホームの絶対パス、メールアドレス、秘密鍵の頭の行、よくあるトークンの頭）。出た行は「確か」の「必ず直す」として「直させるもの」に入れる。
- 作り物の例とはっきり分かる当たり（example.com など）は、直させず、理由を添えて「報告に書くもの」に回す。

やり直しの形（文書だけ）：何も起動せず、秘密と個人のパスの確かめだけを流し直して返す（当たりがあれば「直させるもの」に残す。前の回の「タスク長が確かめるもの」は run が確かめた結果のとおりに扱う）。

## テストだけ（観点を絞る）

設計書で「テストだけ」としたタスクは、codeReview が full のとき、正しさとテストの2つの観点に絞って回す。テストの誤りは論理の誤りと弱い確かめに出て、秘密とパスは機械の確かめで止められるため。

見分け方：次の全部に当たるときだけテストだけとする。1つでも外れたら、今までどおりの full で回す。

- 設計書の要点に `- コードレビュー：テストだけ（観点を絞る）` の行がある（この文字のとおり）。
- codeReview が full（書いていないときも）で、reviewBackend が claude。
- 文書だけに当たらない（文書だけの判定が先。両方に当たれば文書だけで回す）。
- 下の一覧のコマンドが終了コード0で、出力が空（`〈baseBranch〉...HEAD` の変わったファイルが、設計書と報告を除いて全部テストのファイル）。
- どのファイルも sharedPaths と pathVerify の場所に当たらない。
- 判定はやり直しの形でも、いつも `〈baseBranch〉...HEAD` でし直す。

テストのファイルの見分け方：どの階層でも、`test/`・`tests/`・`__tests__/`・`__snapshots__/` の下のファイルと、名前が `*.test.*`・`*.spec.*`・`*_test.*`・`test_*.py` のファイル。テストの助け（helpers）・fixtures・snapshot は、この場所の下にあればテストのファイルに入れる。外にある設定（例：vitest.config.ts）は入れない。秘密を置くファイル（`.env*`・`*.pem`・`*.key`・`id_rsa*`）は、テストの場所の下でも、名前が `*.test.*` でも、テストのファイルにしない（下の一覧に出す）。

テストでないファイルの一覧：`git diff --name-only --no-renames 〈baseBranch〉...HEAD -- ':/' ':(top,exclude,glob)**/test/**' ':(top,exclude,glob)**/tests/**' ':(top,exclude,glob)**/__tests__/**' ':(top,exclude,glob)**/__snapshots__/**' ':(top,exclude,glob)**/*.test.*' ':(top,exclude,glob)**/*.spec.*' ':(top,exclude,glob)**/*_test.*' ':(top,exclude,glob)**/test_*.py' ':(top,exclude)〈tasksDir〉/〈ID〉.md' ':(top,exclude)〈reportsDir〉/〈ID〉.md' && git diff --name-only --no-renames 〈baseBranch〉...HEAD -- ':(top,glob)**/.env*' ':(top,glob)**/*.pem' ':(top,glob)**/*.key' ':(top,glob)**/id_rsa*'`

- 終了コードが0で、出力が空ならテストだけ（0でなければ、テストだけにせず今までどおり回す）。2つ目のコマンドは、秘密を置くファイルをテストの場所の下でも必ず出すためのもの（同じファイルが2度出てもよい）。設計書と報告（`〈tasksDir〉/〈ID〉.md`・`〈reportsDir〉/〈ID〉.md`）は一覧から除く。移動は移動元も出す（`--no-renames`。テストでない場所からテストの場所への移動をテストだけにしないため）。

回し方（最初の形）：手順3〜5のとおりに、次を変える。

- 見る観点は正しさとテストの2つだけ（上の表のその2行を渡す）。小さな差分のしきい値まではレビュー役を1つで2つの観点を見させ、超えたら観点ごとに2つ並べて起動する。
- 検証役を起動する（full のまま。テストへの指摘は、テストを流して確かめないと誤りが混ざりやすいため）。渡すのは「必ず直す」「直したほうがよい」だけで、「確認だけ」と「前からある」は渡さない（通常の full と同じ）。直させるものの扱いも full のまま。
- 見ない3つの観点（セキュリティ・設計・運用と互換性）は、件数に「テストだけで絞った」と書く。「未実施」と書かない（未実施は統合の前に人に聞く扱いになるため）。
- 秘密と個人のパスの確かめ（テストだけ）：文書だけと同じコマンドを、指摘の有無によらず流し、当たりを「直させるもの」に入れる（作り物の例の扱いも文書だけと同じ）。

やり直しの形（テストだけ）：レビュー役は起動せず、検証役を起動し（手順7）、秘密と個人のパスの確かめも流し直す（当たりがあれば「直させるもの」に残す）。

## 見直しの形

マージの順にあるタスクが rebase したあと、タスク自身の変更が変わったときに、run が呼ぶ（run の「マージの順」の節）。コードレビュー全体は流さない。

- 3つ目の引数が「見直し」のときだけ。codeReview が `off` か `light` なら、何も起動せず「軽くする設定のため、見直しの確かめはしない」と返す（run はそのまま `--done` を流す）。
- レビュー役は起動せず、検証役1つ（`orca-flow:review-verifier`）だけを背景で起動する。
- 検証役に渡す：run が本文に書き出した `orca-flow rebase-review` の出力（ファイルごとの、前にだけある行・今にだけある行）、ID（$0）、設計書のパス、baseBranch、差分の範囲（$1。`〈baseBranch〉...HEAD`）、verify の結果。
- 検証役は、変わった所だけを確かめる。rebase の競合の直しで、タスクの意図が壊れていないか、前のタスクの変更とぶつかっていないか、足した行が消えたり重なったりしていないかを見る。変わっていない所は見ない。
- 返すのは「直させるもの」（「確か」の「必ず直す」）と「報告に書くもの」。件数には「見直し（検証役のみ）」と書く。run の出力の書き出しが見当たらなければ、そう伝えて止まる。
- 検証役が失敗した・決まった形で返さなかったときは、手順6と同じに扱う。それでもだめなら、変わった所を「確かめられなかった」として返す（run が人間に聞く）。

## 手順

1. `orca-flow config --json` で設定を読む（baseBranch・idPrefix・tasksDir・reportsDir・codeReview・reviewBackend・localReview・sharedPaths・pathVerify）。ID（$0）が 〈idPrefix〉〈数〉の形でない（空や、ドル記号と数字のまま）か、設計書 `〈tasksDir〉/$0.md` がなければ、そう伝えて止まる。差分の範囲を決め（上の「差分の範囲」）、〈ref〉..〈ref〉か〈ref〉...〈ref〉の形（ref は英数字・/・.・_・- だけで、- で始まらない）でなければ、そう伝えて止まる。ここまでは、どの形でも先に済ませる。そのあと見直しの形（$2）なら、上の「見直しの形」の節へ進む（codeReview が off・light のときの扱いだけ、その節に従う。以下の分かれ道は見ない）。見直しの形でなければ、codeReview が `off` なら、差分の確かめをせずに上の「codeReview」のとおり返して終わる。codeReview が `light` で、やり直しの形（$2）なら、差分の確かめをせずに、何も起動せず「軽くする設定のため、やり直しの確かめはしない」と返して終わる。`git diff --name-only 〈範囲〉` が空なら「差分なし」と返して終わる（やり直しの形のときは、前の回の直させるものを全部「直っていない」として返す）。上の「文書だけ」の見分け方に全部当たり、かつやり直しの形のときは、ほかの手順に進まず、何も起動せずに秘密と個人のパスの確かめだけを流し直し、手順9の形で返して終わる。文書だけに当たらず、上の「テストだけ」の見分け方に全部当たるときは、テストだけで回す（やり直しの形も手順7へ進む）。
2. 渡すものをそろえる。
   - verify の結果：run の手順5で流したコマンドと、通った・落ちた。この会話になければ「verify の結果なし」とする。
   - 前の回の直させるもの（やり直しの形のときだけ）：run の手順6で、このスキルを呼ぶ直前に run が本文に書き出したもの（前の回の review が返した「直させるもの」のまま）。「なし」と書き出されていれば、直しで新しく入った問題だけを確かめる。やり直しの形なのに書き出しが見当たらなければ、そう伝えて止まる。
   - やり直しの形なら手順7へ進む（レビュー役を起動しない）。
   - 見直しの形なら、上の「見直しの形」のとおりに検証役1つだけを起動して返す（ほかの手順に進まない）。
3. 差分の大きさを数え、小さな差分のしきい値と比べてレビュー役を起動する（codeReview が `light` か、上の「文書だけ」の見分け方に全部当たるなら、数えずにレビュー役を1つだけ起動し、5つの観点を全部見させる）。テストだけなら、正しさとテストの2つだけを渡し、しきい値まではレビュー役1つ、超えたら2つ並べる。worktree を分けさせない（isolation を指定しない）。落ちたときは、その場で手順6の扱いをする。
   - しきい値までなら、`orca-flow:code-reviewer` を1つだけ背景で起動し、5つの観点を全部見させる（観点ごとに分けて返させる。テストだけなら正しさとテストの2つ）。
   - しきい値を超えたら、5つの観点ごとに `orca-flow:code-reviewer` を1つずつ、5つ並べて背景で起動する（テストだけなら2つの観点ごとに2つ並べる）。
   - 渡すもの：観点の名前と上の表のその行（1つのときは表の5行すべて。テストだけの1つのときは正しさとテストの2行）、ID（$0）、設計書のパス、baseBranch、差分の範囲、verify の結果。
4. レビュー役の報告を全部待ち（起動し直した役の報告も含む）、指摘を観点の名前をつけたまま1つにまとめる。文書だけなら、指摘の有無によらず、先に上の秘密と個人のパスの確かめを流し、当たりを「直させるもの」に入れる。テストだけも同じで、指摘の有無によらず、先に秘密と個人のパスの確かめを流し、当たりを「直させるもの」に入れる（検証役は起動する）。指摘が1つもなければ検証役を起動せず、手順8へ進む。codeReview が `light` なら、検証役を起動せず、全部の指摘を「たぶん」として「報告に書くもの」に回し、手順8へ進む。文書だけなら、検証役を起動せず、上の「軽い回し方」のとおりに指摘を「タスク長が確かめるもの」と「報告に書くもの」に分け、手順8へ進む。
5. まとめた指摘のうち、「必ず直す」「直したほうがよい」だけを、1つの `orca-flow:review-verifier` に渡して背景で起動する（観点ごとに分けない）。「確認だけ」と「前からある」は渡さない。
   - 渡すもの：渡す指摘（そのまま。指摘ごとに観点の名前つき）、ID（$0）、設計書のパス、baseBranch、差分の範囲、verify の結果。
   - 渡さなかった「確認だけ」と「前からある」は、検証せずに手順9で「検証していない」として報告に回す。
   - 報告を待ち、検証役が「誤り」としたものは捨てる。手順8へ進む。
6. 落ちたときの扱い（手順3〜5と7の中で、その場で行う）。レビュー役か検証役が失敗した・決まった形（観点の名前をつけて指摘を並べる形）で返さなかったときは、同じものを渡して1回だけ起動し直し、それでもだめなら未実施とする。
   - 担当の種類（`orca-flow:code-reviewer`・`orca-flow:review-verifier`）が見つからないときは起動し直さず、「担当の種類が見つからない」と返して終わる（run がプラグインの再読み込みを頼む）。
   - レビュー役が未実施なら、その役が見るはずだった観点を「未実施」とする（指摘なしではない。1つにまとめたときは渡した観点の全部。テストだけなら正しさとテストの2つで、残る3つは「テストだけで絞った」のまま）。ほかのレビュー役の指摘は、手順4・5でそのまま検証役に通す。
   - 検証役が未実施なら、全部の指摘を「たぶん」として「報告に書くもの」に回し（直させない。渡さなかった「確認だけ」「前からある」は「検証していない」のまま）、手順8へ進む（最初の形のとき。やり直しの形では手順7の最後に従う）。
7. やり直しの形：1つの `orca-flow:review-verifier` だけを背景で起動する（レビュー役は最初の形の1回だけ）。テストだけなら、検証役を起動したうえで、秘密と個人のパスの確かめも流し直す。
   - 渡すもの：前の回の直させるもの（そのまま）、直した差分の範囲（$1。`〈直す前のコミット〉..HEAD`）、ID（$0）、設計書のパス、baseBranch、verify の結果。
   - 検証役は、前の回の直させるものを1件ずつ「直った」「直った（意図的な挙動変更）」「直っていない」で返し、直した差分で新しく入った問題があれば、確か・たぶん・誤りに分けて返す。意図的な挙動変更は、元と違うというだけで「直っていない」にしない。
   - 失敗した・決まった形で返さなかったときは1回だけ起動し直す。それでもだめなら、前の回の直させるものは全部「直っていない（確かめられなかった）」として扱い、コードレビューを「未実施」とする。
8. 残った指摘を、重さの順（「必ず直す」→「直したほうがよい」→「確認だけ」）に並べる。重さと「前からある」の印は、検証役が直したものを使う（直した理由も添える）。検証に回さなかったものは、レビュー役の重さと印のまま「検証していない」を添える。同じ場所への同じ指摘が2つの観点から来たら1つにまとめ、両方の観点を書く。
9. 最後に、次の4つ（文書だけのときは「タスク長が確かめるもの」を足した5つ）に分けて返す。指摘ごとに、観点、ファイルと行、起きること、直し方の案、確か・たぶんのどちらか、を書く。
   - 直させるもの：「確か」で「必ず直す」で、「前からある」ではないもの。やり直しの形では、前の回の直させるもののうち「直っていない」もの（前の回からの印をつける）と、直しで新しく入った「確か」の「必ず直す」もの。
   - タスク長が確かめるもの（文書だけのときだけ）：レビュー役の「必ず直す」「直したほうがよい」で「前からある」ではないもの。run が根拠を開いて確かめる。
   - 報告に書くもの：「たぶん」のもの、「直したほうがよい」「確認だけ」のもの、「前からある」もの。「確認だけ」と「前からある」は「検証していない」と添える。
   - 前の回の直させるものの結果（やり直しの形のときだけ）：1件ずつ、直った・直った（意図的な挙動変更）・直っていない。
   - 件数：最初の形では観点ごとに、見つけた数、検証に回した数、誤りで捨てた数、検証していない数、残った数。レビュー役を1つにまとめたか5つ並べたかも書く。テストだけのときは、見ない3つの観点（セキュリティ・設計・運用と互換性）に「テストだけで絞った」と書き、「未実施」と書かない。レビュー役の数は1つか2つで書く。未実施の観点は「未実施」と書き、落ちた役（レビュー役か検証役）を添える。

直させるものを担当に戻すこと、直したあとのやり直し、報告への書き方は、run の手順6に従う。

run から呼ばれたときは、返したあと番を終えずに、そのまま run の手順6の続きに進む（確認役の結果を待ち、直させるものを担当に戻す）。
