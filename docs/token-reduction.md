# L2 と段3 のトークン消費メモ

2026-10-30 時点。L2（run を新しい会話で始める）と段3（検証役には直す指摘だけ渡す）を入れたときの、変更前後のトークン消費を比べるためのメモ。数値は Opus の重み1（入力×1＋作成×1.25＋読み×0.1＋出力×5）を主に使う。M は100万。

## 変えたこと

- **L2**：`orca-flow approve` が、タスク長のターミナルに `/clear` を送ってから `/orca-flow:run` を送る。設計書に「設計の経緯（run のときに読む）」を足し、run は設計で読んだファイルをむやみに読み直さない。
- **段3**：`/orca-flow:review` が検証役に渡すのを「必ず直す」「直したほうがよい」だけにする。「確認だけ」と「前からある」は渡さず、報告に「検証していない」と書く。タスク長は、直させる前に根拠のファイルと行を開いて確かめる。

## 変更後の見込み

| 変更 | 重み1の見込み           | 重み2の見込み  | 備考                                                       |
| ---- | ----------------------- | -------------- | ---------------------------------------------------------- |
| L2   | 0.74〜7.1M 減（2〜20%） | 0.56〜2.31M 増 | `/clear` でキャッシュが冷える分。長い run ほど得           |
| 段3  | 2.6〜2.8M 減            | 未見積り       | 検証役の入力を半分ほどにし、タスク長の根拠確認を足した差引 |
| 合計 | 3.3〜9.9M 減（6〜19%）  | 不明           | 2つを同時に入れるため、個別の効果は分けない                |

L2 は、設計で読んだ仕様・コードが run の各ターンから消えることで減る。ただし新しい会話の最初にキャッシュを書き直すので、短い run では逆効果になりうる。段3は、直さない「確認だけ」「前からある」を検証しなくなることで減る。

## 測り方

1. 変更を入れたあとに始まった5タスクを取る。設計と run が別の会話になるので、`docs/lead-context/turns.csv` の `conv=2` を使う。
2. 次の値を、変更前と同じ決め方で出す。
   - run 以降の1ターンあたりの重み1
   - 設計と設計の直しの1ターンあたりの重み1
   - 2つ目の会話の報告のときの文脈
   - タスクごとの重み1・重み2
   - 検証役に渡した指摘数と、渡さなかった指摘数
3. 比べる相手は、L1 後の5タスク。L1 の窓が閉じていなければ、以前の計測の中央値を仮の基準にする。
4. 2つを同時に入れているので、全体の前後差は分かるが、L2 と段3の寄与は分けない。分けたいときは、片方だけ戻した5タスクをもう1組取る。

## 戻す条件

- L2：run の1ターンあたりの重み1が10%以上減らない。設計の経緯が原因の抜けが5タスクで1件。run 中の `status question` が3件以上増える。
- 段3：最終報告に残る誤りが2件以上増える。直させるものに誤りが1件でも入る。
- 合計：5タスクの重み1が、変更前の中央値より減らない。
