# 決定の記録

orca-flow の設計で「なぜこの形か」「どの案を捨てたか」を残す、追記だけのファイル。設計書と報告は公開に出さないので、公開の読み手はここで経緯を読む。

- 末尾に足すだけで、書いた項は書き換えない。
- 1つの決めごとを1つの項にし、足した順（統合の順）に並ぶ。日付は項を足した日なので、前後することがある。写した過去の項は統合の日の順。項の前には空行を1行入れる（統合で空行がまとめられることがある）。
- 項の見出しは「## 〈日付〉 〈見出し〉」。ほかの項を指すときは、この日付と見出しで指す。
- 本文は「決めたこと」「理由」「捨てた案と理由」「人が選んだこと」の箇条書き。ないものは「なし」と書く。
- 記録を始めるまでの決めごとのないタスクは、写した項のあとの「決めごとなし」の一覧に並べた。そのあとの項は一覧のうしろに足す。決めごとのないタスクは項を足さない。

## 2026-10-23 テストをタスク側の verify で流す

- 決めたこと：テストはタスクのコンソールの `verify` で流して記録を残し、integrate は記録を確かめてマージだけをする。記録が使えない場合の道（`--verify-here`）と、テストを飛ばせる場所の設定（verifySkipPaths）を持つ。差分が空のときは、すべて飛ばせる場所の中とはみなさない。設計書と報告も特別扱いしない。
- 理由：統括役のコンソールがテストの間ずっと待たなくなる。
- 捨てた案と理由：run のスキルと仕様書の変更を同じタスクに入れる案は、別の小さなタスクで入れることにした。その間は、統合が一度戻され、タスク長に verify のやり直しが送られる。急ぐときは `--verify-here` で今までどおり統合できる。

## 2026-10-23 コードレビューの仕組み

- 決めたこと：run の確認のあとに、5つの観点（正しさ・セキュリティ・設計・テスト・運用と互換性）を別々のレビュー役が読み、検証役が確かめた指摘だけを直させる。小さな差分（足した行と消した行の合計が300行まで）では、レビュー役を1つにまとめる。やり直しは検証役だけで確かめる。レビューの一言は、review の中でなく run が出す。
- 理由：小さな変更にもセキュリティの穴は入りうるので、どのタスクでも毎回流す。トークンを減らす3つの工夫（小さな差分でレビュー役1つ、検証役は1つ、やり直しは検証役だけ）は、実装中に人が決めた。一言を run が出すのは、統合待ちのタブで手で打つとカードを壊すため。300行は担当が決めた値で、実測の根拠はない。
- 捨てた案と理由：Claude 以外のモデルでレビューする案は、Claude が書いたコードを別系統のモデルが見ると正答率が下がったという比較があるので、今回は使わない。
- 人が選んだこと：Claude 以外のモデルを使わない・毎回流すは、おすすめどおり（承認で決まった）。トークンを減らす3つは、実装中に人が決めた。

## 2026-10-23 古い記録でもマージする

- 決めたこと：記録のあとに main で変わったファイルが「テストに関係しない場所」だけなら、integrate はテストを流さず、タスクの worktree で rebase してからマージする。「テストに関係しない場所」は、テストを飛ばせる場所の設定に、既定の設定ファイルと進捗表を足したもの。設定ファイルの変更もテストに関係しないとして扱い、記録のコマンドと今の verify の比べは今までどおり行う。rebase が競合したら取りやめてテストのやり直しにする。

## 2026-11-03 決定の記録の行が union でまとめられて消えるときは、取り込みと verify で止める

- 決めたこと：PR の道の後始末の取り込みで、取り込む前の手元の記録が取り込んだあとの記録の先頭に残らなければ、取り込みを戻して「後始末で止まった」にし、直し方を出す。戻すときは未コミットの変更を消さない戻し方にし、戻せなかったときも投げずに止まった扱いにして、マージが残っていることと戻し方を文に書く。
- 決めたこと：タスク長の verify でも、rebase のあと main の記録がタスクの記録の先頭に残らなければ止める。見出しの前の空行の欠けは戻してコミットする。
- 理由：union は2つの足しの最後の共通の行を1つにまとめ、手元の項の最後の行が消えて見出しがくっつく。今は何も知らせずに進み、あとの整形の確かめで原因の分からないまま落ちる。
- 捨てた案と理由：消えた行を CLI が組み直す案（同じ項が両側に別のコミットで入ると重なる）。警告だけで後始末を続ける案（背景の待ち受けの警告は人の目に届かない）。
- 人が選んだこと：行が消えるときは取り込みを戻して止める（警告だけで進めない）は、おすすめどおり（おまかせで統括役が決めた）。verify が止まるようになったため、すでにある push のテストの準備の順を変えることを、人が書き込んでよい場所に足して許した。

## 2026-11-03 PR でマージしたタスクも、依存の見分けで入ったと分かるようにする

- 決めたこと：PR のマージを見つけた後始末が、そのタスクの push の記録に GitHub のマージのコミットと時刻を足す。依存が入ったかは、件名の行か、記録のコミットが比べる先のブランチの祖先かで決める。見分けは CLI の1つの関数と読み出しのサブコマンドにし、intake と CLI のマージの前の確かめが同じものを使う。マージのコミットが GitHub から取れないときは書かずに続け、記録に書けないときだけ警告を1行出す。
- 理由：GitHub のマージのコミットの件名は squash などで決まった形にならず、件名だけでは見分けられない。手元の git だけで祖先かを決められる。取れないときに警告を出すと、今の push の後始末の出力の決まり（標準エラーは空）を変えることになるため。
- 捨てた案と理由：取り込んだあとの手元の先頭を記録する案は、2回目で値が変わるので捨てた。作業中のタスクの一覧に足す案は、統合済みのタスクが出ないので捨てた。
- 人が選んだこと：なし（決めてほしいことはなかった）。
