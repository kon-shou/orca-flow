# 公開用のスクリプト

このリポジトリを public に上げるための道具。main から抜くパス（`exclude.txt`）を除いたコミットを `public` ブランチに作り、push を `public` から GitHub の `main` への1本だけに限る。orca-flow の CLI ではなく、このリポジトリ用の開発の道具。

入口は `node scripts/public/main.ts 〈build|check|local|pre-push|setup〉`。メッセージは標準エラーに出る。終了コードは 0＝成功、1＝確かめに落ちた・失敗、2＝人の作業が先に要る（名前・語の一覧・フックの衝突など）。

| サブコマンド                                                   | することと、止めるもの                                                                                                       |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `setup --name 〈名前〉 --email 〈メール〉 [--remote 〈名前〉]` | 公開用の名前とメールを git の設定に書き、`pre-push` のフックを置き、remote があれば `remote.〈名前〉.push` を設定する        |
| `build [--message 〈文〉]`                                     | main の木から抜くパス（`exclude.txt`）を除いて `public` にコミットを作る。check に通ったときだけ `public` を進める           |
| `check [〈コミット〉]`                                         | 抜くパス・語・作者・ID の形・秘密などの形を確かめる。既定は `public`。語の当たりは語を出さず、パスと「何番目の語か」だけ出す |
| `local`                                                        | 公開に出るファイルを、コミットする前の手元の作業ツリーで確かめる（下の「手元の確かめ」）                                     |
| `pre-push`                                                     | フックから呼ばれる。`public` を `main` へ送るときだけ通し、送る範囲の全コミットに check をかける                             |

## 手元の確かめ

`node scripts/public/main.ts local` は、公開用の確かめのうち、語の一覧の要らないものを、build の前に手元で流す。`pnpm test` のテストでも、このリポジトリに対して流れる（落ちたら当たりの一覧が出る）。

- 確かめる中身：追跡中のファイルの作業ツリーの中身（コミットしていない変更を含む）から一時の木を作り、その木の `exclude.txt` で抜いたもの。追跡外のファイルは見ない。作業ツリー・index・HEAD・ブランチは変えない。
- 確かめること：抜くパスが残っていないこと、ID の形（`idPrefix` はその木の `.orca-flow/config.json` から読む）、手元のパス、秘密などの形（下の「秘密・メール・Windows のパス・ページの ID の形」）。パス・中身・シンボリックリンクの行き先を見る（秘密などの形は中身だけ）。
- 語の一覧：置いてあるときだけ確かめる（なければ、または空なら、語は飛ばして終了コード0か1を返す）。当たりは「何番目の語」だけ出し、語は出さない。
- 手元のパスの規則：Mac のホームの頭の形と、流した人のホームのディレクトリ（環境変数 `HOME`）の文字。大文字小文字を区別しない。頭の形は左が英数字・`_`・`.`・`-` でないときだけ（API のパスや URL の途中にある形は拾わない）、`HOME` は右が英数字・`_`・`-` でなく、`.` のあとに英数字・`_`・`-` が続く形でもないときだけ当てる（文の終わりの `.` は当てる）。パスの照合は先頭に `/` を足して同じ規則で見る。パスに手元のパスを含むファイルの当たりは、パスを出さず件数だけにする。`HOME` がないか、ルートの1段（`/` や `/root`）なら、`HOME` の規則だけ飛ばす。偽の値に使う `/home/someone/` のような形は拾わない。出力には「手元のパス」と場所だけ出し、ホームのディレクトリの文字は出さない。
- 終了コード：当たりがあれば1（一覧を標準エラーに出す）、なければ0。

## 初めて公開する手順

1. **語の一覧を作る**：`"$(git rev-parse --git-common-dir)/orca-flow/public-words.txt"`（普通は `.git/orca-flow/public-words.txt`）に、公開してはいけない語を1行1語で書く（`#` はコメント）。git の外に置くので、コミットされない。一覧そのものを文書やメッセージに書かない。ない・空だと build と check は終了コード2で止まる。
2. **setup**：`node scripts/public/main.ts setup --name 〈公開用の名前〉 --email 〈公開用のメール〉`。違うフックがすでにあるか `core.hooksPath` があると、書き換えずに終了コード2で止まる（自分で統合する）。
3. **build**：`node scripts/public/main.ts build`。最初は親のないコミットができる。作業ツリーと index と main は変わらない。build は始めにフックの効きを確かめる（`core.hooksPath` がない、`pre-push` が setup の書いたもので実行できる、フックが指す `main.ts` がある）。1つでも欠けると、`public` を作らず・進めずに終了コード2で止まる（setup の前に build するとここで止まる）。語が見つかると `public` を進めずに終了コード1で止まる。
4. **check**：`node scripts/public/main.ts check`。`public` をもう一度確かめる。
5. **GitHub にリポジトリを作る**：空のリポジトリを作り、下の「ルールセット」を先に設定する。
6. **remote を足して setup をもう一度**：`git remote add origin 〈URL〉` のあと、手順2と同じ setup を流す。`remote.origin.push` が `refs/heads/public:refs/heads/main` になる。
7. **push（人が行う）**：`git push origin`。フックが、送る範囲の全コミットに check をかけてから通す。`git push origin main` や `--all`・`--mirror` はフックが止める。

## GitHub のルールセット

- main への force push を禁止する。
- main 以外のブランチを作らせない（ブランチの作成を制限する）。

## 公開を更新する

1. 手元の main を更新する（普通の開発のとおり）。
2. `node scripts/public/main.ts build`。木が前の `public` と同じなら何も作らず終了コード0。
3. `git push origin`（人が行う）。

### GitHub で入った変更を取り込んだあとの更新

GitHub 側で入った変更（プルリクエストなど）は、手元の main に pull せず、`git cherry-pick` で取り込む。そのあとの更新は次の順で行う。

1. `git fetch origin`
2. `git branch -f public origin/main`（`public` を GitHub の main に合わせる。そうしないと、push が先に進めない形になる）
3. cherry-pick した main で `node scripts/public/main.ts build`
4. `git push origin`

## 守ること

- push に `--no-verify` を使わない。フックは公開用の確かめの最後の砦。
- build はフックの効きを確かめる。setup のあとでフックが外れたり `core.hooksPath` が足されたりすると終了コード2で止まるので、理由を直して setup を流し直す。`--no-verify` だけは確かめられないので、上のとおり使わない。
- フックは setup した時の `main.ts` と node を使う。ブランチを統合して `main.ts` の場所が変わったら、メインの作業ツリーで setup を流し直す。node を入れ替えたときも、setup をもう一度流す（フックの node が見つからないと、push は日本語のメッセージで止まる）。
- 抜くパスは、流した作業ツリーではなく main の `scripts/public/exclude.txt` から読む。変えたら main にコミットしてから build する。

## 抜くパス

main の `scripts/public/exclude.txt` に1行1パスで書く（`#` はコメント、末尾の `/` はディレクトリ）。一覧はこのファイルだけを正にして、ここには並べない（並べると、足すたびに直し忘れてずれる）。抜くのは、タスクの記録・調べた結果・測った記録・手元の道具とそのテストのような、環境ごとのもの。check は、これらが木に残っていないことも確かめる。公開の木のファイルは、抜くパスの中のファイルを import しない（テストで確かめる）。

公開の木のコードとテスト（`.ts`・`.js`・`.mjs`・`.cjs`）は、抜くパスの中に実在するファイルのパスを文字のまま書かない（`test/scripts/public/named.test.ts` で確かめる）。公開の clone ではそのファイルがないので、読むテストが落ちる。私的な文書を読むテストは、パスを実行時につないで作り、ファイルがないときは `describe.skipIf` で飛ばす。当たりは「ファイル：行：名指しされたパス」で出る。

## ID の形

タスクの番号は clone した環境ごとに作られるので、公開の木には出さない。check は、公開の木のパスと中身、コミットのメッセージに「ID の形」があると、終了コード1で止める（build・check・pre-push のどれでも効く）。

- ID の形：main の `.orca-flow/config.json` の `idPrefix`（ファイルがなければ既定値の `T`）のすぐあとに数字が1つ以上、英小文字が0〜1個、そのあとが ASCII の英数字でないもの。前も ASCII の英数字でないこと（行頭は可）。大文字小文字は区別する。`idPrefix` が読めない・形が違うと終了コード2。
- 例（`idPrefix` が `Q` のとき）：`Q12`・`Q12a`・`（Q12）`・`Q12-名前` は当たり、`xQ12`・`Q12X`・`HTTP2`・`…/Q96Sfx` のように英数字が続く形は当たらない。記号に挟まれた並びは当たりうる（下の「ID の形の限界」）。
- 中身は文字のファイルだけ見る（NUL を含むファイルはバイナリとして見ない。`.gitattributes` の binary・-diff では飛ばさない）。シンボリックリンクの行き先も見る。例外のパスの一覧はない。
- 当たりは「ファイル：行：当たった語」で出る。語の一覧の当たりと違い、語を隠さない。パスとメッセージの当たりも語を出す。ただしパスに語の一覧の語を含むファイルの当たりは、件数だけ出す。
- 当たったら、公開に残すファイルなら、番号を中身の言葉に直す（例の ID は仕様の作り物にする）。環境ごとのファイルなら、`exclude.txt` に足して抜く。

## 秘密・メール・Windows のパス・ページの ID の形

check は、公開の木の中身に次の形があると、終了コード1で止める（build・check・pre-push・local のどれでも効く）。パス・シンボリックリンクの行き先・コミットのメッセージは見ない。NUL を含むファイルはバイナリとして見ない。

| 種類                       | 形                                                                                                                                                                                         | テストのファイルの中 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------- |
| トークンの形               | `ghp_`・`github_pat_`・`sk-`・`xoxb-`・`xoxa-`・`xoxp-` の頭に英数字・`_`・`-` が20文字以上、`AKIA` に英大文字・数字が16文字。頭の左が英数字・`_`・`-` のときは当てない                    | 見ない               |
| 秘密鍵の頭の行             | `-----BEGIN 〈…〉 KEY-----` のうち、PEM の秘密鍵の頭の行                                                                                                                                   | 見ない               |
| パスワードつきの接続文字列 | URL の `://` のあとに、ユーザー（空でもよい）と `:` とパスワードと `@` が続くもの。パスワードが `〈`・`${`・`<` で始まる置き場は当てない                                                   | 見ない               |
| メールアドレス             | 英数字などの名前と `@` とドメイン。架空のドメイン・公開用のメール・名前が `git` のもの・URL の認証情報の中は当てない                                                                       | 見る                 |
| Windows のパス             | `〈ドライブ〉:\Users\`・`\\wsl.localhost\〈名前〉\home\`・`\\wsl$\〈名前〉\home\`・`/mnt/〈ドライブ〉/` のあとに名前の文字（英数字・`.`・`_`・`-`）が続くもの。区切りの `\` は重ねてもよい | 見ない               |
| 32桁の16進                 | 前後が英数字でない32桁の16進（Notion のページの ID など）。40桁のコミットの番号の一部は当てない                                                                                            | 見ない               |

- 架空のドメイン：`example.com`・`example.net`・`example.org`（とその下のドメイン）と、末尾が `.example`・`.invalid`・`.test`・`.localhost` のもの。
- 公開用のメール：check・build・pre-push では git の設定の公開用のメール（setup で書いたもの）を当てない。local では、git の設定にあるときだけ当てない（なくても止めない）。
- テストのファイル：どの階層でも `test/`・`tests/`・`__tests__/`・`__snapshots__/` の下のファイルと、名前が `*.test.*`・`*.spec.*`・`*_test.*`・`test_*.py` のもの（レビューのスキルの見分け方と同じ）。ただし秘密を置くファイル（`.env*`・`*.pem`・`*.key`・`id_rsa*`）は、テストの場所の下でもテストのファイルにしない。テストの作り物の秘密・パス・ID は当てないが、メールは架空のドメインで書く。
- 例外の決め方：例外のパスの一覧はない。テストでないファイルで当たったら、値を消すか作り物の形（架空のドメイン、`…` で切った説明、`〈名前〉` のような置き場）に直す。接続文字列のパスワードは、`〈パスワード〉`・`${token}`・`<password>` のように `〈`・`${`・`<` で始まる置き場にする。説明のために形そのものを書くコード（この確かめのような）は、文字を実行時につないで作る。
- 当たりは「ファイル：行：種類」で出し、値は出さない。パスに語の一覧の語か手元のパスを含むファイルの当たりは、パスも出さず、種類ごとの件数だけ出す。

### 秘密などの形の限界

- 形にない秘密（ほかのサービスのトークン、頭のない長い乱数、パスワードだけの設定の値）は拾わない。
- ハイフンでつないだ形の ID（UUID の形）、32桁でない ID、英数字に挟まれた16進は拾わない。逆に、32桁の16進のハッシュ（MD5 など）は当たる。
- メールの形は、`〈名前〉@2x.png` のようにドメインに見えるファイル名にも当たりうる。
- ファイルのパス・コミットのメッセージ・シンボリックリンクの行き先は見ない（メッセージは build が作る）。
- 抜くパスの名指しの確かめは、文字のまま書いたパスだけ拾う。つないで作ったパスや、`path.join` に区切って渡したパスは拾わない。

## ID の形の限界

ID の形の確かめは、記号に挟まれた並び（例：`integrity: sha512-abc/〈接頭辞〉3+xyz==` の `〈接頭辞〉3`）に当たりうる。例外の一覧はないので、当たったら依存の版を変えてハッシュを変えるか、例外を作るタスクを立てる。

## 限界

check の語の照合には、次の限界がある。語の一覧を作るときに気をつける。

- パスの照合の大文字小文字の区別なしは ASCII だけ。ASCII 以外は、語の元の形・小文字・大文字で一致するものだけ見つかる。大文字小文字が混ざった形は取りこぼすことがある。
- 正規化の形が違うパス（NFD など）は、語が NFC の形だと見つからない。
- 中身の照合は `git grep -F -i` で行う。ASCII 以外の大文字小文字の区別なし、`\E` を含む語は、中身で当たらないことがある。
- シンボリックリンクの行き先は、別に読んで照合する（件数だけ出す）。
